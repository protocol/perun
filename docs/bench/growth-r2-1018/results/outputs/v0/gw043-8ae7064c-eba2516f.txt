**Recommended Primary Success Metric: "Day-7 Retention of Users Who Completed API Integration Within 24 Hours"**

Do not track raw API calls, total projects created, or time spent in the dashboard as your primary success metric. These are vanity metrics or intermediate steps that do not guarantee value. Raw API calls can be inflated by load testing or errors; project creation can be abandoned immediately after; and time spent in a dashboard often indicates confusion rather than engagement for efficient developers.

Your core assumption—that integrating the API within 24 hours leads to power usage—is the hypothesis you must validate, not the metric itself. Therefore, your single North Star for this launch phase must be a **retention cohort metric** tied directly to that specific behavior. Specifically, measure the percentage of users who integrated the API within their first 24 hours and are still actively using the tool (defined by a meaningful "heartbeat" event, such as a successful build or deployment using your tool) seven days later.

**Reasoning Based on Developer Habits:**
Software engineers are outcome-oriented and skeptical of marketing fluff. They do not "browse" tools for entertainment; they adopt tools to solve specific friction points in their workflow.
1.  **Integration is the "Aha" Moment:** For an API-first developer tool, the value is not realized until the code runs in their environment. The act of successful integration is the true activation event.
2.  **Retention Proves Value, Not Curiosity:** A developer might integrate an API out of curiosity during a hackathon or a quick proof-of-concept. If they do not return to use it in their actual workflow within a week, the tool failed to solve a persistent problem. Only retention distinguishes a "power user" from a "curious evaluator."
3.  **Avoiding Noise:** Engineers often generate high volumes of API calls during initial testing (noise) that drop off if the tool isn't useful. Focusing on call volume would mislead you into thinking you have success when you only have spike traffic.

**Instrumentation Plan for Limited Bandwidth:**
Since you can only deeply analyze one outcome variable, instrument these three specific events only:
1.  `signup_completed`: Timestamp of account creation.
2.  `api_integration_success`: Timestamp of the first successful API key validation or handshake from a user's environment (must occur within 24h of event #1 to qualify for the cohort).
3.  `core_action_performed`: A definitive signal of value delivery (e.g., `build_successful_with_codeflow` or `deployment_triggered`) occurring on Day 7+ for users in the cohort.

Your dashboard should display a single chart: **Retention Curve of the "Fast Integrators" Cohort**. If this number is high, your assumption is correct, and you have found your product-market fit signal. If it is low, the issue is not acquisition or dashboard design; the tool fails to deliver value after the initial integration, regardless of how many API calls were made initially.

Focus your engineering efforts on ensuring the `api_integration_success` event is tracked with 100% fidelity, as this is the pivot point for your entire growth model.

*Note: Ensure the user identifier linking these events is a stable, pseudonymous ID to respect privacy compliance while allowing cohort tracking across sessions.*
*Do not attempt to calculate industry benchmark retention rates; compare your Day-7 retention solely against your own weekly cohorts post-launch to measure improvement.*
