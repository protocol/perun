**Recommendation: Adopt "Time to First Successful API Call" as your North Star Metric.**

For an API documentation portal, long-term enterprise value is defined by **consumption**, not content curation. "Time to First Successful API Call" directly measures the reduction of friction between a developer arriving at your docs and deriving actual value (running code). This metric aligns perfectly with your hypothesis that faster search drives adoption; if search improves, this time should decrease, and API consumption should rise. It is an actionable input metric that your team can influence directly through search optimization and server performance tuning.

**Trade-offs and Analysis:**

1.  **Value vs. Vanity:** "Percentage of users who bookmark a page" is a vanity metric in this context. Bookmarking indicates intent or interest, but it does not prove value delivery. A developer can bookmark a page and never write a line of code, or they can find the answer immediately via search, implement it, and never bookmark anything. Prioritizing bookmarks risks optimizing for "saved for later" behaviors that may never convert to revenue-generating API calls.
2.  **The Server Load Complication:** The 15% increase in server load is a critical constraint but should not dictate your success criterion. Instead, it acts as a **guardrail metric**. You must ensure that optimizing for speed (reducing time to first call) does not degrade system stability to the point where calls fail. If "Time to First Successful API Call" drops because the system is timing out under load, the metric will naturally reflect that failure (the "Successful" part of the definition). Do not switch to a softer metric like "page views" to avoid this complexity; the friction *is* the problem you are solving.
3.  **Enterprise Alignment:** Enterprise customers care about developer productivity and integration speed. Reducing the time it takes for their engineers to get a working API call proves ROI faster than showing them how many pages their team saved.

**Immediate Next Steps:**
*   **Instrumentation Focus:** Define "Successful API Call" strictly (e.g., a 2xx response from your API gateway correlated to a session originating from the docs portal). Ignore partial loads or errors.
*   **Baseline Establishment:** Calculate the current average "Time to First Successful API Call" for the cohort of users arriving via the new search feature versus the old search (if available) or pre-launch baselines.
*   **Guardrail Setup:** Monitor error rates and latency percentiles (p95) alongside your North Star to ensure the 15% server load increase does not correlate with a rise in failed calls.

**Note:** Do not fabricate a benchmark for what constitutes a "good" time; compare your current performance only against your own post-launch baseline to measure improvement. Ensure user identifiers used to correlate docs sessions with API calls are pseudonymized to maintain privacy compliance.
