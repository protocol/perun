### Success Framework: The "Secure Efficiency" Ratio

Do not evaluate speed and support costs in isolation. For a legal firm, **security reliability is the product**; speed is only valuable if access is guaranteed. Define success using a composite metric: **Net Secure Sessions per Hour**.

**Formula:** `(Total Successful Logins × Core Action Retention) / (Total Support Minutes + Failed Login Attempts)`

This metric rejects the vanity of "average login time" if it comes at the cost of blocked users. A 45-second speed gain is a net loss if it generates 13 extra support tickets weekly, as each ticket represents a lawyer unable to bill hours and a potential security breach investigation.

**The Decision Matrix for the CSO**
Present the rollout decision based on these three thresholds, derived from your own baseline, not external benchmarks:

1.  **The Blocker Rate (Primary Guardrail):** Calculate the percentage of login attempts resulting in a support ticket or failure.
    *   *Threshold:* If the blocker rate for biometric users exceeds the password baseline by >0.5%, **STOP**. Speed is irrelevant if lawyers cannot enter the system.
    *   *Current Status:* **UNVERIFIED**. You have ticket volume (15/week) but lack the total login attempt count for the 5,000 users to calculate the rate.

2.  **The Resolution Cost (Operational Tax):** Measure the average time to resolve a biometric ticket vs. a password reset.
    *   *Hypothesis:* Biometric issues (sensor compatibility, enrollment errors) often require manual IT intervention, whereas password resets are automated.
    *   *Threshold:* If the *total* weekly support minutes for biometrics exceeds the time saved by the 5,000 users (5,000 users × sessions/week × 45 seconds), the feature burns money.

3.  **The Root Cause Split (Diagnostic):** Segment the 15 tickets into "User Error" (e.g., forgotten enrollment) vs. "System Failure" (sensor incompatibility).
    *   *Action:* If >40% are "System Failure," the sensor logic is flawed for your specific hardware mix. Do not expand.

**Immediate Next Steps (Before Tuesday)**
1.  **Instrument the Denominator:** Query logs for total login *attempts* (success + failure) for the beta group since Jan 10. Without this, the 15 tickets are noise; with it, you have a failure rate.
2.  **Tag the Tickets:** Manually audit the 15 recent tickets. Label each as `User_Error` or `System_Flaw`. This single cut determines if you need better onboarding (training) or a code fix (compatibility).
3.  **Compute the Break-Even:** Calculate exactly how many additional successful logins per hour are needed to offset one support ticket. If one ticket costs 20 minutes of IT time, you need ~27 successful logins (saving 45s each) just to break even on *one* ticket.

**Verdict Path:**
*   **Expand:** Only if the *failure rate* is flat or lower than passwords, AND the *resolution cost* is automated.
*   **Kill:** If the failure rate is higher AND the root cause is `System_Flaw`.
*   **Iterate:** If the failure rate is acceptable but `User_Error` is high; deploy targeted in-app guidance before expanding.

Do not present "average speed" to the CSO. Present the **failure rate** and the **net time impact** (speed gained minus support time lost). Anything else is vanity.

*Note: The 30% speed assumption is already exceeded (45s), but this is a trap if retention drops. Verify if users are abandoning the app after failed biometric attempts.*
