### Measurement Directive: API Rate Limiting Launch

**Primary Success Metric: Rejected Request Rate by Tier**
Track the count and percentage of requests returning `429 Too Many Requests` segmented by user tier (Free vs. Paid). This is your leading indicator for both stability and sentiment.
*   **Stability Signal:** A high volume of rejected requests from the Free tier confirms the limiter is absorbing the load that previously caused outages.
*   **Sentiment Signal:** A spike in rejected requests from *Paid* tiers indicates a configuration error that will immediately drive support tickets and churn.

**Secondary Metric: P95 Latency for Valid (200 OK) Requests**
Monitor the 95th percentile latency only for successful requests. Do not average latency across all requests, as the inclusion of instant `429` rejections will artificially lower the average and mask performance degradation on valid traffic.
*   **Threshold:** Alert if P95 latency increases by >10% compared to the pre-launch baseline. This detects if the limiting logic itself is introducing system drag.

**Critical Data Points to Instrument (Due Friday)**
Ensure engineering adds these specific fields to every API log entry before Tuesday:
1.  `response_status_code`: Specifically flag `429`.
2.  `user_tier`: Free, Pro, Enterprise (essential for segmentation).
3.  `rate_limit_remaining`: The number of requests left in the window (helps CS debug user complaints).
4.  `rate_limit_reset`: Timestamp when the limit resets (for user communication).
5.  `request_processing_time_ms`: Duration excluding queue time (to isolate limiter overhead).

**Immediate Alerting Rules**
Configure alerts for the Customer Success and Engineering teams to trigger on:
*   **Critical:** Any `429` errors generated by users on Pro or Enterprise tiers (indicates misconfiguration).
*   **Warning:** Free tier `429` error rate exceeds 5% of total Free tier traffic (indicates potential widespread friction).
*   **Performance:** P95 latency for 200 OK responses rises above baseline +10%.

**Support Readiness Metric**
Track the ratio of `429` errors to incoming support tickets tagged "API Limit" or "Rate Limit."
*   **Goal:** Establish a baseline conversion rate (e.g., 1 ticket per 1,000 rejected requests). If this ratio spikes post-launch, your error messages or documentation are unclear, requiring immediate copy updates.

**Decision Framework for Launch Day**
*   **If Free Tier Rejections are High & Paid Rejections are Zero:** The system is working as intended. Monitor support volume.
*   **If Paid Tier Rejections > 0:** Immediately rollback or adjust thresholds; this directly threatens revenue.
*   **If Latency Spikes without Rejections:** The limiting logic is inefficient; prepare to optimize code while monitoring stability.

Do not track "total requests" as a primary metric, as a drop in total volume is an expected and desired outcome of this feature. Focus exclusively on the *quality* of traffic allowed through and the *protection* afforded by rejections.

Note: Ensure `user_tier` is populated in logs even for anonymous or unauthenticated calls if they are subject to IP-based limiting.
Verify that timezones for `rate_limit_reset` match the user's local time or clearly state UTC to reduce support confusion.
