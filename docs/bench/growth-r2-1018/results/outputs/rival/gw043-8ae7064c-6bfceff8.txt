**Recommended Primary Success Metric: API Integration Completion Within 24 Hours**

Do not track raw API calls, project counts, or dashboard time as your primary success metric. Instead, define a binary event: `api_integration_completed` triggered when a user successfully executes their first authenticated API request that returns a 200 OK status within 24 hours of signup.

**Reasoning for Developer Audiences**

Software engineers exhibit distinct behavioral patterns that render vanity metrics misleading:

1.  **Dashboard Time is Noise:** Developers spend minimal time in UI dashboards. Their workflow occurs in IDEs, terminals, and documentation tabs. High "time spent in dashboard" often indicates confusion or broken documentation, not engagement. Optimizing for this metric could lead design teams to create cluttered interfaces that trap users rather than empowering them.

2.  **Project Counts are Premature:** Creating a project is often a sandbox activity. A developer might create five projects to test edge cases and abandon all of them. This measures curiosity, not commitment. It lacks the friction required to signal true intent.

3.  **Raw API Calls are Volatile:** A single script might generate 10,000 calls in a load test, while a genuine power user building a complex integration might only make 50 calls initially. Volume correlates poorly with early-stage retention; it measures scale, not adoption depth.

**The "Hello World" Moment**

For developer tools, the critical retention threshold is the "Hello World" moment—the point where the user moves from reading about the tool to successfully using it in their own environment.

Your core assumption states that integrating within 24 hours predicts power user status. Therefore, your metric must directly measure that specific integration event. By tracking `api_integration_completed`, you align your engineering and design teams around a single, high-signal outcome: reducing the time-to-first-successful-call.

This metric forces the right optimizations:
*   **Engineering** focuses on SDK stability, clear authentication flows, and error message clarity.
*   **Design** prioritizes documentation findability and copy-pasteable code snippets over dashboard aesthetics.
*   **Product** can clearly segment users into "Integrated" vs. "Not Integrated" to analyze downstream retention without data noise.

**Implementation Directive**

Instrument your analytics to fire a single event upon the first successful API response linked to a new user account. Tag this event with the latency from signup to integration. Ignore all other behavioral metrics for the initial launch analysis. This binary signal provides the cleanest correlation to your retention hypothesis and respects the workflow realities of your technical audience.

*Note: Ensure your tracking captures the HTTP status code to distinguish between failed attempts and successful integration.*
*Re-evaluate secondary metrics like call volume only after validating the correlation between this primary event and Day-30 retention.*
