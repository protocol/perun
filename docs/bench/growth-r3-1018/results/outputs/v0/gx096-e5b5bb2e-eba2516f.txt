### Data Integrity Remediation Plan for GlobalChic

**Objective:** Isolate the root cause of duplicate purchase events, clean historical data, and validate corrected financials before the November 5th earnings call.

#### Phase 1: Root Cause Diagnosis (Days 1–3)
Do not assume the cause is network latency; verify it against the data patterns.
1.  **Cluster Analysis:** Group the 1,200 weekly erroneous transactions by region, payment method, device type, and browser. If duplicates correlate strongly with specific regions experiencing high latency or specific payment gateways with slow callbacks, the "double-click" hypothesis gains weight. If they are evenly distributed, the issue likely lies in backend retry logic or webhook duplication.
2.  **Timestamp Delta Inspection:** Analyze the time difference between duplicate event IDs.
    *   *Sub-second deltas:* Strongly indicate UI double-clicks.
    *   *Seconds-to-minutes deltas:* Suggest network timeouts triggering client-side retries or idempotency key failures.
    *   *Irregular deltas:* Point to backend job retries or data pipeline re-processing errors.
3.  **Session Correlation:** Check if duplicates share the same session ID and user ID. True double-clicks will share both; pipeline errors might not.

#### Phase 2: Historical Data Cleansing (Days 4–10)
Execute cleaning in a isolated staging environment to protect real-time reporting.
1.  **Define Deduplication Rules:** Based on Phase 1 findings, establish a deterministic rule set. For example: "For identical Order ID, User ID, and Amount, keep the event with the earliest timestamp and flag others as 'duplicate'."
2.  **Backfill Scripting:** Write an idempotent script to apply these rules to historical data from the start of the fiscal year. Do not delete records; instead, add a `is_corrected` boolean flag and a `correction_reason` column to maintain an audit trail.
3.  **Parallel Run:** Run the cleaning script on a copy of the production database. Compare the aggregated revenue output of the clean dataset against the raw dataset to confirm the ~8% reduction aligns with expectations across all twelve countries.

#### Phase 3: Validation & Financial Reconciliation (Days 11–14)
Before presenting to the CFO, the cleaned data must be reconciled with external sources.
1.  **Gateway Reconciliation:** Compare the cleaned internal transaction count and total value against settlement reports from your payment processors (e.g., Stripe, Adyen, PayPal). The internal "clean" figures must match the actual money settled in your bank accounts. This is the ultimate source of truth.
2.  **Sample Audit:** Manually inspect 50 random "removed" duplicate transactions. Verify that the kept transaction exists in the shipping logistics system and the payment gateway, while the removed one does not have a corresponding second shipment or charge.
3.  **Variance Reporting:** Generate a bridge report showing: *Reported Revenue* minus *Identified Duplicates* equals *Corrected Revenue*. Break this down by region to ensure no specific market is disproportionately affected, which could indicate localized fraud rather than technical error.

#### Phase 4: Prevention & Real-Time Fix (Days 15–20)
1.  **Idempotency Enforcement:** Ensure the purchase API requires a unique idempotency key (generated by the client per transaction attempt) that the server checks before processing. This prevents duplicate processing regardless of network clicks.
2.  **UI Debouncing:** Implement a frontend lock on the 'buy' button immediately after the first click, disabling it until a response is received.
3.  **Monitoring Alert:** Set up an alert for any future occurrence of duplicate Order IDs within a 5-minute window to catch regressions immediately.

**Timeline Summary:**
*   **Diagnosis Complete:** Oct 4
*   **Clean Dataset Ready for Audit:** Oct 15
*   **Final Validation & CFO Review:** Oct 20
*   **Buffer for Q&A/Adjustments:** Oct 21 – Nov 4

This plan ensures the November 5th figures are backed by reconciled bank settlements, not just database logic.

*Note: Do not apply cleaning scripts directly to the production database; always use a shadow table or flagging system to allow for instant rollback if reconciliation discrepancies arise.*
