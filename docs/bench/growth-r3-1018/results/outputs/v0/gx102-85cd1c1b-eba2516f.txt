### Strategy for Timestamp Integrity and Reporting

**1. Identification Rules (Flagging Logic)**
Do not delete records yet. Create a new boolean column `is_timestamp_suspicious` and apply these three rules to flag rows:
*   **Future Check:** Flag if `event_timestamp` > `current_processing_time` + 5 minutes (allowing for minor clock skew).
*   **Midnight Anomaly:** Flag if `event_timestamp` equals `00:00:00` UTC exactly. This is a classic default value error when a timezone conversion fails or a null is cast incorrectly.
*   **Logical Duration:** Flag if `delivery_complete_timestamp` < `delivery_start_timestamp`.

**2. Cleaning & Segmentation Logic**
Once flagged, segment the data rather than blindly deleting:
*   **The "Midnight" Cluster:** Isolate all records hitting exactly `00:00:00` UTC. If these cluster heavily in the southern districts post-March 3rd, this confirms a regional migration mapping error. These records likely have valid dates but lost time precision; they may need to be excluded from *average time* calculations but kept for *volume* counts.
*   **The "Future" Cluster:** These are physically impossible. Exclude them entirely from time-based metrics.
*   **Valid Data Set:** Create a view `cleaned_delivery_metrics` that excludes flagged rows *only* for the calculation of "Average Delivery Time." Keep the full dataset for record-keeping.
