### Strategy for Timestamp Integrity and Reporting

**1. Flagging Logic (Suspicious Entry Rules)**
Apply the following filters to your 200,000 daily records to isolate the ~15% inconsistent data without deletion. Mark these rows with a `data_quality_flag` rather than removing them.

*   **Future Timestamp Rule:** Flag any event where `event_timestamp` > `current_processing_time` + 15 minutes (allowing for minor network latency). True future dates are impossible and indicate clock skew or timezone misconfiguration.
*   **Midnight UTC Artifact Rule:** Flag any event where `event_timestamp` equals `00:00:00` UTC exactly. This pattern strongly suggests a default value assignment during the March 3rd migration when a valid timestamp was missing or failed to convert from the legacy system.
*   **Timezone Mismatch Rule:** Since operations are in Chile (CLT/CLST), flag records where the local hour component is inconsistent with typical delivery windows (e.g., if converted local time shows deliveries occurring strictly at midnight local time, matching the UTC artifact).

**2. Cleaning and Correction Approach**
Do not delete flagged records immediately. Instead, create a "cleaned_for_analysis" view:
*   **Exclude from Aggregation:** Remove flagged records from the calculation of "Average Delivery Time" for the director's report.
*   **Segmented Analysis:** Run the average delivery time calculation twice: once including all data (to show the distortion) and once excluding flagged data (the reliable metric).
*   **Regional Segmentation:** To answer your hypothesis about southern districts, group the *flagged* records by region. If the percentage of flagged records in the south significantly exceeds the global 15% average, the issue is regional; if it matches, the issue is systemic to the March 3rd migration configuration.
