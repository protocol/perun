### Recommended Action Plan

**1. Treat this as a "Major Infrastructure Change" requiring prior consensus.**
Adding a new platform target (Windows ARM) to a dormant CI pipeline is not a trivial fix; it alters build times, resource usage, and release artifacts. Given the project has no active CI maintainer and hasn't been updated in a year, submitting a Pull Request (PR) immediately carries a high risk of being ignored or rejected for breaking the existing fragile workflow. You must establish contact before coding.

**2. Open a "Request for Comments" (RFC) Issue first.**
Do not open a PR yet. Instead, open a new Issue titled: `RFC: Proposal to add Windows ARM64 CI build job`.
In the issue body, include:
*   **The Business Case:** Explicitly mention Stark Industries' reliance on this for mobile deployments. Real-world usage cases are the strongest motivator for dormant maintainers to re-engage.
*   **The Technical Scope:** Detail that you intend to add a single job to the existing configuration based on provider documentation.
*   **The Ask:** "Does the core team approve of adding this target? Are there known incompatibilities with Windows ARM in the current codebase?"
*   **The Offer:** State clearly that you are willing to maintain this job or troubleshoot initial failures.

**3. Provide pre-compiled artifacts *before* asking for the CI merge.**
Yes, you should provide verification binaries. Since the maintainers are inactive, they cannot easily verify your claim that the code compiles on Windows ARM.
*   Build the library locally (or in a private fork) for Windows ARM.
*   Attach the static/dynamic libraries and a simple test executable to the RFC Issue.
*   Include a short "Verification Report" in the issue showing successful compilation and basic execution logs.
This reduces the maintainer's cognitive load from "I need to set up a cross-compiler to check this" to "I can download and run this attached file." It proves feasibility without forcing them to trust a configuration change blindly.

**4. Gauge interest via a time-bound soft deadline.**
In your RFC issue, add a polite note: "If there are no objections or alternative suggestions within 14 days, I will proceed with submitting a PR implementing this job." This respects the maintainers' authority while preventing the request from entering "issue limbo" indefinitely.

**5. Prepare for the "Bus Factor" scenario.**
If no one responds after 2–3 weeks:
*   Submit the PR anyway, linking it to your RFC issue.
*   Ensure the PR includes a "fail-safe": configure the new Windows ARM job as `allow_failure: true` (or equivalent) in the CI config initially. This ensures that if your new job breaks due to environment quirks, it does not block the existing build pipeline for other users. This significantly increases the likelihood of a merge because it removes the risk of breaking the project for everyone else.

2.  **Verification Package:** Pre-compiled Windows ARM binaries + build logs attached to the issue.
