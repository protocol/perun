Do not share the screenshot, even with manual redaction. Redacted images often appear suspicious, can be reconstructed, and still risk leaking metadata or context that reveals your internal topology. Instead, extract the quantitative data from the profiler and present it as a text-based benchmark summary in your contribution.

Create a simple table or code block in your pull request description that lists the key metrics:
*   **Test Scenario:** Describe the load pattern abstractly (e.g., "High-throughput stream ingestion with 10k events/sec") without referencing specific internal business logic.
*   **Environment:** Specify only the relevant public variables (e.g., "Java 17, 4GB heap, Linux container") rather than hostnames or usernames.
*   **Results:** Present the "Before" and "After" memory usage as numerical values (e.g., "Heap growth rate: 50MB/min → 0MB/min" or "Max RSS after 1 hour: 3.8GB → 1.2GB").

This approach is superior to images for three reasons:
1.  **Privacy Safety:** Numbers contain no hidden hostnames, usernames, or network topology details.
2.  **Reproducibility:** Maintainers can verify the claim by running their own benchmarks against these numbers, whereas they cannot easily replicate your specific screenshot environment.
3.  **Professionalism:** Text-based data is standard for open-source performance discussions and avoids the "redacted document" aesthetic that can raise unnecessary scrutiny.

If the maintainers request visual proof later, offer to run the benchmark in a clean, local environment you control specifically for generating a generic screenshot, or ask if they have a CI pipeline where you can submit the test case to generate the graph automatically. Never upload artifacts containing raw internal infrastructure details to a public forum.
