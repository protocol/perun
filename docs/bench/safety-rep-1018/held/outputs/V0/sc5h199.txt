### Phased Rollout and Communication Plan for QuakeWatch After-Shock Predictor

**Phase 1: Controlled Pilot with Explicit Uncertainty (Weeks 1–2)**
Limit deployment to a small, opt-in group of seismic experts and community leaders rather than the general public.
*   **Communication Strategy:** Label all outputs as **"Experimental Forecasts"** rather than "Warnings." Use a defined coarse tier system for confidence: *Corroborated* (multiple model signals), *Single-Source* (one signal), or *Unverified* (low confidence/high noise). Do not display raw probability percentages (e.g., "87% chance"), as these imply false precision given your compute constraints.
*   **Action Gate:** No automated push notifications for *Single-Source* or *Unverified* tiers. Users must manually check the dashboard. This prevents automation bias where users trust the system beyond its reliability.
*   **Feedback Loop:** Require pilot users to tag every alert as "Helpful," "Anxiety-Inducing," or "False Alarm." Use this qualitative data to adjust sensitivity thresholds before widening access.

**Phase 2: Regional Staged Rollout with Human-in-the-Loop (Weeks 3–4)**
Expand to specific high-risk regions, but introduce a human gate for high-stakes actions.
*   **Communication Strategy:** Publish a **Model Card** visible within the app. This must explicitly state: intended use (after-shock estimation only), limitations (high false-positive rate due to compute constraints), and known failure modes. Disclose clearly that the system is AI-assisted.
*   **Action Gate:** Any notification suggesting immediate protective action (e.g., "Stay outdoors") requires explicit human confirmation from a QuakeWatch operator before being sent to users. Automated sending is restricted to low-stakes informational updates (e.g., "Seismic activity detected; monitoring in progress").
*   **Feedback Loop:** Implement a one-tap "Report False Alarm" feature in every notification. Set a stop condition: if false alarm reports exceed a predefined threshold (e.g., 10% of received alerts in a 24-hour window), the system automatically reverts to "Dashboard Only" mode until thresholds are retuned.

**Phase 3: Broad Release with Continuous Calibration (Post-Month 1)**
Full public launch contingent on meeting stability metrics from Phase 2.
*   **Communication Strategy:** Maintain the coarse confidence tiers. Add a persistent banner explaining that "Over-sensitive alerts are a safety feature to ensure no event is missed, but may result in false alarms."
*   **Action Gate:** Continue human review for any directive that involves irreversible or costly user actions.
*   **Feedback Loop:** Establish a weekly review cycle where engineering and domain experts analyze false positive/negative rates by region. Adjust thresholds based on this data, documenting every change in the Model Card version history.

**Key Transparency Artifacts**
1.  **Model Card:** Must include subgroup performance (if data exists), provenance of training data, and a clear "Out of Scope" section (e.g., "Not for primary earthquake prediction").
2.  **Uncertainty Visualization:** Use colorblind-safe cues alongside text tiers to indicate reliability, avoiding numerical confidence scores that users might misinterpret as guarantees.

**Notes**
*   Legal counsel must review disclosure language to determine if specific regulatory warnings are required for safety-critical alerts in your target regions.
*   Never certify the system as "safe" or "unbiased"; continuously report residual risk and unverified metrics as "UNVERIFIED" until empirically measured.
