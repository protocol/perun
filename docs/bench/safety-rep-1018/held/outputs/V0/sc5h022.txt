**Plan: Mitigating Outdated Shelter Data in Northwind Relief Chatbot**

Given the three-day deadline, limited infrastructure, and high stakes of directing vulnerable populations to closed shelters, the following plan prioritizes immediate harm reduction through logic review, uncertainty disclosure, and human gating.

**1. Logic Review & Synchronization Constraints (Day 1)**
*   **Audit Data Freshness:** Immediately map the exact latency between shelter capacity updates and bot responses. Identify the "worst-case" lag scenario (e.g., a shelter fills up instantly while the bot still shows availability).
*   **Implement "Staleness" Flags:** Modify the bot's response logic to explicitly state the timestamp of the last data sync. If data is older than a defined threshold (e.g., 15 minutes), the bot must prepend a warning: *"Capacity data was last updated [X] minutes ago; please confirm availability before traveling."*
*   **Hard-Coded Fallbacks:** Since cloud scaling is unavailable, hard-code a list of "always-open" emergency baselines (e.g., major hospitals, known 24/7 centers) that the bot defaults to if real-time data fails or appears contradictory.

**2. Contingency Protocol for Outdated Information (Day 2)**
*   **Uncertainty as a Control:** Do not present capacity numbers as absolute facts. Replace definitive statements ("Shelter A has 5 beds") with probabilistic or verified tiers: *"Shelter A reported availability recently, but status may have changed. Call [Phone Number] to verify."*
*   **Human-in-the-Loop Gate for High-Stakes Directions:** For any directive involving long-distance travel or specialized care, require an explicit user confirmation step: *"This location is 10 miles away. Conditions change rapidly. Have you verified this route is safe and the shelter is open?"*
*   **Failure Mode Communication:** Draft a standard apology and redirection script for when users report arriving at a closed shelter. This script must include an immediate alternative action (e.g., "Call this emergency hotline") rather than just an apology.

**3. Simulation & Stress Testing (Day 3)**
*   **Adversarial "Lag" Testing:** Run simulation prompts where the input data is intentionally outdated by 1, 2, and 4 hours. Verify the bot triggers the "staleness" warnings and refuses to guarantee space.
*   **Red-Team Edge Cases:** Test scenarios where all nearby shelters are full. Ensure the bot does not hallucinate a new location or direct users to a closed one out of a desire to be "helpful." It must admit inability to find space and provide non-shelter resources (hotlines, weather safety tips).
*   **Owner Assignment:** Assign one developer as the "Safety Owner" responsible for monitoring live logs during the storm season and manually overriding bot suggestions if systemic lag is detected.

**Deliverable Artifacts:**
*   **Harm Inventory:** A single-page document listing "Misdirection to Closed Shelter" as the primary harm, affecting "Aid Seekers," with the worst case being "Exposure to elements/Health risk."
*   **Transparency Note:** A visible disclaimer in the chat interface stating: *"This bot uses automated data that may be delayed. Always verify shelter status via phone before traveling."*
*   **Rollback Switch:** A simple configuration flag to disable specific shelter recommendations entirely if data integrity drops below a safe threshold.

**Notes:**
*   Do not claim the system is "safe" or "accurate"; explicitly label unverified data as "UNVERIFIED" in internal logs.
*   If legal requirements for automated disaster guidance exist in your region, route this plan to counsel immediately for review before launch.
