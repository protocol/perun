### Verification Workflow: Manual Form Library Cross-Check

**Objective:** Prevent application rejections caused by outdated form versions without real-time database access.

**1. Source of Truth Identification**
*   Assign one developer as the "Source Owner" for each specific visa category (e.g., Work, Family, Student).
*   The Source Owner must identify the single official URL for each form on the relevant government website (e.g., USCIS, IRCC, Home Office). Bookmark these URLs in a shared, version-controlled document (e.g., `OFFICIAL_SOURCES.md`). Do not rely on search engines; go directly to the known domain.

**2. The "Three-Point" Manual Audit (Weekly or Pre-Release)**
Before any content release, the team executes this manual check for every active form:
*   **Point A (Version Number):** Compare the form edition date/version number on your local file against the official source.
*   **Point B (Barcode/QR Check):** If the government form uses a 2D barcode or QR code that encodes the version, visually verify the code format matches the official sample.
*   **Point C (Instruction Page):** Scan the first page of instructions for "Revision Date" alerts. Government forms often update instructions before the form itself; mismatched pairs cause rejections.

**3. The "Human Gate" Release Protocol**
*   No form update is merged to production unless a second developer (not the author) performs a "blind check": they look at the official site first, write down the version number, and then compare it to the proposed update.
*   If the official site is unreachable during the check, the release for that specific form is **blocked**. Do not guess.

**4. Documentation Artifact**
*   Create a `FORM_AUDIT_LOG.csv` containing: Form ID, Official URL, Date Checked, Official Version, Local Version, Checker Name, and Status (MATCH/MISMATCH/BLOCKED). This serves as your transparency record.

### Contingency Plan: Unexpected Form Changes

**Scenario:** A user starts an application with Form V1, but the government releases V2 before the user submits.

**1. Immediate "Stop-Work" Banner**
*   Implement a hard-coded logic check on the form landing page. If the internal database flags a form as "UNDER_REVIEW" or "SUPERSEDED," display a high-contrast warning banner: *"Alert: The government has updated this form as of [Date]. Continuing with the old version may result in rejection. Please restart your application."*
*   This banner must appear before the user enters any new data.

**2. In-Progress User Notification**
*   **Email/SMS Trigger:** If a user has saved a draft associated with a now-outdated form ID, trigger an immediate notification template: *"Important Update: The [Form Name] you are using has been replaced. Your current draft cannot be submitted. Click here to migrate your data to the new version."*
*   **Data Migration Strategy:** Since you cannot auto-update the PDF structure safely without validation, advise users to export their text answers (if your system allows) and re-enter them into the new official PDF. Do not attempt to auto-fill the new form with old data structures unless you have verified field-mapping compatibility.

**3. The "Uncertainty" Disclosure**
*   Add a permanent footer to every generated PDF: *"Generated by GlobalMove Assist on [Date]. Users are responsible for verifying the form version against [Official Government URL] prior to submission."*
*   This manages the risk of "hallucination as fact" by explicitly stating the tool's limitation regarding real-time government changes.

**4. Escalation Path**
*   If a major form overhaul occurs (e.g., structural layout change), pause the feature entirely for that visa category until the manual audit is complete. It is safer to disable a feature than to facilitate mass rejections.

**Note:** This workflow relies on human verification; never assert a form is "100% current" without the latest manual check. Legal requirements for automated decision disclosures vary by jurisdiction; consult counsel to determine if specific regulatory notices are mandatory for your region.
