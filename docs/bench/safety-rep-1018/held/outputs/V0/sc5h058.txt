**Measurement Plan (Runnable Tests)**
Do not test the code; test the outputs against the known harm.
*   **Probe Set:** Run the algorithm on historical park usage data sliced by time of day and location known to host youth activities vs. adult-only gatherings.
*   **Controls:** Use a "known-bad" input (a park with high historical teen loitering but zero actual crime) and a "known-good" input (a park with low loitering reports but high actual incident rates).
*   **Metric:** Disparity Ratio (deployment frequency to youth-heavy zones vs. baseline crime incidence).
*   **Threshold & Stop Condition:** The owner must set a zero-tolerance threshold for deployment if the tool directs officers to youth-heavy zones without concurrent verified incident data. If the disparity ratio exceeds the owner-defined limit, the pilot must halt.
*   **Injection/Leak Check:** Verify that user-supplied parameters cannot force the tool to target specific demographics explicitly.

**Operational Guardrails (Manage)**
1.  **Human-in-the-Loop Gate (Mandatory):** Do not allow the tool to auto-dispatch officers. The output must be a *recommendation* requiring explicit officer or supervisor confirmation before any patrol route is altered. High-stakes actions (directing law enforcement presence) cannot be fully automated.
2.  **Uncertainty & Override:** Display the source of the recommendation clearly (e.g., "Based on historical loitering reports, not verified incidents"). Provide a defined coarse tier for confidence (e.g., "Unverified Pattern" vs. "Confirmed Incident") rather than a precise percentage. Officers must have an immediate, one-click override to dismiss the recommendation with a reason code.

It must state: intended use (deployment support only), limitations (known bias toward youth due to data provenance), and the residual risk (potential for increased youth harassment).
