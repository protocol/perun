# FreshCart Substitution Audit Plan

Given the two-week timeline and fixed budget, this plan focuses on a deterministic, manual audit of your existing rule set without requiring new data or model training. The goal is to identify logic gaps where dietary constraints are overridden by generic availability rules.

### Phase 1: Rule Inventory & Mapping (Days 1–3)
Extract all active substitution rules into a single spreadsheet. Create columns for:
1.  **Trigger Item:** The out-of-stock product.
2.  **Candidate Replacements:** The list of potential swaps defined in the logic.
3.  **Dietary Tags:** Explicit labels attached to both trigger and candidates (e.g., "Gluten-Free," "Low-Sodium," "Vegan," "Diabetic-Safe").
4.  **Priority Logic:** The current decision hierarchy (e.g., "Match Brand" > "Match Price" > "Match Dietary Tag").

*Action:* Flag any rule where the "Priority Logic" allows a non-matching dietary tag to be selected if the primary match is out of stock. This is the highest risk area.

### Phase 2: The "Negative Constraint" Matrix (Days 4–7)
Do not test for "good" matches; test specifically for forbidden outcomes. Construct a matrix of high-risk dietary profiles against your top 50 most frequently substituted items.
*   **Test Case A (Allergen Swap):** Input a gluten-free trigger with no gluten-free candidates available. Verify if the system defaults to a wheat-based product or returns "Out of Stock." The latter is the only safe failure mode.
*   **Test Case B (Medical Condition):** Input a low-sodium trigger for a hypertensive user profile. Check if high-sodium alternatives are suggested due to price or brand matching.
*   **Test Case C (Lifestyle/Religious):** Input vegan or halal triggers. Ensure no animal-derived substitutes are offered even if they are the closest nutritional match.

*Action:* Manually execute these scenarios against the rule engine. Record any instance where a "forbidden" attribute bypasses the dietary filter.

### Phase 3: Edge Case Stress Testing (Days 8–10)
Focus on complex, multi-restriction households which often break simple logic trees.
*   **Compound Restrictions:** Test users with overlapping needs (e.g., "Gluten-Free" AND "Low-Sugar"). Many rules handle single constraints but fail when two filters reduce the candidate pool to zero.
*   **Ambiguous Tagging:** Review items with vague labels (e.g., "Natural" or "Healthy") that might incorrectly satisfy a strict dietary filter. Ensure only binary, verified tags drive substitution logic.
*   **Nutritional Thresholds:** If your rules use numerical thresholds (e.g., "<5g sugar"), manually calculate the boundary conditions. Verify that an item with 5.1g sugar is rejected, not accepted due to rounding or data type errors.

### Phase 4: Remediation & Fail-Safe Implementation (Days 11–14)
For every failure identified:
1.  **Hard Block:** Update the logic to treat dietary mismatches as absolute disqualifiers, not just lower-priority scores.
2.  **No-Substitute Default:** Configure the system to return "Item Unavailable" rather than suggesting an unsafe alternative when no compliant match exists.
3.  **Human-in-the-Loop Flag:** If possible, flag substitutions involving critical medical diets (e.g., renal or severe allergy) for manual review before order confirmation, even if this slows processing slightly for those specific cases.

**Deliverable:** A finalized "Go/No-Go" report listing every tested rule, the specific failure modes found, and the confirmed status of the fix.

**Note:** Prioritize safety over completion rate; it is better to cancel an order than to deliver an unsafe product. Ensure your "Out of Stock" messaging clearly explains that no safe substitute was found to maintain user trust.
