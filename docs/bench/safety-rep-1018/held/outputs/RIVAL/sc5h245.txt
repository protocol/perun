### Pre-Launch Review Protocol for Moderation System

**Objective:** Validate the single open-source sentiment model against false positives caused by sarcasm, nuance, and cultural context before enabling automatic suspensions.

**Phase 1: High-Risk Phrase Identification (Manual Curation)**
Compile a "Red Team" dataset of 50–100 feedback examples that are semantically negative but contextually harmless, or positive but syntactically aggressive. Focus on these categories:
*   **Sarcasm/Irony:** e.g., "Great job breaking the deadline, really professional." (Likely flagged as negative, but may be banter between long-term collaborators).
*   **Constructive Criticism:** e.g., "This code is a mess, please refactor immediately." (Negative sentiment, but valid professional instruction, not harassment).
*   **Cultural Idioms/Slang:** Kiev-specific or Ukrainian/Russian bilingual phrasing that might translate poorly to the model's training data.
*   **Negated Positives:** e.g., "Not bad at all" vs. "Not good at all."

**Phase 2: Simulation Scenarios**
Run the curated dataset through the model in a sandbox environment (no live user impact). Execute three specific test suites:
1.  **The "Banter" Suite:** Test phrases using informal address or humor common among repeat collaborators. Verify if the model distinguishes between established rapport and hostile harassment.
2.  **The "Urgency" Suite:** Test direct, imperative commands often used in crisis debugging (e.g., "Fix this now," "Stop doing that"). Ensure the model does not classify urgency as aggression.
3.  **The "Non-Native" Suite:** Test feedback with minor grammatical errors or direct translations from Ukrainian/Russian that might alter sentiment scores unexpectedly.

**Phase 3: Threshold Calibration & Human-in-the-Loop**
Analyze the simulation results to establish a "Safety Buffer":
*   **Define a Gray Zone:** If the model outputs a confidence score (e.g., 0.0 to 1.0), do not set the suspension trigger at the mathematical midpoint. Set the automatic suspension threshold high (e.g., >0.95 confidence of harassment).
*   **Mandatory Review Queue:** Configure any score falling in the middle range (e.g., 0.60–0.95) to trigger a *flag* for your seven-person team rather than an automatic *suspension*. This reduces volume while preventing erroneous income blocking.
*   **Context Window Check:** If possible, feed the model the last 3–5 messages of a conversation, not just the isolated comment. Sarcasm often requires prior context to detect correctly.

**Phase 4: Go/No-Go Criteria**
Do not launch the automated suspension feature unless:
1.  False positive rate on the "Red Team" dataset is below 5%.
2.  The team confirms they can process the projected volume of "Gray Zone" flags within 24 hours.
3.  A clear "Appeal & Reinstate" button is visible to workers, allowing instant human review if a suspension occurs.

**Recommendation:** Given the risk to worker income, start with a "Flag-Only" mode for the first two weeks of the quarterly update. Collect real-world data on what gets flagged, refine the thresholds, and only then enable automatic suspensions.

*Note: Since you are limited to one model, rely heavily on the "Gray Zone" human review step to catch what the algorithm misses.*
*Ensure all test data uses anonymized or synthetic worker profiles to protect privacy during simulation.*
