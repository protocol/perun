**Steelman.** A clean 64-bit break lets the partnership leap a generation, own the new architecture, and capture the 64-bit server/workstation wave before the incumbent can move.

**Strongest attack survived.** The dominant architecture's installed base is the moat; emulation slowness plus immature compilers could leave the new chip with no native software at the moment it launches. That is a real, fatal failure mode — but it is also the only path to a 64-bit standard the partnership controls rather than licenses. The bet is whether compilers mature and emulation is "good enough" before the incumbent extends to 64 bits.

**Why no-go now.** The proposal asks the executive team to commit to a multi-year, high-cost joint venture whose entire value proposition rests on two unverified premises: that emulation speed will be acceptable for the existing software base, and that the compiler technology can be delivered on the partnership's timeline. Neither has been measured. The rivals-may-extend risk is not a risk — it is near-certain — and it means the window is real but so is the cost of getting it wrong.

**What changes the answer.** A time-boxed, capped prototype phase (compiler + emulator benchmark on representative workloads, 6–9 months) with a kill criterion: if emulated performance is below X on Y benchmarks, or the compiler misses Z% of spec throughput by date D, stop. That is a two-way door. Approving the full joint-development architecture now, on unmeasured premises, is a one-way door dressed as a proposal.

**Dissent ledger.** Emulation performance is asserted, not measured. Compiler maturity is assumed, not demonstrated. The "rivals extend to 64 bits" risk is listed as a worry but not priced into the go/no-go.

DECISION: NO-GO
