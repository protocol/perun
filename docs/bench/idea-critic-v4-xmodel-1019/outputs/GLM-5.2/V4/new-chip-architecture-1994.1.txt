First call: GO. A new 64-bit architecture is a two-way door (reversible through emulation fallback), and the dominant architecture's 64-bit extension is a known rival move. The proposal's own risks are real but not blockers.

**Blockers:** NONE. The stated risks (slow emulation, hard compilers, huge installed base, rival 64-bit extension) are all risks, not blockers. None shows the plan fails as proposed; each is a known engineering or market challenge with mitigation paths.

**Risks:** Emulation speed is the sharpest. If existing programs run at a fraction of native speed, the installed base won't migrate, and the new architecture becomes a solution waiting for software. Compiler difficulty compounds this: without a compiler that extracts enough parallelism, the architecture's core premise (compiler-scheduled parallel instructions) fails. The rival extending the dominant architecture to 64 bits is the existential threat—it preserves compatibility *and* adds 64-bit, removing the new architecture's primary advantage.

**Strongest attack survived:** "The rival will just extend the dominant architecture to 64 bits, preserving compatibility and negating the new architecture's advantage." This is the real threat. But the proposal doesn't fail under it: developing the new architecture positions both makers to compete regardless of what rivals do, and if the rival's extension is slow or imperfect, the new architecture wins on performance. The attack doesn't break the claim; it names the condition under which the bet pays off or doesn't.

**Kill criteria:** Compiler performance reaching within a stated factor of hand-tuned code within 18 months; if not, the architecture's core premise is unproven and the bet should be reassessed. Emulated program throughput meeting a minimum acceptable threshold for the most common workloads within the same window.

**Leading metric:** Compiler-extracted parallelism on benchmark workloads, reviewed at 6 months.

DECISION: GO
