Do not open a pull request to the main repository with this change in its current form. Submitting code that depends on a private, non-redistributable SDK without prior maintainer approval will almost certainly result in the PR being closed immediately, as it breaks the build for all other contributors and violates the principle of reproducible builds.

Instead, follow this specific contribution path:

1.  **Open a Feature Request Issue First:** Before writing any upstream code, open a detailed issue titled "Proposal: Support for [Console Name] via optional SDK." Explicitly state that you have a working local implementation but cannot share the binaries due to NDA. Ask the maintainers if they are willing to accept an *optional* build path guarded by flags.
2.  **Propose an Abstraction Layer, Not Implementation:** If maintainers express interest, do not commit the direct SDK integration. Instead, propose adding empty stub functions or a new abstract interface in the engine's platform layer (e.g., `PlatformConsole.cpp`) that returns "not implemented" by default. Your PR should only contain the interface definitions and the build system hooks (CMake/Meson flags) that allow users to *optionally* define a macro (e.g., `ENABLE_CONSOLE_SDK`) to link their own private libraries.
3.  **Host the Integration Externally:** Maintain the actual implementation (the code that includes the private headers and links the SDK) in a private fork or a separate patch file hosted by your studio. Your upstream PR should only provide the "hooks" necessary for that private patch to apply cleanly. Document in the PR description exactly where external users can obtain the SDK legally and how to apply your private patch on top of the main branch.
4.  **Ensure Zero Impact on Default Builds:** Verify rigorously that when the optional flag is not set, the build process remains identical to the current state. No new dependencies, no new warnings, and no changed behavior for existing platforms. If your change requires modifying shared core files, refactor them to use dependency injection or virtual dispatch rather than `#ifdef` sprawl, ensuring the proprietary logic is completely isolated.

This approach respects the open-source nature of the project while providing a legal pathway for other licensees to reproduce your work without violating NDAs or breaking the CI for the general community.

Note: If the maintainers indicate that they do not support proprietary toolchains at all, respect that decision and maintain your port entirely within your studio's private fork.
