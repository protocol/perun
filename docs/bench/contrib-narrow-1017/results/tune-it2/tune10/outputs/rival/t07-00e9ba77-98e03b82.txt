### Responsible Disclosure Strategy for Missing Security Policy

Since no private channel exists, your goal is to alert maintainers without publishing an exploit. Follow this sequence:

**1. Attempt Indirect Contact (24–48 hours)**
Before posting anything public, try to find a maintainer outside the repo:
*   Check the `gemspec` file or RubyGems page for an author email.
*   Look for a "Security" or "Contact" page on the project's documentation site.
*   Search for the primary maintainer on Twitter/LinkedIn and send a brief DM: *"Hi, I found a potential path traversal vulnerability in [Project]. There is no security policy listed. Where should I send details?"*

**2. Post a "Sanitized" Public Issue**
If indirect contact fails, open a public issue but **strictly omit** the exploit recipe. Use this template:

> **Title:** [Security] Potential path traversal vulnerability reported
>
> **Body:**
> I have identified a potential path traversal vulnerability that may allow reading files outside the source directory via specially crafted filenames.
>
> I have verified this locally but have **not** included reproduction steps or proof-of-concept code in this issue to prevent immediate exploitation by bad actors.
>
> **Impact:** High (Arbitrary file read).
> **Affected Component:** Static file rendering / path resolution logic.
>
> Maintainers: Please contact me at [Your Email] or via a private channel to discuss a coordinated disclosure timeline. I am happy to share full details once a secure communication line is established.

**3. Manage the Conversation**
*   **If maintainers respond:** Move the discussion to email or a private GitHub security advisory (if they enable one) immediately. Share your PoC only after confirming their identity.
*   **If no response after 7 days:** Post a follow-up comment noting the lack of response. If still silent after 14–30 days, you may need to consider full disclosure or contacting the platform hosting the project (e.g., GitHub Support) for assistance, though this is a last resort.

**Key Principle:** Never publish the specific filename pattern or directory structure that triggers the bug until a patch is available. Your leverage is the *existence* of the bug, not the public details of it.

*Note: Since the project is Ruby-based, check if it is hosted on RubyGems; you can sometimes report security issues directly to RubyGems support if the maintainer is unresponsive.*
*Note: Keep your local PoC ready but private; you will need it to verify the fix once the maintainer engages.*
