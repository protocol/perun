### Recommended PR Strategy

**Do not** mention AI assistance in your commit messages. Commit history should reflect logical changes and authorship, not the tools used to draft them. Since the project has no explicit policy against AI and you have manually verified every line, the code is effectively yours.

However, given your concern about ethics and potential future discovery, **include a brief, confident disclosure at the very bottom of your PR description**, not as an apology, but as a statement of process. This preempts accusations of hiding tools while emphasizing your rigorous validation.

#### 1. Commit Message Strategy
Keep commits clean and focused on the *what* and *why*. Use the Conventional Commits format.
*   **Bad:** `fix(date): use AI to correct timezone offset logic`
*   **Good:** `fix(date): correct timezone offset calculation during DST transitions`

#### 2. PR Description Structure
Use this template. It highlights the technical value first, making the AI disclosure a minor footnote rather than the headline.

```markdown
## Summary
Fixes incorrect timezone offsets during daylight saving time (DST) transitions. This resolves a critical issue affecting users in regions currently observing DST.

## Changes
- Updated `src/date-utils.js` to handle edge cases in `getOffset()` where standard library calls return ambiguous times.
- Added three new test cases covering: (1) spring-forward transition, (2) fall-back transition, and (3) boundary conditions at exact switch-over seconds.

## Verification
- All existing tests pass.
- New tests specifically target the reported bug scenario.
- Manually verified output against known timezone database (IANA) expectations for 2024-2025 transitions.

## Related Issue
Fixes #[IssueNumber] (or "Resolves reported production error regarding DST")

---
*Transparency Note: The initial draft of this logic was generated with AI assistance to accelerate pattern matching on complex timezone edge cases. I have personally reviewed, refactored, and validated every line of code and test case included here to ensure correctness and adherence to project standards.*
```

### Why This Approach Works

1.  **Prioritizes Value:** Maintainers care first about whether the bug is fixed and tests pass. By putting the technical proof upfront, you establish competence before mentioning tools.
2.  **Reframes the Narrative:** Instead of "I used AI" (which can sound like "I didn't do the work"), you say "I used AI to accelerate drafting, but I own the verification." This aligns with the ethical standard of "human-in-the-loop."
3.  **Mitigates Risk:** If the project later adopts a strict anti-AI stance, you have already disclosed. If they don't care, the note is easily ignored because it's at the bottom. Hiding it risks a "trust collapse" if they ever suspect AI usage; transparency protects your reputation long-term.
4.  **Commit Hygiene:** Keeping AI out of commit messages prevents cluttering the `git blame` history with irrelevant metadata, which is standard professional practice.

**Final Advice:** Since the fix is solid and tested, your confidence in the *result* matters more than the *origin* of the draft. Present the PR as a solution to a critical bug, with the AI note as a mere formality of your personal workflow.
