**Strategy for Inferring Format**
To match the project culture without direct documentation:
1.  **Scan the last 10–20 merged PRs.** Look specifically for entries involving performance or architectural changes. Do they start with a verb (e.g., "Added," "Improved") or a noun phrase? Do they include issue numbers?
2.  **Identify the "Goldilocks" entry.** Find an entry that is neither the shortest one-liner nor the longest essay. Aim for that middle ground, which usually balances context with brevity.
3.  **Prioritize User Impact.** Unless the project is strictly internal tooling, maintainers usually prefer knowing *what* changed for the user (30% faster queries) over *how* it was coded, unless the implementation detail explains a breaking change or new configuration requirement.

**Draft Release Note Entry**
You can propose the following entry. It focuses on the measurable outcome while briefly acknowledging the structural change, which is a safe default for high-impact updates:

> **Improved query performance under high load by approximately 30% through the introduction of a new distributed caching layer.** This change reduces latency spikes during peak traffic without requiring configuration changes from users.

**Why this works:**
*   **Headline-first:** It leads with the benefit (30% improvement), which is what most readers care about.
*   **Context:** It mentions the "caching layer" so developers understand the scope of the change.
*   **User Assurance:** It explicitly states no configuration changes are needed, preempting a common follow-up question.
