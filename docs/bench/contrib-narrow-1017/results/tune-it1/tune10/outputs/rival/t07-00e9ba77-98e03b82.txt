### Responsible Disclosure Strategy for Missing Security Policy

Since the project lacks a dedicated security policy or private channel, you must create a temporary private channel through the public tracker while strictly withholding exploit details. Follow this sequence:

**1. Prepare a Sanitized Proof of Concept (PoC)**
Create a minimal reproduction case that proves the *existence* of the bug without providing a copy-paste exploit for real-world targets.
*   **Do:** Use abstract paths (e.g., `/tmp/sandbox/secret.txt` vs. `/etc/passwd`) and generic filenames (`traversal_test.rb`).
*   **Do:** Demonstrate the *mechanism* (e.g., `../../` escaping the root) but stop short of accessing sensitive system files.
*   **Don't:** Include scripts that scan for real user data or target specific production environments.

**2. Open a "Placeholder" Security Issue**
Create a new public issue with a title that signals severity without giving away the vector.
*   **Title:** "Security: Potential path traversal vulnerability in file handling"
*   **Body:**
    > "I have identified a potential path traversal vulnerability that may allow reading files outside the source directory. I have verified this locally with a sanitized test case.
    >
    > **Action Required:** This report contains sensitive details that could be weaponized before a fix is available. I am withholding the specific reproduction steps and code snippets.
    >
    > **Next Steps:**
    > 1. Please acknowledge receipt of this issue.
    > 2. Provide a preferred private channel (email, Signal, encrypted chat) or invite me to a private security fork if your organization supports it.
    > 3. Once a private channel is established, I will share the full PoC and technical details immediately.
    >
    > Until then, I will not post further technical specifics here to protect users."

**3. Manage the Timeline**
*   **If maintainers respond quickly:** Move the conversation to the private channel they provide, share the full PoC, and agree on a disclosure timeline (typically 45–90 days for a fix).
*   **If maintainers are unresponsive (7–14 days):** Post a follow-up comment stating you will share a *redacted* technical analysis in 7 days if no private contact is made, emphasizing that you are trying to help them secure the project.
*   **Last Resort:** If there is still no response after multiple attempts over a month, you may need to disclose the sanitized details publicly with a strong warning that no fix is yet available, though this is less ideal.

**4. Draft the Private Follow-up**
Once contact is established, send your full report including:
*   The exact Ruby code snippet causing the issue.
*   The step-by-step reproduction using your sanitized PoC.
*   Suggested fix (e.g., using `Pathname#realpath` and verifying it starts with the source root).
*   Proposed timeline for public disclosure.

This approach balances the urgency of the flaw with the ethical obligation to prevent immediate exploitation, forcing the maintainers to engage privately without leaving the vulnerability fully exposed on the public web.

*Note: Do not mention "AI-assisted" in your initial contact; maintainers may deprioritize reports that appear automated or unverified.*
*Keep all communication professional and focused on user safety to build trust quickly.*
