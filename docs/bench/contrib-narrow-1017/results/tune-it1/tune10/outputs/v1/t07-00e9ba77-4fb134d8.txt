### Responsible Disclosure Strategy for Missing Security Policy

**Immediate Action: Do Not Post Exploit Details Publicly**
Since the project lacks a dedicated security policy or private channel, posting a full reproduction case (exploit recipe) to the public issue tracker is unsafe. It exposes users to immediate attack before a fix exists. Instead, follow this phased approach:

**Phase 1: Locate a Human Contact (The "Soft" Search)**
Before filing any issue, attempt to find a maintainer through indirect channels to initiate a private conversation:
1.  **Check Commit History:** Run `git log` or view the repository's "Contributors" page. Look for maintainers with personal email addresses in their commit metadata (though many use noreply addresses).
2.  **Profile Mining:** Check the GitHub/GitLab profiles of the top 3-5 contributors. Look for linked websites, Twitter/X handles, or LinkedIn profiles where you might send a polite, non-public DM.
3.  **Dependency Check:** If this generator is a gem, check the `.gemspec` file for an `email` or `homepage` field that might lead to a personal contact.
4.  **Community Channels:** Search for a linked Discord, Slack, or forum. Join and ask politely: "Who is the best person to contact regarding a potential security vulnerability?" without giving details.

**Phase 2: The "Vague but Urgent" Public Issue (If No Contact Found)**
If you cannot find a private contact after a reasonable search (e.g., 24-48 hours), file a public issue that signals severity without providing the weapon. Use this template:

*   **Title:** `[SECURITY] Potential path traversal vulnerability affecting file access`
*   **Body:**
    > "I have identified a potential path traversal vulnerability that allows reading files outside the source directory via crafted filenames. I have verified this locally with synthetic test data.
    >
    > **Action Required:** I am withholding specific reproduction steps and payload examples to prevent active exploitation while a fix is developed.
    >
    > **Next Steps:** Maintainers, please contact me at [Your Secure Email/PGP Key] to discuss responsible disclosure and coordinate a patch. If no contact is made within [e.g., 7 days], I will proceed with standard disclosure timelines."

**Phase 3: Coordination and Fix**
Once a maintainer responds:
1.  **Verify Identity:** Ensure you are talking to a recognized contributor.
2.  **Share Details Privately:** Send the full reproduction case, including your synthetic test directory structure and the specific code paths involved.
3.  **Agree on Timeline:** Propose a reasonable window for them to develop and release a patch (typically 30-90 days) before you publish the full details.
4.  **Draft the Fix (Optional):** If you are comfortable, offer a generalized patch that strips all specific paths and uses synthetic data, ensuring no private information leaks.

**Key Principles for Your Communication:**
*   **Synthetic Data Only:** Never share logs or paths from your actual machine. Use invented values like `/tmp/fake_root` and `../../etc/passwd` (as a concept, not a live target).
*   **No Blame:** Frame the report as "helping secure the project," not "your code is broken."
*   **Patience:** Maintain silence on the public thread until the maintainer engages or the agreed timeout expires.

**Note:** If the project remains unresponsive after multiple attempts over several weeks, you may need to consider notifying the broader community (e.g., via a security mailing list like OSS-Security) to pressure a response, but only as a last resort.
**Note:** Always use encrypted email (PGP) if possible when transmitting vulnerability details.
