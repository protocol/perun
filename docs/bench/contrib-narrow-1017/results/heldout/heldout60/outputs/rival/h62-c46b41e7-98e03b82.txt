Open the pull request immediately without creating a separate issue.

For single-line documentation fixes like broken hyperlinks, creating a separate issue is widely considered unnecessary noise in the Go and broader open-source community. Maintainers of large repositories (30k+ lines) typically view "issue for a typo/link" as process bloat that slows down trivial merges. Since you have already verified the new link works and confirmed no other files reference the old address, you have satisfied the due diligence required for a "drive-by" contribution.

To ensure quick acceptance, structure your contribution as follows:

1.  **Branch Name**: Use a clear, descriptive name like `docs/fix-deprecated-api-link`.
2.  **Commit Message**: Strictly follow the Conventional Commits format, which is standard for Go projects. Use:
    `docs: update deprecated API reference link`
    In the body, briefly state: "The previous URL returned a 404 error. Updated to the current documentation location at [New URL]. Verified link accessibility across browsers."
3.  **PR Description**: Keep it minimal but evidence-based.
    *   **Summary**: "Fixes broken hyperlink in documentation pointing to deprecated API."
    *   **Evidence**: Explicitly state, "Verified new link resolves correctly; grep confirmed no other occurrences of the old URL in the repository."
    *   **Checklist**: If the PR template asks "Is there an associated issue?", select "No" or write "N/A: Trivial documentation fix."

Do not wait for approval before opening the PR; the PR *is* the request for approval. Waiting to file an issue first risks your contribution stalling in the backlog or being closed as "won't fix" simply because the maintainer considers the overhead disproportionate to the change. By submitting the fix directly with a professional commit message and clear verification evidence, you respect the maintainer's time and demonstrate the competence required for trust.

Note: If the repository has a specific `CONTRIBUTING.md` file (distinct from the README) that explicitly mandates issues for *all* changes, follow that rule; otherwise, the direct PR approach is the community norm.
Note: Monitor the PR for 24 hours to respond promptly if a maintainer requests minor adjustments.
