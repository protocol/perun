Do all three updates (changelog, docs, migration guide) in the **same branch** as your code fix. Do not open separate PRs. Since the maintainer explicitly requested these items before merging, they view them as part of the atomic change required to make your fix complete and safe for users. Splitting them would delay the merge and force reviewers to context-switch between code and documentation.

**Workflow:**

1.  **Check Existing Patterns:** Even without a template, scan the last 5–10 merged PRs in the repository history. Look at how they formatted changelog entries (e.g., `## [Version] - Date` vs. bullet points under `### Fixed`). Mimic the most recent style exactly. For the docs site, find the relevant section (e.g., "Networking" or "Configuration") and match the paragraph length and tone of adjacent entries.
2.  **Draft Content with Conservative Tone:**
    *   **Changelog:** Be terse and factual. Format: `Fixed: Memory leak in [Protocol Name] causing latency spikes under high load.` Avoid marketing language.
    *   **Docs Site:** Write for the end-user. Explain *what* changed and *how* it affects them, not the internal C++ implementation details. Example: "The library now correctly releases socket buffers after transmission failures. Users should see reduced memory footprint during network instability."
    *   **Migration Guide:** Be explicit about the breaking change. Use a warning block if the site supports it (e.g., `> **Warning:** Configuration structure changed...`). Provide a concrete "Before vs. After" code snippet showing the old config vs. the new required structure.
3.  **Commit Separately but Push Together:** Create distinct commits for clarity (e.g., `docs: add migration note for config break`, `chore: update changelog`), but push them all to your existing branch immediately. This keeps the PR history clean while allowing the maintainer to see that you addressed each requirement specifically.
4.  **Explicitly Invite Correction:** In a new comment on the PR, tag Ravi and write: "I've added the changelog entry, docs paragraph, and migration warning to this branch. I modeled the format on recent merges, but please let me know if the tone or technical detail needs adjustment before you hit merge." This signals compliance while acknowledging you don't have the internal style guide.

By keeping everything in one branch, you reduce friction for the maintainer. They can review the docs alongside the code to ensure the documentation accurately reflects the fix, then merge once with a single click.

Note: If the maintainer rejects the format, be prepared to amend commits immediately rather than arguing style preferences.
Note: Ensure your migration guide example compiles or validates against the new config schema if possible.
