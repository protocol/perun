## Summary
Restores graceful handling of out-of-stock items by reintroducing a configurable backorder fallback, preventing unhandled exceptions in downstream checkout systems while preserving the recent performance optimizations introduced in the previous update.

## What
- Reverts the hard-failure behavior for out-of-stock items to a soft-failure with a backorder signal.
- Introduces a `StockSyncConfig` flag (`allowBackorderFallback`) to make this behavior explicit and toggleable.
- Refactors the inventory check logic to separate performance caching (kept) from the error-handling policy (changed).
- Adds unit tests verifying both the new config flag and the legacy-compatible default behavior.

## Why
The recent update optimized inventory lookup speed but inadvertently changed the contract for out-of-stock scenarios from "return backorder status" to "throw exception." While the performance gain is valuable, the hard failure breaks the standard graceful-degradation pattern expected by many retail integrations, not just specific internal systems. This PR argues that throwing on missing stock is a regression for any system expecting to handle backorders manually, and provides a configuration switch to satisfy both high-throughput strict modes and legacy-compatible graceful modes.

## Test Plan
- Run `mvn test -Dtest=StockSyncFallbackTest` to verify backorder signaling.
- Run `mvn test -Dtest=PerformanceRegressionTest` to confirm caching logic remains intact.
- Verify `StockSyncConfigTest` covers both enabled and disabled fallback states.
- Manual verification: Simulate out-of-stock response; observe application continues with backorder message instead of crashing.

## Backward Compatibility
This change restores backward compatibility for users relying on the pre-update behavior. The new configuration option defaults to `true` (graceful fallback) to prevent immediate crashes in existing deployments, but can be set to `false` for systems preferring strict failure.
