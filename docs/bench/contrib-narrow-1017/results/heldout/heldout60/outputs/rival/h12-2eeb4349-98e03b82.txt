## Summary
Resolves a race condition in the test harness causing ~5% flaky failures during parallel execution. The fix introduces a deterministic synchronization barrier before state assertion, ensuring async operations complete fully before validation begins.

## What
- **Modified:** `test-utils/async-helpers.js` – Added `waitForStableState()` utility.
- **Modified:** `core/test-runner.js` – Integrated the new utility into the pre-assertion lifecycle hook.
- **Added:** `tests/regression/race-condition-fix.spec.js` – Specific stress test reproducing the timing window.

## Why
The current test runner asserts DOM state immediately after triggering an event. In high-load CI environments, microtasks or macrotasks (e.g., network mock resolution) occasionally lag behind the main thread, leading to assertions running against stale data. This manifests as non-deterministic failures where the application is functionally correct but the test observes an intermediate state. This change enforces a "settle" period, guaranteeing the event loop is empty before proceeding.

## Technical Deep Dive (Race Condition Analysis)
The root cause is a classic "check-then-act" race in the asynchronous test lifecycle.
1. **Trigger:** Test fires `click()` event.
2. **Race:** The framework queues a state update via `Promise.resolve().then(...)`.
3. **Failure Point:** The test runner's assertion logic executes *before* the microtask queue drains, reading the pre-update value.
4. **Fix:** The new `waitForStableState()` inserts a `await new Promise(r => setTimeout(r, 0))` loop that checks a "pending mutations" counter. It only resolves when the counter hits zero, ensuring the microtask queue is fully drained and all reactive updates have flushed to the DOM before the assertion runs.

This approach avoids arbitrary `sleep()` calls, which are brittle, by instead actively polling the framework's internal mutation scheduler until idle.
