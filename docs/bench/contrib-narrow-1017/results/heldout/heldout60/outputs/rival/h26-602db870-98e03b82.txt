### Step 1: Generate the Patch Correctly

1.  Ensure your fix is committed:

2.  Generate the patch file. The `-p1` format is standard for most C projects:
    ```bash
    git format-patch -1 --stdout > fix-attachment-corruption.patch
    ```

### Step 3: Subject Line Formatting
Email-based projects rely on subject prefixes for filtering and archiving. Based on standard conventions for C projects:
*   **Prefix:** Use `[PATCH]` followed by the subsystem or component.
*   **Format:** `[PATCH] attachment: fix corruption for files >10MB`
*   **Versioning:** If you need to resend, increment the version: `[PATCH v2] ...`

### Critical Pitfalls to Avoid
1.  **Line Wrapping:** The most common failure. If any line in your diff exceeds 78 characters and the mail server wraps it, the patch fails. `git send-email` handles this; webmail does not.
2.  **Character Encoding:** Ensure your email is sent as `UTF-8` or `ASCII` without "Quoted-Printable" encoding if possible, though `git send-email` manages this automatically.
3.  **HTML Artifacts:** Never send HTML. Even a single `<div>` tag or hidden CSS style will cause the maintainer's `git am` command to reject the patch immediately.
