Do not open a new issue. In projects with large backlogs (500+ open items), maintainers actively dislike duplicates because they fragment context and force manual merging later. Since the original report describes the *exact* same symptom and error code, your data belongs in that thread to prove the bug is reproducible and not an isolated environment glitch. The "needs info" label is a blocker; your logs remove that blocker, which is the most direct path to getting the issue triaged.

**Action Plan:**

1.  **Comment on the existing issue immediately.** Start by explicitly stating you have reproduced the bug.
2.  **Provide the missing evidence.** Paste the relevant log snippets showing the "connection reset by peer" error at the 24-hour mark. If the logs are long, attach them as a file or link to a Gist.
3.  **Confirm environment details.** Briefly list your Java version, OS, and library version to show if the issue persists in newer releases or is specific to certain configurations.
4.  **Offer a minimal reproduction.** If you have a small code snippet that triggers the drop reliably, include it. This is often the "golden ticket" that moves an issue from "needs info" to "confirmed."
5.  **Politely ping the maintainer.** Tag the maintainer who last commented (e.g., "@maintainer-name I've added the requested logs below...") to trigger a notification.

**Why this works:** It transforms a stale, blocked ticket into an actionable, confirmed bug without creating noise. Maintainers prefer one rich thread over two sparse ones.
