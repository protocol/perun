**Deliverable: Strategy and Draft Text**

Do not check boxes you cannot honestly verify. Maintainers prefer accurate, minimal compliance over false claims. For a documentation-only typo fix, the standard open-source convention is to mark the template as "Partially Applicable" or to check only the relevant boxes while explicitly noting the scope in the PR description. This prevents bot rejection (which usually scans for *any* unchecked box without context) and maintains integrity.

**Step 1: Modify the PR Description Header**
Add a clear scope declaration at the very top of your PR body, before the template starts:
> "Scope: Documentation only (README typo fix). No code, build, or runtime changes included. Consequently, checks related to performance, security, and binary compatibility are marked N/A below."

**Step 2: Handle the Checkboxes**
- **Check** boxes related to: "Documentation updated," "Tests passed" (if CI runs linting on docs), and "No breaking changes."
- **Leave Unchecked** boxes related to: "Benchmarks," "Security Audits," "Backward Compatibility Tests."
- **Add a comment** next to the unchecked boxes directly in the template text: `- [ ] Performance benchmarks (N/A: No code changed)`

**Step 3: Ready-to-Paste Commit Message**
```text
docs: fix typo in README installation section

Corrects a minor spelling error in the setup instructions.
No functional code changes.
```

**Step 4: Ready-to-Paste PR Body Snippet**
```markdown
## Summary
Fixes a typo in the README file.

## Scope Note
This change is documentation-only. The following template items are not applicable:
- Performance benchmarks
- Security audits
- Backward compatibility tests

## Checklist
- [x] Documentation updated
- [ ] Performance benchmarks (N/A: No code changed)
- [ ] Security audits (N/A: No code changed)
- [x] No breaking changes
- [ ] ... (continue pattern for other non-applicable items)
```

**Direct Answer to Your Uncertainty**
Leaving boxes unchecked without explanation risks automated closure; checking them falsely risks maintainer distrust. The solution is to leave them unchecked but **annotate them as "N/A"** within the list. This satisfies bots looking for human engagement and signals honesty to maintainers.

**Fallback if Maintainers Stay Silent**
If the PR sits for two weeks, post a single polite comment: "Hi, just checking if the N/A markings on the checklist are acceptable for this docs-only fix, or if you'd prefer I adjust the template usage. Thanks!"

**Stop Checks & Privacy Note**
Before submitting, ensure you are not violating any employer IP rules regarding external contributions, even for typo fixes. Since your internal pipeline flagged this, confirm that the *fact* of the error isn't proprietary (e.g., if the typo reveals an internal codename). If the typo is generic, no further stripping is needed. Do not mention your internal pipeline in the PR; simply state you found the typo.

*Note: Never edit the project's CI configuration or template files to bypass these checks for your own PR.*
*If the project strictly requires all boxes checked with no N/A option, file an issue first asking for clarification rather than forcing a submission.*
