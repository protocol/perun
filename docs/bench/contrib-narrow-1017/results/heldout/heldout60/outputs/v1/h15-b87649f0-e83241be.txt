**Deliverable: Evaluation and Draft Contribution**

**1. Evaluation: Do not submit yet.**
Documenting an undocumented, experimental flag without maintainer confirmation carries high risk. If the flag is unstable, your documentation will become incorrect immediately upon the next release, confusing users and creating a support burden. The "strict rule" requiring a working example and use case implies the project values stability; documenting an internal experiment likely violates the spirit of this rule even if it technically satisfies the format. The correct path is to treat this as a **question first**, not a contribution.

**2. Strategy: Inquiry before Documentation**
Instead of opening a Pull Request (PR) with the documentation immediately, open an **Issue** or start a **Discussion** (if the project uses them). This allows you to:
*   Verify the flag's stability without committing to a public doc change.
*   Ask the maintainers directly if they intend to stabilize or remove it.
*   Offer your real-world use case as evidence for *why* it should be documented, rather than assuming it should be.

**4. How to Phrase the Description (If Approved)**
If maintainers confirm the flag is stable, phrase the documentation to emphasize the **specific problem it solves** rather than just the flag's existence. This aligns with the project's requirement for a "use case."

*Draft Documentation Snippet:*
> **`--force-atomic`**
> *Ensures archive integrity during network interruptions.*
>
> When transferring archives over unstable network connections, this flag forces the tool to complete write operations atomically, preventing partial or corrupted files if the connection drops mid-transfer.
>
> *Example:*
> ```bash
> zipmaster create backup.zip /data --force-atomic
> ```
> *Use Case:* Recommended for automated deployment scripts running over WAN or unreliable networks where connection drops may occur during large file transfers.
