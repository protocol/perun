### Benchmarking Strategy for Confidential Data

To satisfy the requirement for reproducible benchmarks without leaking Acme Industries' confidential transaction logs, you must decouple the **data structure** from the **data content**. The goal is to create a synthetic dataset that mimics the statistical properties of your real data (size, schema, distribution, and cardinality) without containing any actual customer information.

**1. Create a Synthetic Data Generator**
Instead of exporting real logs, write a small script (e.g., `generate_bench_data.py`) included in your contribution. This script should:
*   **Match Schema:** Replicate the exact column names and data types of the Acme logs.
*   **Match Scale:** Generate the same number of rows (e.g., 10 million records) to ensure memory and I/O pressure are identical to your internal tests.
*   **Match Distribution:** If your performance gain relies on specific patterns (e.g., high cardinality in a "user_id" column or skewed timestamps), configure the generator to produce random data with those same statistical characteristics. Use libraries like `Faker` or `numpy` to generate plausible but fake values.
*   **Determinism:** Seed the random number generator with a fixed integer. This ensures that anyone running the script gets the exact same dataset, satisfying the "reproducible" requirement.

**2. Define the Benchmark Harness**
Since the project lacks a formal suite, propose a simple, standard format. Create a script (e.g., `run_benchmarks.sh` or a Python script using `timeit` or `pytest-benchmark`) that:
*   Runs the data generator.
*   Executes the DataStream processing pipeline on the generated data.
*   Measures **wall-clock time** and **peak memory usage**.
*   Runs the test multiple times (e.g., 5 iterations) and reports the average and standard deviation to account for system noise.
*   Compares the "before" (main branch) and "after" (your PR) versions side-by-side.

**3. Addressing the "Random Data" Concern**
Your worry that random data won't reflect real gains is valid only if the optimization depends on specific *values*. If the 15% speedup comes from algorithmic efficiency (e.g., better indexing, reduced copying, optimized loops), it will manifest on any data of the same shape and volume. In your PR description, explicitly state: *"The synthetic data preserves the row count, schema, and value distribution of production workloads to ensure the benchmark reflects real-world computational complexity."* This demonstrates rigor.
