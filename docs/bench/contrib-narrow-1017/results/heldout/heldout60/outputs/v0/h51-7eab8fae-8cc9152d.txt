For a trivial deprecation fix, your pull request description should be **brief and focused on the "what" and "why,"** omitting the full stack trace entirely. Since the change is a direct version compatibility update (replacing an outdated assertion method), the motivation is self-evident to maintainers: silence noise and ensure future compatibility.

Include only:
1.  **The specific warning message** (text only, no stack trace).
2.  **The action taken** (e.g., "Updated `assertXYZ` to `newAssertXYZ`").
3.  **Verification** (e.g., "Verified locally that warnings are gone and tests pass").

**Do not include the full stack trace.** It adds no value for a simple API update and significantly increases the risk of leaking your internal project structure, private file paths, or the "private tags" you mentioned. A single sentence summarizing the error is sufficient context. If maintainers need more, they will ask.

**Crucially:** Ensure you manually scrub the warning text itself. Even without a stack trace, the raw warning message might contain dynamic values, internal IDs, or environment-specific paths generated by your test runner. Copy the text into a neutral editor, remove any variable data, and paste only the static template of the message into the PR.

*Note: Never paste raw logs from internal runners directly into public forums; always assume they contain hidden identifiers.*
*Note: If the warning message itself reveals proprietary logic, paraphrase it generically (e.g., "fixed deprecated assertion warning in test suite").*
