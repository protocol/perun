Submit the pull request directly without opening a separate issue first.

For minor, non-controversial fixes like broken hyperlinks, typos, or trivial documentation updates, the open-source community generally prefers direct patches. Creating an issue for a fix you have already verified and implemented adds unnecessary friction for both you and the maintainers, cluttering the tracker with "noise" that delays actual work. Since you have already confirmed the new link works and verified that no other files reference the old address, your contribution is ready for immediate review.

In your pull request description, clearly state:
1.  **What** is broken (the old URL returning 404).
2.  **What** you changed (the new, verified URL).
3.  **Verification** that you checked for other instances of the old link.
4.  **Impact** (resolves user confusion during integration).

This approach respects the maintainers' time by presenting a complete solution rather than just a problem report. If the project strictly requires issues for all changes, the maintainers will simply comment on your PR asking you to open one, but this is rare for documentation hyperlinks. Most projects explicitly welcome "drive-by" fixes for docs to lower the barrier for new contributors.

Note: Ensure your commit message follows the repository's existing style (e.g., "docs: update deprecated API link").
If the PR remains unreviewed for several weeks, a polite comment bumping the thread is appropriate.
