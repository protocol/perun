First call: GO — the strategic need for control is real, but the execution risks are severe and largely unmitigated.

Steelman: A default maps switch gives the phone maker independence, data leverage, and a differentiated UX (3D, voice) that could win users over despite initial gaps.

Attacks:

- **Data quality gap is existential.** Less data and wrong place info directly degrade the core utility of maps. Users don’t forgive navigation errors; they switch away or complain loudly. This is not a cosmetic risk—it’s the product’s reason to exist.
- **Default removal is a user-hostile act.** Taking away a working, trusted app and replacing it with a worse one invites backlash, bad press, and support load. The annoyance is predictable, not hypothetical.
- **No pilot, no fallback, no metric.** The plan commits to a full fall launch with no staged rollout, no opt-out for users, and no defined quality threshold. If the data is wrong, you’ve already shipped the damage.
- **Reversibility is low.** Once default, switching back is a public admission of failure and a strategic setback.

Better ways: keep the rival app as default but preinstall the new maps as an option, run a beta with a user cohort, or delay launch until data parity is closer. These reach the same strategic goal with far less blast radius.

Kill criteria: if place-error rate exceeds X% in pilot, or if user complaints exceed Y per 1000 activations, hold the launch. None are defined.

The proposal fails as written because its own stated risks—less data, wrong info, user annoyance—are not answered by any mitigation. The upside is real but the path is reckless.

DECISION: NO-GO
