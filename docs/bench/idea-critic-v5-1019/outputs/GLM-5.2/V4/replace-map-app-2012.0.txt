First call: NO-GO — the stated risks are not edge cases but the core product failing at launch, and the plan removes a working app to force that failure on every user.

Steelman: owning maps is strategically essential for a phone platform's location, navigation and assistant future; shipping now captures that even if v1 is rough.

Blockers: the proposal's own risks state, as present fact, that the new maps have far less data and contain wrong place/business information. That is not a risk to mitigate — it is the core product failing at launch. The plan removes the working rival app by default, so the user's only escape is manual re-add. Removing what works to ship what the proposal itself admits is broken is a self-inflicted downgrade with no rollback path for the installed base.

Risks: a maps product is only as good as its data; several providers stitched together will have seams and gaps that take years, not weeks, to close. Brand trust, once burned by a flagship launch failure, is expensive to recover. Voice assistant and navigation features built on incomplete data inherit that incompleteness.

Kill criteria: place-data accuracy below a named threshold on launch day → keep the rival app as default for one more cycle. A pilot on a subset of new phones (not updates) for 30 days, measuring reported wrong-locations per 10k lookups against the incumbent's rate, would settle whether the data is good enough.

Better way: ship the own maps app as an optional install alongside the rival's default for one cycle, collect accuracy telemetry, then flip the default when place-data parity is demonstrated — same strategic destination, no forced downgrade.

DECISION: NO-GO
