### Pre-Launch Safety Plan: On-Device Chronic Pain Assessment

**1. Harm Inventory (MAP)**
Before testing, explicitly record the specific risks this tool poses to patients:
*   **Bias/Unfair Outcomes:** The algorithm systematically underestimates pain impact for specific demographics (e.g., elderly, non-native speakers) due to training data gaps.
*   **Hallucination as Fact:** The tool assigns a high "intervention level" based on contradictory or vague patient inputs, presenting the suggestion as a definitive medical necessity.
*   **Over-reliance:** Clinicians or patients trust the automated score without clinical context, ignoring visible signs of distress that the model missed.
*   **Unsafe High-Stakes Automation:** The tool automatically triggers a referral or medication change without human review, leading to inappropriate treatment.
*   **Missing Disclosure:** Patients are unaware the assessment is machine-generated and do not know its limitations.

**2. Measurement Strategy (MEASURE)**
Since cloud updates are impossible, your evaluation dataset must be frozen, comprehensive, and embedded on-device. Do not assert accuracy; measure residual risk.

*   **Construct Edge-Case Probe Sets:** Create a local "red-team" dataset containing:
    *   *Non-linear inputs:* Patients reporting low pain scores but high functional impairment (or vice versa).
    *   *Subtle indicators:* Vague language, cultural idioms of distress, and conflicting self-reports.
    *   *Positive Controls:* Known cases where the tool *must* flag high risk.
    *   *Negative Controls:* Known cases where the tool *must* suggest low intervention.
*   **Define Runnable Test Rows:** For each harm above, run a test with a pass/fail threshold.
    *   *Example:* "Input: Patient describes 'manageable' pain but reports inability to sleep or work for 3 weeks. Metric: Intervention Level suggested. Threshold: Must not suggest 'Low/Monitor Only'. Stop Condition: If >5% of subtle-high-risk cases are misclassified as low risk, block launch."
*   **Report Residual Risk:** Document the failure rate on these edge cases as `UNVERIFIED` for any scenario not covered by your local dataset. Do not invent a "99% accurate" claim.
*   **Transparency Artifact:** Create a **Model Card** stored locally with the app. It must list: intended use (screening only, not diagnosis), known limitations (e.g., "performance not verified for pediatric populations"), and the specific edge cases tested.

**3. Risk Management (MANAGE)**
*   **Human-in-the-Loop Gate (Critical):** Because this tool suggests intervention levels for health outcomes, **no automated action should be final.** The output must be presented as a "Draft Recommendation" requiring explicit confirmation by a clinician before any care plan is altered. Fully autonomous execution of high-stakes medical decisions is the failure state this plan prevents.
*   **Show Uncertainty:** Do not display a precise percentage (e.g., "87% severity"). Instead, use defined coarse tiers (e.g., "High Confidence," "Corroborated," "Unclear/Needs Review") based on input clarity. If inputs are ambiguous, the tool must default to "Needs Review" rather than guessing.
*   **Disclosure:** Clearly label the output: "This assessment is generated by an automated tool to assist clinical judgment. It does not replace professional medical advice."

**4. Governance (GOVERN)**
*   Name one owner responsible for reviewing any reported errors.
*   Since the model cannot update via cloud, establish a protocol for pushing a full app version update if new edge cases are discovered in the field.

**Note:** This plan identifies risks and controls; it does not certify the tool as "safe" or "unbiased." Legal requirements for medical device disclosure must be verified by counsel.
