### Harm Inventory: Patient-Medication-Timing-Bot

Before launch, the following specific harms must be recorded for this feature, given the constraint of static location strings:

1.  **Unsafe Automation of High-Stakes Actions (Missed/Duplicate Doses):**
    *   **Failure Mode:** The bot fails to adjust for Daylight Saving Time (DST) start/end or timezone transitions because the static string does not update automatically, or the logic misinterprets the string during transition periods.
    *   **Affected Users:** Patients on complex chronic schedules (e.g., insulin, anticoagulants, immunosuppressants) traveling between regions.
    *   **Worst Realistic Case:** A patient misses a critical dose due to a time shift error, leading to acute health deterioration, hospitalization, or death. Conversely, a duplicate reminder causes accidental double-dosing.

2.  **Over-Reliance / Automation Bias:**
    *   **Failure Mode:** The interface presents the reminder as an authoritative, dynamically adjusted instruction without surfacing the limitation that the underlying location data is static and may be stale if the user traveled recently without updating their profile.
    *   **Affected Users:** Traveling patients who assume the bot "knows" their current location.
    *   **Worst Realistic Case:** User trusts the bot's incorrect time over their own judgment or other cues, resulting in medication error.

3.  **Missing AI-Disclosure / Transparency:**
    *   **Failure Mode:** The user is not informed that the "dynamic" adjustment relies on a manually updated static string, creating a false impression of real-time geolocation awareness.
    *   **Affected Users:** All users, specifically those with low technical literacy.
    *   **Worst Realistic Case:** User fails to manually update their location string upon travel, assuming the system handles it automatically.

### Management Controls (Required Before Launch)

1.  **Human-in-the-Loop Gate:** For any detected timezone ambiguity or transition date, the system must **not** auto-send the reminder. It must require explicit user confirmation or fall back to a safe, explicit "Please verify your current time zone" notification.
2.  **Uncertainty Disclosure:** The reminder message must include a defined tier of confidence or a disclaimer: *"Reminder based on profile location: [City]. If you have traveled, please update your settings immediately."* Do not display raw confidence percentages.
3.  **Transparency Artifact:** Create a **Model/Data Card** for this feature documenting:
    *   **Limitation:** Reliance on static user-provided strings; no real-time geolocation.
    *   **Intended Use:** Reminder aid only, not a medical device replacement.
    *   **Known Failure Modes:** DST transitions if user data is stale; travel without profile update.
    *   **Owner:** Name the specific team member responsible for monitoring timezone-related incidents.
