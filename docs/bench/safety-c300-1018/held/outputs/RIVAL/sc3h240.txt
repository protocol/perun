**Pre-Launch Safety Verification Plan for Offline Fall-Recovery Bot**

**1. Static Instruction Validation (Pre-Deployment)**
Since remote updates are impossible, the core instruction set must be validated against a comprehensive medical matrix before loading onto devices.
*   **Medical Expert Review Board:** Convene a panel of geriatricians, physical therapists, and orthopedic specialists to audit every possible instruction branch. They must verify that advice for specific scenarios (e.g., "hip pain," "dizziness," "unable to bear weight") aligns strictly with current clinical guidelines for fall recovery.
*   **Scenario Coverage Matrix:** Create a grid mapping all detected variables (body position, reported pain location, mobility aid availability, cognitive state) to specific instruction outputs. Ensure there are no "dead ends" where the bot provides no guidance or contradictory advice.
*   **Contraindication Check:** Explicitly test logic to ensure the bot *never* instructs a user to stand if high-risk indicators (e.g., suspected hip fracture, severe head impact, loss of consciousness) are detected. The default failure mode must be "Stay down and call for help," not "Try to get up."

**2. Simulated Stress-Testing of Instruction Logic**
To account for high-stress confusion and varying senior capabilities, simulate the user environment rigorously.
*   **Cognitive Load Simulation:** Recruit participants (including seniors) to act as users in simulated fall scenarios. Introduce stressors such as background noise, poor lighting, and time pressure. Observe if users misinterpret verbal cues due to anxiety or hearing limitations.
*   **Ambiguity Injection:** Test the bot's response to vague or contradictory user inputs (e.g., "I think I'm hurt" vs. "I'm fine"). Verify the bot defaults to the safest possible path (assuming injury) rather than guessing.
*   **Mobility Level Variance:** Simulate users with different mobility constraints (e.g., post-stroke, arthritis, prosthetic limbs). Ensure instructions are adaptable; for instance, if a user cannot push up with their arms, the bot should suggest rolling to a side or crawling to a stable object rather than insisting on a standard push-up maneuver.
*   **"Happy Path" vs. "Edge Case" Ratio:** Dedicate 70% of testing cycles to edge cases (partial falls, tangled limbs, obstructed views) rather than ideal scenarios. The offline nature means the bot must handle these locally without failing silently.

**3. Human-in-the-Loop Verification Protocol**
*   **Blind Audits:** Have independent safety engineers, unaware of the specific code logic, observe simulated tests. They should flag any instance where the bot's advice feels unsafe or confusing, regardless of whether it technically follows the code.
*   **Step-by-Step Timing Analysis:** Measure the time between fall detection and the first instruction. Ensure the pacing allows a disoriented senior to process information. If instructions are too rapid, the user may panic; too slow, and they may attempt unsafe self-recovery.
*   **Fail-Safe Trigger Testing:** Physically simulate conditions that should trigger an emergency halt (e.g., user stops responding, detects secondary impact). Confirm the bot immediately switches to emergency alert mode (if connected to local alarm) or repetitive "Do not move" verbal loops.

**4. Final Freeze and Immutable Build Verification**
*   **Hash Verification:** Once the instruction set is approved, generate a cryptographic hash of the final offline model and instruction database. Deploy this exact build to all pilot units.
*   **Pilot Shadow Mode:** In the initial assisted living deployment, run the bot in "shadow mode" where it analyzes falls and generates instructions internally but does not speak them aloud unless a human supervisor confirms the advice matches the safety protocol. This provides a final real-world validation layer before full activation.

*Note: Given the offline constraint, consider including a physical "emergency stop" button on the device hardware to immediately silence the bot if it begins issuing unsafe advice.*
*Ensure all pilot participants sign informed consent forms acknowledging the experimental nature of the offline verification process.*
