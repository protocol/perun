### Pre-Launch Safety Protocol: Adolescent Fitness Guidance Verification

Given the constraint that hardware shipment cannot be delayed, this protocol focuses on a rapid, high-intensity software validation sprint to be executed in parallel with final hardware assembly. The goal is to certify the advice engine's logic before the devices leave the factory floor or via a mandatory "safe-mode" activation sequence that requires a verified safe firmware signature.

**1. Establish Adolescent-Specific Safety Guardrails (Days 1-2)**
Define explicit, non-negotiable boundaries based on pediatric exercise physiology and psychology. These rules will serve as the "oracle" for all testing.
*   **Physiological Limits:** Hard-code maximum heart rate zones, calorie deficit caps, and growth-plate-safe movement restrictions specific to ages 13–19. Any recommendation exceeding these thresholds is an automatic critical failure.
*   **Psychological Safeguards:** Prohibit language promoting rapid weight loss, body shaming, or eating disorder triggers (e.g., "burn off," "punishment," specific low-calorie targets). The system must prioritize "strength," "energy," and "skill" over "weight" or "size."
*   **Contextual Awareness:** Ensure the system adjusts recommendations based on user-inputted age and development stage. A routine for a 14-year-old must differ materially from an adult routine.

**2. Adversarial Simulation & Edge Case Testing (Days 3-5)**
Since real teen testing is ethically complex and time-consuming, employ a "Red Team" of experts (pediatricians, child psychologists, and certified youth trainers) to simulate vulnerable user personas.
*   **Persona Injection:** Simulate inputs from users with varying risk profiles: e.g., a 13-year-old seeking extreme weight loss, a user with known anxiety, or a user attempting to bypass age restrictions.
*   **Stress Testing:** Feed the system ambiguous or leading prompts (e.g., "How can I lose 10 lbs in a week?") to verify the refusal mechanisms. The system must not only refuse harmful requests but actively pivot to safe, supportive alternatives.
*   **Longitudinal Simulation:** Run simulated 30-day user journeys to detect "drift," where cumulative advice might inadvertently encourage unhealthy patterns over time, even if daily advice seems safe.

**3. Automated Logic Verification (Days 6-8)**
Implement a deterministic test suite that runs against the advice engine's output.
*   **Keyword & Sentiment Analysis:** Scan all generated responses for banned phrases and negative sentiment patterns associated with body dysmorphia.
*   **Metric Validation:** Automatically flag any workout plan that exceeds established physiological limits for the declared age group.
*   **A/B Comparison:** Compare current engine outputs against a "golden set" of pre-approved, expert-vetted responses. Any deviation beyond a strict tolerance threshold triggers a block.

**4. The "Golden Signature" Release Gate (Days 9-10)**
To address the hardware constraint without compromising safety:
*   **Cryptographic Signing:** Once the software passes all above tests, generate a cryptographic signature of the safe firmware version.
*   **Hardware Handshake:** Configure the mirrors to check for this specific signature upon first boot. If the installed software does not match the signed "Safe Version," the mirror enters a locked "Maintenance Mode" displaying a customer support number, preventing any workout guidance from being delivered.
*   **Kill Switch:** Embed a remote capability to disable the coaching module if a post-launch vulnerability is discovered, reverting the device to a basic display-only mode.

**Deliverable:** A validated "Safe Version" firmware binary with a cryptographic signature, accompanied by a test report certifying zero critical violations against adolescent safety guardrails.

*Note: This protocol assumes the software can be updated or verified post-assembly; if the firmware is permanently burned into read-only memory before this testing completes, shipment must be halted regardless of partner refusal.*
