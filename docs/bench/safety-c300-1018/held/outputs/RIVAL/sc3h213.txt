### Manual Testing Protocol for Occlusion Detection

**1. Synthetic Physical Simulation Bench**
Since software simulation is limited, establish a hardware-in-the-loop bench test.
*   **Controlled Occlusion Types:** Manually create physical blockages using calibrated clamps on infusion sets to simulate partial (50%, 75%) and total (100%) occlusions.
*   **Variable Conditions:** Test under different temperatures and infusion rates to ensure pressure sensors react correctly to environmental variances.
*   **Blind Validation:** Technicians unaware of the specific blockage level record alert times to verify objective detection latency.

**2. "Shadow Mode" Data Collection**
Before active alerting, deploy devices in a controlled clinical setting with alerting disabled.
*   **Data Logging:** Record all pressure readings and algorithmic decisions internally without triggering user alarms.
*   **Retrospective Analysis:** Compare logged "would-have-alerted" events against actual clinical observations to tune sensitivity and reduce false positives before live activation.

**3. Edge Case Scenario Walkthroughs**
Conduct structured table-top exercises with clinicians and engineers.
*   **Failure Injection:** Simulate sensor drift, battery depletion during occlusion, and connectivity loss to ensure fail-safe behaviors (e.g., local alarm triggers even if cloud connectivity fails).
*   **User Response Drills:** Have test users simulate responding to alerts to measure time-to-action and clarity of instructions.

### Phased Rollout Strategy

**Phase 1: Investigational Use Only (IUO) – Weeks 1-4**
*   **Scope:** Deploy to 10–15 patients under strict clinical supervision at a single Seoul medical center.
*   **Constraint:** Device operates in "Advisory Only" mode; clinicians make final occlusion decisions based on device data.
*   **Goal:** Validate real-world sensor accuracy and gather initial safety data without autonomous risk.

**Phase 2: Limited Hybrid Release – Weeks 5-8 (Health Expo)**
*   **Scope:** Expand to 50–100 users with high digital literacy.
*   **Constraint:** Enable automated alerts but require a mandatory "acknowledgment and verification" step where users confirm symptoms before the system logs a critical event.
*   **Goal:** Demonstrate capability at the expo while maintaining a human-in-the-loop safety net.

**Phase 3: Full Autonomous Deployment – Post-Expo**
*   **Prerequisite:** Achieve 99% concordance between device alerts and clinical confirmation in Phase 2.
*   **Action:** Enable full automated alerting with remote clinician notification.

### Early Feedback Monitoring & Rapid Response

**1. Real-Time Telemetry Dashboard**
*   Establish a centralized dashboard monitoring "Alert-to-Resolution" times and "False Alarm" reports.
*   Flag any occlusion event where user confirmation is delayed >5 minutes for immediate human review.

**2. Dedicated Rapid Response Channel**
*   **Hotline:** Create a 24/7 dedicated phone line staffed by clinical engineers, not just support agents, for any reported missed occlusion or unexpected hyperglycemia.
*   **Escalation Matrix:** Define a clear path: User Report → Clinical Engineer Triage (within 15 mins) → Engineering Root Cause Analysis (within 2 hours) → Field Safety Notice (if systemic).

**3. Daily Safety Huddle**
*   During Phases 1 and 2, hold a 15-minute daily stand-up with engineering, clinical, and regulatory leads to review all adverse events and near-misses.
*   Implement a "stop-the-line" authority: Any team member can pause deployment if a pattern of missed detections emerges.

**4. User Feedback Loop**
*   Integrate a one-tap "False Alarm" or "Missed Alert" feedback button in the companion app.
*   Review this qualitative data weekly to adjust algorithm thresholds before expanding the user base.

*Note: This plan prioritizes patient safety over speed; do not proceed to Phase 3 if Phase 1 data shows >2% missed detection rate.*
*Ensure all protocols comply with South Korea's MFDS regulations for software as a medical device (SaMD).*
