### Manual Curation and Rapid-Update Plan for Mental Health Whitelist

**Phase 1: Pre-Launch Curation (Days 1–10)**
Given the API call limits, do not attempt broad regression testing. Instead, execute a targeted "seed-and-expand" manual curation:

1.  **Seed Collection:** Aggregate a static list of 50–100 high-authority URLs and 200 critical keywords from trusted sources (e.g., CDC, WHO, local Vancouver health authorities, and established suicide prevention NGOs). Focus on terms like "suicide prevention," "crisis text line," "mental health first aid," and specific educational program names.
2.  **Manual Verification:** Assign two moderators to manually verify each seed entry against the filter in a sandbox environment using single, direct API calls. Record the exact string or URL pattern that triggers the false positive.
3.  **Rule Construction:** Create explicit "allow" rules for these verified patterns. Prioritize exact URL matches and specific phrase exemptions over broad keyword whitelisting to minimize security risks.
4.  **Stakeholder Review:** Have the remaining four team members (engineers and lead moderators) review the allow-list for logic errors or overly permissive entries.

**Phase 2: Deployment with Human Gate (Days 11–14)**
Deploy the filter with the pre-curated whitelist active. Crucially, set the system to **log and block** rather than silently fail. If a teacher attempts to access a resource that is blocked, the system must display a clear message: *"This content was flagged by our safety filter. If you believe this is an educational resource, click here to request an immediate review."* This creates a mandatory human-in-the-loop gate for any contested content during the pilot.

**Phase 3: Rapid Update Workflow (Live Pilot)**
Establish a "Red Flag" protocol for the two-week pilot to handle teacher reports:

1.  **Intake Channel:** Create a dedicated, high-priority ticket queue (or Slack channel) solely for "Blocked Educational Resource" reports from the school district.
2.  **Triage SLA:** Assign one engineer and one moderator to monitor this queue continuously during school hours. Commit to a <2 hour response time SLA for these specific tickets.
3.  **Verification & Patch:** Upon receipt of a report:
    *   The moderator manually verifies the content is safe/educational.
    *   The engineer immediately adds the specific URL or term to the production allow-list.
    *   The team notifies the reporting teacher that access is restored.
4.  **Daily Sync:** Hold a 15-minute end-of-day standup to review all new additions, ensuring no malicious patterns were accidentally whitelisted and identifying if a broader category adjustment is needed.

**Risk Mitigation Note:**
Because this approach relies on manual curation and reactive updates, there is a residual risk that unlisted but safe resources will be blocked initially. Clearly communicate this limitation to the school district: the system is optimized for safety first, with a guaranteed rapid human override for educational needs. Do not claim the system is "bias-free" or "fully accurate"; explicitly state that the human review process is the primary safety net for educational content during this pilot phase.
