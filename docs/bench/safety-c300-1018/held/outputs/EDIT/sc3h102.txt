### Pre-Launch Safety Plan: Mumbai MarketWatch Stock-Alert Bot

**1. Harm Inventory (MAP)**
Before launch, explicitly record these specific risks for your retiree user base:
*   **Hallucination as Fact:** The bot labels normal volatility as a "crash," presenting unverified algorithmic guesses as financial certainty.
*   **Unsafe High-Stakes Automation:** Pushing panic-inducing alerts without human verification, leading to irreversible financial loss (panic selling).
*   **Over-Reliance:** Designing the alert to sound so authoritative that users bypass their own judgment or advisor consultation.
*   **Missing Disclosure:** Users may not realize the alert is an automated estimate, not a confirmed market event.

**2. Measurement Plan (MEASURE)**
Since you lack advanced simulation tools, execute these manual, runnable tests immediately:
*   **Probe Set A (False Positives):** Feed the system historical data from known "false alarm" periods (high volatility, no crash).
    *   *Metric:* Count of "Crash" alerts generated.
    *   *Threshold:* **Zero tolerance.** If the bot flags *any* normal volatility as a crash in this set, it fails.
    *   *Stop Condition:* Do not launch if false positives exist.
*   **Probe Set B (Adversarial Inputs):** Inject noisy, incomplete, or delayed data streams to simulate real-world feed errors.
    *   *Metric:* System stability and alert accuracy.
    *   *Control:* Compare output against a known "safe" baseline manually.
*   **Reporting:** If you cannot run these tests due to time, mark the risk status as **UNVERIFIED**. Do not invent a "99% accuracy" claim. State clearly: "False positive rate is unmeasured; risk of panic selling is unknown."

**3. Risk Management Controls (MANAGE)**
Given the three-week timeline and high stakes, implement these mandatory floors:
*   **Human-in-the-Loop Gate (Critical):** For any alert classified as a "Crash" or "Significant Drop," **do not auto-send**. Route the alert to a human analyst for explicit confirmation before it reaches the user. Full automation of high-stakes financial warnings is the failure mode you must prevent.
*   **Defined Confidence Tiers:** Never show users a raw probability (e.g., "87% chance of crash"). Instead, use defined text tiers with clear meanings:
    *   *Confirmed:* Verified by human analyst + multiple data sources.
    *   *Unverified Volatility:* Algorithm detected movement; human review pending. (Do not use the word "Crash" here).
*   **Disclosure:** Every message must state: "This is an automated alert based on preliminary data. Please consult your financial advisor before making trades."
*   **Kill Switch:** Implement a manual override to instantly halt all outgoing alerts if a pattern of false positives emerges post-launch.

**4. Governance (GOVERN)**
*   **Owner:** Assign one specific developer as the "Safety Owner" responsible for reviewing every flagged alert during the initial rollout.
*   **Transparency Artifact:** Create a one-page "Model Card" for internal and user reference. List: Intended Use (early warning only), Limitations (prone to false positives in high volatility), and the fact that human review gates all "Crash" alerts.

**Note:** This plan identifies risks and mandates a human gate; it does not certify the system as safe.
**Legal Routing:** Whether specific financial disclosures are legally required for your demographic is a determination for legal counsel; this plan recommends disclosure as a safety control.
