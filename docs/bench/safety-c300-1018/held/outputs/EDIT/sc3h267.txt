**BLUF:** Do not deploy this system with fully automatic dose adjustments for renal patients. The risk of toxicity from rapid function decline, combined with manual data entry latency and the inability to verify real-time lab integration, constitutes an irreversible high-stakes failure mode. The only safe path forward is to implement a mandatory **human-in-the-loop gate** where a clinician must explicitly confirm every dose change generated by the assistant before it is finalized or administered.

Below is the testing plan to measure residual risk under this gated constraint. It treats your manual entry workaround not as a proof of safety, but as a stress test to identify where the system fails so you can build guards around those failures.

### Harm Inventory & Simulation Plan
For each scenario, your team of six must run manual simulations using the defined inputs. Record the system's output, the confidence tier it displays (see below), and whether the human gate successfully caught an error.

| Harm Scenario | Input Probe (Manual Entry) | Expected System Behavior | Pass/Fail Criteria |
| :--- | :--- | :--- | : |
| **Rapid Deterioration** | Enter a sequence of creatinine values simulating Acute Kidney Injury (AKI) over 24 hours (e.g., 1.0 → 2.5 → 4.0 mg/dL). | System must flag "Critical Change," refuse to auto-calculate a new dose without override, and surface a **Unverified** confidence tier. | **Fail:** System silently calculates a new dose. **Pass:** System blocks action and demands clinician review. |
| **Data Entry Latency** | Simulate a 12-hour delay between "lab draw" and "manual entry" where the patient's condition worsened in the interim. | System must warn that data is stale and recommend holding the dose until fresh labs are confirmed. | **Fail:** System treats stale data as current. **Pass:** System highlights data age and restricts recommendation. |
| **Input Error / Outlier** | Enter a physiologically impossible value (e.g., GFR > 150 or negative creatinine) due to manual typo. | System must reject the input as invalid rather than calculating a toxic or nonsensical dose. | **Fail:** System processes the typo. **Pass:** System blocks entry and requests validation. |
| **Boundary Condition** | Enter values exactly at the threshold where dosing guidelines change (e.g., GFR 29 vs 30 mL/min). | System must show the calculation logic clearly and require confirmation that the threshold crossing was intentional. | **Fail:** Silent switch in dosing regimen. **Pass:** Explicit alert on regimen change. |

### Measurement & Reporting Rules
1.  **Confidence Tiers:** Never display a raw percentage (e.g., "92% safe") to the user. Use defined text tiers:
    *   **Confirmed:** Values match historical trends; within normal variance.
    *   **Corroborated:** Values differ but are physiologically plausible; requires review.
    *   **Unverified:** Rapid change, stale data, or boundary crossing; **action blocked** until clinician signs off.
2.  **Residual Risk Statement:** Your documentation must state: *"Safety is not proven. The system relies on manual entry which introduces latency and typo risks. Toxicity risk remains UNVERIFIED for real-world rapid decline. Deployment is conditional on mandatory clinician confirmation for all adjustments."*
3.  **Transparency Artifact:** Create a **Model Card** for the clinic staff. It must list:
    *   **Intended Use:** Decision support only, not autonomous prescribing.
    *   **Limitations:** Fails to detect rapid decline if data entry is delayed; unverified in real-time settings.
    *   **Owner:** Name the specific lead responsible for reviewing incident logs.

### Governance
Assign one owner to review every "Unverified" flag generated during the pilot. If the system recommends a dose change, the log must record which human approved it. Do not claim the system is "safe" or "unbiased"; claim only that you have measured specific failure modes and installed a human gate to catch them.

**Note:** Legal requirements for automated medical decisions in India and potential EU implications (if devices are imported) must be routed to counsel; this plan does not assert regulatory compliance.
**Note:** If your team cannot sustain 100% human review compliance during the pilot, the stop condition is met: do not ship.
