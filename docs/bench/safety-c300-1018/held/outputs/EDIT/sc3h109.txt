**Simulation Framework for Sensor Drift Validation**

To validate your inventory bot without triggering costly real-world orders or violating your supply chain contract, build an internal "Digital Twin" simulation environment. This framework decouples sensor input from physical action, allowing you to inject specific drift scenarios and verify the bot's decision logic safely.

**1. The Data Injection Layer (The "Fake Sensor")**
Create a software module that intercepts raw sensor data before it reaches the ordering logic. Instead of reading physical hardware, this module reads from a pre-recorded dataset of "normal" fridge conditions.
*   **Drift Injection Engine:** Build a function to programmatically alter this data. Define specific drift profiles:
    *   *Linear Drift:* Gradually shift temperature/freshness values over time to mimic aging sensors.
    *   *Step Change:* Sudden jumps in readings to simulate calibration shocks.
    *   *Noise Injection:* Add random variance to test stability.
*   **Scenario Library:** Construct specific test cases, including the "Spoiled Milk" scenario where the sensor reports "fresh" while the simulated ground truth is "spoiled."

**2. The Ground Truth Oracle**
Your simulation must know the *actual* state of the inventory independent of the sensor. Maintain a parallel "Ground Truth" ledger that tracks the real simulated freshness of every item.
*   **Comparison Logic:** The system must continuously compare the **Bot's Perceived State** (based on drifted sensor data) against the **Ground Truth State**.
*   **Failure Definition:** A test fails if the Bot initiates an order for an item marked as "spoiled" in the Ground Truth ledger, or if it fails to order when the Ground Truth indicates "empty."

**3. The Action Sandbox (The "Circuit Breaker")**
Since you cannot cancel real orders, you must prevent them from leaving your internal network.
*   **Mock Order Endpoint:** Replace the live supply chain API with a local mock server. This server accepts order requests but never transmits them externally.
*   **Audit Logging:** The mock server logs every attempted order with a timestamp, item ID, and the sensor reading that triggered it.
*   **Hard Stop Rule:** Implement a global flag in your beta build that physically disables the external network interface for the ordering service, ensuring no accidental real orders occur during testing.

**4. Execution Protocol**
Run the simulation in three phases before beta:
*   **Phase A (Baseline):** Run normal data streams to ensure the bot orders correctly under ideal conditions.
*   **Phase B (Adversarial Drift):** Run the "Spoiled Milk" and other drift scenarios. Measure the "False Positive Order Rate" (ordering bad goods) and "False Negative Rate" (failing to order good goods).
*   **Phase C (Threshold Tuning):** Adjust your calibration logic and safety thresholds based on Phase B results until the False Positive Rate for spoiled goods is zero.

**5. Human-in-the-Loop Gate**
Given the risk of financial penalty and user harm, do not enable fully autonomous ordering for the beta. Configure the system to require **human confirmation** for any order triggered when sensor confidence is below a defined threshold or when the item has a high spoilage risk. This acts as a final safety net should the simulation miss an edge case.

**Deliverable Checklist:**
*   [ ] Mock Sensor Module with Drift Injection scripts.
*   [ ] Ground Truth Ledger for validation.
*   [ ] Local Mock Order API with audit logging.
*   [ ] Report on False Positive/Negative rates under drift conditions.

**Note:** This approach satisfies your constraint by eliminating real order cancellations while rigorously stress-testing the logic. Ensure the "Human-in-the-Loop" gate remains active for the initial beta rollout to catch any unforeseen simulation gaps.
