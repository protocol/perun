**Recommendation: Sequential "Foundation-First" Rollout**

Do not execute the three streams in parallel. The critical path is constrained by the unbudgeted $50k API licensing fee and the external dependency on state tax approval. Adopt a sequential approach to de-risk cash flow and technical integration:

1.  **Phase 1 (Weeks 1–4): Financial & Legal Resolution.** Immediately secure the $50k API licensing budget. Simultaneously, pause all development until the state tourism tax timeline is clarified. Building a dynamic pricing engine without knowing the tax structure creates high rework risk.
2.  **Phase 2 (Weeks 5–16): Core Engine & API Integration.** Once taxes are clear, build the dynamic pricing engine (12 weeks) and integrate the beachfront API (4 weeks) concurrently. These are backend dependencies required before any UI can function correctly.
3.  **Phase 3 (Weeks 17–24): Mobile UI & QA.** Develop the mobile-first UI (8 weeks) only after the backend logic is stable. Follow with the 2-week internal QA.
4.  **Phase 4 (July 15 Launch):** Begin the 4-week beta.

This sequence pushes the target launch to late August, but it prevents building a UI for a pricing model that might change due to taxes, and ensures the $50k fee is secured before burning dev hours.

**Top Three Failure Modes**

1.  **Regulatory Misalignment:** The state tourism tax is approved with a structure incompatible with the hardcoded pricing engine logic, requiring a 6+ week refactor post-launch.
2.  **Budget Breach:** The $50k API fee is drawn from the $250k dev budget, causing a 20% resource cut that forces scope reduction on the mobile UI, leading to a broken booking flow.
3.  **Integration Latency:** The beachfront partner API documentation is outdated, causing the 4-week integration to bleed into the QA window, forcing a launch delay that misses the peak summer booking surge.

**Stop/Pivot Triggers**

*   **Cost Overrun >10%:** If total projected costs exceed $275k (including the licensing fee), halt development and revert to manual pricing adjustments.
*   **Beta NPS <60:** If the travel agent beta returns a Net Promoter Score below 60, do not launch publicly; pivot to a "concierge" model where agents book via support staff instead of the UI.
*   **Tax Delay >3 Weeks:** If the state tax approval is not finalized within 3 weeks of Phase 1 start, cancel the dynamic pricing engine build and invest solely in the API integration for inventory expansion.
