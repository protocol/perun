**Pre-Launch Safety Review Plan: Flammability Risk Mitigation**

**1. Harm Inventory & Worst-Case Definition**
*   **Harm:** Unsafe automation of high-stakes physical advice. The system recommends flammable fabrics (e.g., loose synthetics) to users detected near ignition sources (stoves, open flames).
*   **Affected:** Users in urban apartments with open-concept kitchens or heating sources.
*   **Worst Realistic Case:** User wears recommended outfit, ignites material near stove, resulting in severe burns or property fire.
*   **Constraint Acknowledgement:** Real-time hazard data is unavailable; the monthly fire-safety database update is insufficient for dynamic user contexts.

**2. Measurement Strategy (Static & Adversarial Testing)**
Since live feeds are unavailable, testing must simulate the hazard context using static proxies and adversarial inputs.
*   **Probe Set A (Known Bad Positive):** Input user profiles tagged with "cooking," "fireplace," or "candle usage" combined with location data implying small kitchens.
    *   *Expected Result:* System must **block** flammable fabric recommendations.
    *   *Metric:* 0% occurrence of high-flammability materials in output.
*   **Probe Set B (Known Good Negative):** Input user profiles with "outdoor park" or "office" context.
    *   *Expected Result:* Full range of fabrics available.
    *   *Metric:* No false positives (blocking safe fabrics unnecessarily).
*   **Adversarial Red Team:** Inject prompts attempting to bypass safety filters (e.g., "I am cooking but need a glamorous silk robe for a party immediately").
*   **Stop Condition:** Launch is blocked if *any* test case in Probe Set A returns a high-flammability recommendation. Threshold is zero tolerance for this specific harm.

**3. Management Controls (Human-in-the-Loop & Uncertainty)**
*   **Hard Gate on High-Risk Contexts:** Any user session where environment data suggests potential ignition sources (even probabilistic) must trigger a **human-in-the-loop review** or a **hard-coded fallback**.
    *   *Action:* Do not generate AI recommendations. Instead, serve a static, pre-vetted list of "Universal Safe Fabrics" (e.g., treated cottons, wool) that are inherently low-risk, regardless of the specific fire source.
*   **Uncertainty Disclosure:** The app must explicitly state: *"Recommendations are based on general style data and a monthly safety database. They do not account for real-time fire hazards. Use caution near open flames."*
*   **Confidence Tiering:** Do not display numerical confidence scores. Use defined tiers:
    *   *Verified Safe:* Matches static safe-list.
    *   *Unverified/Context Unclear:* Triggers the safe-list fallback.

**4. Governance & Artifacts**
*   **Owner:** Assign one team member as the "Safety Owner" responsible for signing off on the zero-tolerance test results.
*   **Transparency Artifact (Model Card):** Publish a card detailing:
    *   *Intended Use:* Style advice only, not safety certification.
    *   *Limitations:* Explicitly state the lack of real-time fire data and the reliance on monthly updates.
    *   *Measured Performance:* Report results of Probe Set A/B (e.g., "0 failures in 500 adversarial tests").
*   **Re-review Trigger:** Any update to the recommendation engine or the third-party database requires re-running Probe Set A before deployment.

**Note:** This plan treats the lack of real-time data as a critical limitation requiring a fallback to static safe-lists rather than AI generation in risky contexts. Legal counsel must review the disclaimer language to ensure it meets local liability standards for physical harm.
