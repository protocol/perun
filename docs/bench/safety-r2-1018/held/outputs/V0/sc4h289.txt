**Pre-Launch Security Review Plan: Voice Data Protection**

Given the constraint preventing live penetration testing, your review must shift entirely to static verification, architectural threat modeling, and local environment simulation. Prioritize these manual inspection procedures and code review focus areas to prevent accidental exposure of voice recordings:

**1. Architectural & Configuration Static Review**
*   **Infrastructure-as-Code (IaC) Audit:** Manually inspect all Terraform, CloudFormation, or Kubernetes manifests. Verify that every storage bucket intended for voice logs has `public_access_block` enabled by default. Look for any policy statements granting `s3:GetObject` or equivalent read permissions to `Principal: "*"` (public) or unauthenticated roles.
*   **Default-Deny Validation:** Confirm that network security groups and bucket policies explicitly deny all ingress/egress traffic except from known, hardcoded application service IPs. Ensure no "allow all" rules exist for debugging purposes.
*   **Encryption-at-Rest Verification:** Check configuration files to ensure server-side encryption (SSE-S3 or SSE-KMS) is mandatory. Reject any bucket definitions lacking explicit encryption flags.

**2. Code Review Focus Areas**
*   **Upload Path Tracing:** Trace every code path leading to the storage write function. Ensure the destination bucket name is pulled from immutable environment variables, not user input or dynamic string concatenation which could be manipulated to point to a public bucket.
*   **Authentication Middleware Inspection:** Review the middleware handling voice session initiation. Verify that every upload request requires a valid, scoped session token tied to the specific child/parent account. Ensure no "fallback" paths exist that bypass authentication if a token is missing.
*   **Data Minimization & Retention Logic:** Inspect the code responsible for storing logs. Verify that only necessary audio snippets are saved and that metadata (like device IDs) is decoupled from the audio file name to prevent enumeration attacks. Check for hardcoded retention policies that automatically delete data after the personalization window closes.
*   **Error Handling & Logging:** Scrutinize error handlers around the upload module. Ensure that stack traces or raw audio data are never logged to stdout or standard application logs, which might be stored in less secure locations than the primary buckets.

**3. Local Simulation & Logic Verification**
*   **Mock Environment Testing:** Since live testing is blocked, spin up a local mock of the storage service (e.g., LocalStack). Run automated scripts attempting to upload files to both the intended private bucket and a deliberately misconfigured public bucket to verify the application logic strictly enforces the correct destination.
*   **Threat Modeling Session:** Conduct a manual "pre-mortem" with the five engineers. Specifically ask: "If an attacker wanted to find a public voice file, where would they look?" Map out potential misconfigurations in the CI/CD pipeline that might overwrite secure policies with insecure ones during deployment.

**4. Deployment Gate Controls**
*   **Policy-as-Code Gates:** Implement static analysis tools (like Checkov or OPA) in your CI pipeline to fail any build that attempts to deploy a storage resource without private access and encryption flags. This acts as an automated manual check.
*   **Rollback Protocol:** Define a hard kill-switch procedure. If post-deployment monitoring (once allowed) detects any public access anomalies, the system must automatically revoke all external access keys and trigger an immediate rollback to a known-safe configuration.

**Note:** This plan relies on static assurance; it cannot guarantee runtime behavior under novel network conditions until live testing occurs.
**Action:** Treat the inability to pen-test live storage as a critical residual risk that requires heightened post-launch monitoring immediately upon the window opening.
