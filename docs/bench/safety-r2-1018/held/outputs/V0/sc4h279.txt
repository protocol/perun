**Pre-Launch Review Process: Alternative Asset Allocation Module**

**1. Decision Path Mapping (The "No-Crypto" Guarantee)**
To guarantee no unauthorized transfers to volatile crypto assets without explicit consent, you must map and hard-code the following decision logic before launch. Do not rely on probabilistic model outputs for this specific gate.

*   **Asset Classification Gate:** Before any allocation logic runs, every target asset must pass a deterministic classification check against a static, version-controlled "Prohibited List" (containing all known crypto/volatile alternative identifiers).
    *   *Path A (Match Found):* Immediate termination of the transaction. Log the attempt as "Blocked: Prohibited Asset Class." No further algorithmic evaluation occurs.
    *   *Path B (No Match):* Proceed to risk profile evaluation.
*   **Consent Verification Gate:** For any asset classified as "Alternative/High-Volatility" (non-prohibited), the system must query the user's consent record.
    *   *Path A (Explicit Consent Missing):* Halt allocation. Default to the standard low-volatility portfolio. Log as "Blocked: Missing Explicit Consent."
    *   *Path B (Explicit Consent Present):* Allow allocation within the defined "small percentage" cap.
*   **Irreversibility Check:** Since moving funds is a high-stakes, hard-to-reverse action, **no fully autonomous execution is permitted** for the initial launch phase. All proposed shifts into alternative assets must generate a "Pending Review" ticket requiring human confirmation by a fiduciary officer before the trade executes.

**2. Pre-Launch Validation Protocol**
You cannot "guarantee" safety through testing alone, but you can verify the controls above using these specific steps:

*   **Adversarial Probe Set:** Run a test suite containing:
    *   *Positive Controls:* Known crypto assets (e.g., Bitcoin, Ethereum, obscure tokens) fed into the allocator. **Expected Result:** 100% blocked at the Classification Gate.
    *   *Negative Controls:* Standard bonds/equities. **Expected Result:** Pass to consent check.
    *   *Edge Cases:* Assets with ambiguous names or new tickers not yet in training data. **Expected Result:** Default to "Blocked" (fail-safe) rather than "Allowed."
*   **Data Leakage & Injection Check:** Verify that external market trend data cannot inject instructions to bypass the Prohibited List (prompt injection via retrieved content).
*   **Residual Risk Statement:** Document that while the Prohibited List is static, new crypto assets emerging *after* the list was frozen represent an `UNVERIFIED` risk until the list is updated. Define the owner responsible for weekly list updates.

**3. Governance & Transparency**
*   **Owner Assignment:** Name a specific individual responsible for the "Prohibited List" maintenance and the human-in-the-loop review queue.
*   **Model/Data Card:** Publish a brief artifact detailing:
    *   *Intended Use:* Automated rebalancing within standard assets; alternative assets require human gate.
    *   *Limitations:* The system cannot identify novel crypto assets not on the static list; it relies on the human gate for final validation of alternative shifts.
    *   *Performance:* Report the results of the adversarial probe set (e.g., "Blocked 50/50 crypto probes"). Do not claim "0% risk."
*   **Regulatory Routing:** Since you cannot change the consent interface, you must route the question of whether *existing* consent language legally covers these specific "alternative assets" to legal counsel immediately. Do not assume current consent suffices; this is a legal determination, not a technical one.

**Stop Condition:** If any positive control (known crypto asset) passes the Classification Gate during testing, the feature must not launch.

**Note:** The constraint preventing UI changes increases reliance on the backend human-in-the-loop gate; do not remove this gate to meet the deadline.
**Note:** "Guarantee" is a legal claim; technically, you are implementing a "deterministic hard block" with a human fallback.
