# Safety Evaluation Plan: Accessible Hiring Game Assessment

## 1. Objective
Identify motion-based barriers in the current webcam-driven assessment that disproportionately exclude candidates with physical disabilities, and validate alternative input pathways using only existing standard hardware (webcam/keyboards) to ensure equitable evaluation of problem-solving skills.

## 2. Scope & Constraints
- **In Scope:** Beta game logic, webcam motion thresholds, keyboard fallback mechanisms, scoring fairness.
- **Out of Scope:** Purchasing new hardware (eye-trackers, specialized controllers), modifying the core problem-solving challenges themselves.
- **Constraint:** Must utilize only standard webcams and keyboards already deployed.

## 3. Methodology

### Phase A: Barrier Identification (Static & Heuristic)
Since live testing with diverse disabilities requires specific recruitment not yet confirmed, begin with a heuristic audit of the code and logic:
1.  **Motion Threshold Analysis:** Review the sensitivity settings for motion detection. Identify specific gestures (e.g., "wave hand," "turn head") that require fine motor control or large ranges of motion.
2.  **Time-Pressure Dependency:** Determine if success relies on speed of movement rather than the correctness of the solution. Fast-twitch requirements often exclude candidates with mobility impairments.
3.  **False Negative Simulation:** Simulate limited mobility by restricting your own movement range during testing (e.g., keeping elbows pinned, limiting head rotation) to see if the system fails to register valid intent.

### Phase B: Alternative Pathway Validation
Develop and test two distinct alternative input modes using existing hardware:
1.  **Keyboard-Only Mode:** Map all motion-based actions to specific key presses (e.g., Arrow Keys for direction, Spacebar for selection). Ensure the game state advances identically whether triggered by motion or keystroke.
2.  **Static Webcam Mode:** For candidates who cannot move but can hold a pose, adjust the algorithm to detect "presence" or static positioning rather than dynamic movement, or allow extended time limits for slow movements.

### Phase C: Fairness Verification
1.  **Score Parity Check:** Run identical problem-solving scenarios using both motion and keyboard inputs. Verify that the scoring algorithm weights the *outcome* of the decision, not the *method* of input.
2.  **Error Rate Comparison:** Measure false rejection rates for simulated low-mobility inputs against standard inputs. A significant disparity indicates a biased threshold.

## 4. Deliverables
- **Barrier Report:** A list of specific game mechanics that fail under low-mobility conditions.
- **Configuration Profiles:** Two new preset configurations for the game engine: "Standard Motion" and "Accessibility Mode" (keyboard/static optimized).
- **Validation Matrix:** A table showing pass/fail rates for both input methods across all beta challenges, proving score equivalence.

## 5. Success Criteria
- Candidates with limited mobility can complete 100% of the assessment using keyboard alternatives.
- Scoring variance between input methods is less than 5%.
- No candidate is rejected solely due to an inability to perform specific physical gestures.

*Note: This plan relies on logical audit and simulated constraint testing; actual validation with disabled users is recommended before full launch.*
*Ensure "Accessibility Mode" is explicitly offered to candidates during the invitation phase.*
