### Pre-Launch Safety Review Process for Milano StyleTech

Given the constraint of non-real-time fire safety data, your review process must shift from dynamic hazard detection to **static environmental profiling** and **conservative recommendation logic**. The goal is to create a "safe-by-default" system that assumes risk in ambiguous situations rather than relying on live feeds to confirm it.

**1. Implement Static Environmental Risk Profiling**
Since you cannot detect active flames in real-time, you must categorize user environments based on static data points available at onboarding or profile setup.
*   **Housing Type Classification:** Require users to specify their living situation (e.g., "Studio with open kitchen," "House with fireplace," "Apartment with gas stove").
*   **High-Risk Tagging:** Flag any profile containing keywords like "gas," "open flame," "fireplace," or "wood stove" as a **High-Risk Environment**.
*   **Default Assumption:** If a user's environment data is missing or vague, the system must default to the High-Risk classification. Do not recommend potentially flammable materials unless the environment is explicitly confirmed as low-risk.

**2. Establish a "Flammability Filter" Logic Layer**
Insert a mandatory filtering step between the recommendation engine and the user interface. This layer operates independently of the monthly fire-safety database update.
*   **Material Whitelisting/Blacklisting:** Create a hard-coded internal list of fabrics categorized by flammability (e.g., loose-weave synthetics, untreated cotton vs. wool, treated fabrics).
*   **Contextual Blocking:** Configure the logic so that if a user is tagged as **High-Risk Environment**, the engine is physically incapable of selecting items from the "High Flammability" category, regardless of style match scores.
*   **The "Uncertainty Principle":** If the fire-safety database is outdated (e.g., 29 days old), the system should treat the data as "unverified" and apply stricter filtering thresholds than when the data is fresh.

**3. Conduct Scenario-Based "Tabletop" Testing**
Before launch, run a manual review session using synthetic user profiles that represent edge cases your live data might miss.
*   **Create "Trap" Profiles:** Generate test accounts with conflicting data (e.g., user claims "no stove" but lives in a building known for gas heating) to ensure the conservative default triggers correctly.
*   **Stress Test the Monthly Lag:** Simulate the system state just before a database update. Verify that recommendations made on Day 29 are safer than those made on Day 1, compensating for data staleness with increased caution.
*   **Manual Audit of Top Recommendations:** For the first two weeks post-launch, manually audit the top 5% of recommendations generated for users in urban apartments to ensure no high-risk fabrics slip through due to algorithmic optimization for style over safety.

**4. User-Facing Disclaimers and Feedback Loops**
Mitigate liability and gather real-world data to refine your static models.
*   **Static Warnings:** Append a permanent disclaimer to all recommendations: *"Style suggestions are based on general safety guidelines. Always exercise caution near open flames regardless of fabric type."*
*   **User Reporting:** Add a "Report Unsafe Suggestion" button. Use this feedback to manually blacklist specific fabric-style combinations that users flag, updating your internal static list immediately without waiting for the third-party database.

By relying on conservative static profiling and hard-coded material filters, you remove the dependency on real-time hazard detection while maintaining a robust safety posture for your holiday launch.

*Note: This process relies on logical constraints rather than live data feeds. Ensure your legal team reviews the specific wording of user disclaimers.*
