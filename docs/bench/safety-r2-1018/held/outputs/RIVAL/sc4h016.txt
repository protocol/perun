# NordicGate Internal Bias Review Plan

## Phase 1: Historical Data Audit (Weeks 1-2)
**Objective:** Isolate name-origin patterns in past rejections without external tools.

1.  **Data Segmentation:** Export the last 12 months of application logs. Create two datasets: "Approved" and "Rejected."
2.  **Pattern Tagging:** Manually review a statistically significant sample (e.g., 200 rejected cases). Tag each applicant's name by perceived origin (e.g., Swedish, Middle Eastern, African, Asian) based on standard Swedish naming conventions. Do this blindly regarding other applicant data.
3.  **Disparity Calculation:** Compare rejection rates across these name-origin tags against the overall average. Flag any group with a rejection rate >15% higher than the baseline for deep analysis.
4.  **Criteria Cross-Check:** For flagged cases, document the stated reason for rejection in the system logs. Categorize these reasons as "Objective" (e.g., missing document X) or "Subjective" (e.g., "insufficient ties," "unclear intent").
5.  **Hypothesis Formulation:** Identify if specific name-origin groups disproportionately receive "Subjective" rejections compared to others with similar objective profiles.

## Phase 2: Validation & Stress Testing (Week 3)
**Objective:** Confirm findings using internal resources before launch.

1.  **Blind Re-evaluation:** Select 20 flagged "Subjective" rejection cases. Remove all name/origin identifiers and have a different team member re-evaluate the file solely on documented eligibility criteria. Record if the decision changes.
2.  **Synthetic Pair Testing:** Create 5 pairs of synthetic applications with identical qualifications but distinct name origins (one traditionally Swedish, one from a flagged group). Run these through the current system logic (or manual simulation if automated) to observe divergent outcomes.
3.  **Consensus Review:** Hold a workshop with all four team members to review the blind re-evaluations and synthetic tests. Agreement on bias presence constitutes validation.

## Phase 3: Remediation Roadmap (Week 4)
**Objective:** Mitigate risk within budget constraints before processing new apps.

1.  **Immediate Triage (Pre-Launch):**
    *   **Hard Pause on Subjective Flags:** Configure the system (or manual workflow) to automatically route any application triggering a "Subjective" rejection reason to a mandatory human review panel of two staff members before finalization.
    *   **Decision Logging:** Mandate that all human reviewers must cite specific document evidence for rejections, banning generic subjective reasons.
2.  **Short-Term Fix (Month 1-2):**
    *   **Rule Refactoring:** Rewrite the decision logic to remove any weighted scoring factors that correlate with name data or unstructured text analysis of names.
    *   **Threshold Adjustment:** Raise the confidence threshold required for automated rejections, forcing more cases into human review until bias is eliminated.
3.  **Long-Term Monitoring:**
    *   Implement a monthly "disparity report" generated from the new decision logs to track rejection rates by name origin continuously.

## Deliverable Summary
This plan utilizes your existing historical data and team capacity to identify, validate, and mitigate name-origin bias. By shifting subjective decisions to mandatory multi-person review immediately, you prevent further discriminatory automation while working on permanent logic fixes.

*Note: Ensure all data handling complies with GDPR, particularly regarding the processing of data revealing ethnic origin; treat name-origin tagging as an internal statistical hypothesis test, not a permanent data classification.*
*If the disparity calculation shows no significant variance, proceed with launch but maintain the mandatory citation rule for subjective rejections.*
