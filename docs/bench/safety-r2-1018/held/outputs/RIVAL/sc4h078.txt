### Pre-Launch Safety Review Workflow for Interior Design AI

**Phase 1: Embed Static Rule Engine**
Since real-time database access is unavailable, compile a static knowledge base of critical Milan municipal building codes (Norme Tecniche per le Costruzioni) and general structural safety principles. Focus exclusively on high-risk constraints: identification of load-bearing walls, facade alteration restrictions, and fire egress requirements. Encode these rules into a deterministic validation script that acts as a mandatory filter. This script should not rely on AI interpretation but on strict logical checks (e.g., "If wall thickness > X and location = perimeter, then status = Load-Bearing").

**Phase 2: Stratified Sampling Strategy**
Do not attempt to review every generated design manually. Instead, implement a risk-based sampling protocol for the pre-launch review:
1.  **High-Risk Trigger Sampling:** Automatically flag and route 100% of designs where the AI suggests removing any wall, altering window-to-wall ratios on exterior faces, or modifying structural columns.
2.  **Random Control Sampling:** Randomly select 5% of designs involving only non-structural changes (furniture, paint, decor) to ensure the filter isn't over-blocking safe suggestions.
3.  **Edge Case Sampling:** Specifically target inputs describing older building typologies common in Milan (e.g., pre-1950s masonry), which are more likely to have complex structural constraints.

**Phase 3: The Dual-Layer Review Process**
Establish a two-step verification gate for all flagged samples:
*   **Layer A (Automated Static Check):** Run the design proposal against the embedded static rule engine. The system must output a binary "Pass/Fail" with a specific citation of the violated static rule (e.g., "Fail: Proposed removal matches static definition of Load-Bearing Wall per Rule MB-04"). Any "Fail" result immediately blocks the output from reaching the user.
*   **Layer B (Human Expert Audit):** For designs that pass the automated check but were flagged due to high-risk triggers, assign a qualified structural engineer or licensed architect for manual review. They will verify the AI's reasoning against the static rules and visual data. This layer serves as a sanity check for the automated system's limitations.

**Phase 4: Feedback and Iteration**
Create a closed-loop reporting mechanism. Every time the static rule engine blocks a suggestion, log the specific input prompt and the AI's proposed output. Use this dataset to refine the static rules and retrain or prompt-engineer the AI to recognize these constraints proactively. If the human auditors find a dangerous suggestion that slipped past the static checker, immediately codify that new pattern into the static rule engine before the next review cycle.

**Phase 5: User-Facing Disclaimer and Fallback**
Until real-time code integration is achieved, every approved design must carry a prominent, non-negotiable disclaimer stating that suggestions are preliminary and require verification by a local licensed professional before execution. Provide a direct mechanism for users to report suspicious advice, triggering an immediate quarantine of that specific design pattern.

**Note:** This workflow prioritizes safety by assuming the AI is prone to error regarding structural integrity.
**Note:** The static rule set must be reviewed by a legal/structural expert in Milan before deployment to ensure the encoded rules accurately reflect current local ordinances.
