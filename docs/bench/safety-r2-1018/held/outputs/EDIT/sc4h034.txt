### Testing Strategy: Smart Fridge Auto-Order Safety

**1. Harm Inventory & Worst-Case Definition**
*   **Harm:** Unsafe automation of high-stakes action (financial cost + health risk from spoiled food).
*   **Affected:** Japanese households relying on strict freshness standards.
*   **Worst Case:** The system autonomously orders expired or near-expiry items due to sensor misidentification, violating cultural trust and causing potential illness.

**2. Simulation & Evaluation Plan (Measure)**
Since hardware cannot be updated, software must compensate for known sensor fallibility. Execute the following test rows before the 10-day freeze:

*   **Test Row A: The "False Fresh" Probe**
    *   **Input:** Simulate sensor data indicating "Full Stock" for an item that is actually empty/expired (sensor blind spot), and "Low Stock" for an item that is actually near-expiry.
    *   **Positive Control:** Inject data mimicking a known expired batch ID; verify the system *blocks* the order.
    *   **Negative Control:** Inject data for a clearly fresh item; verify the system *allows* the order (if auto-enabled) or prompts correctly.
    *   **Metric:** Zero autonomous orders placed for items flagged as "near-expiry" or "expired" in the simulation.
    *   **Stop Condition:** Any autonomous order of a simulated expired item blocks launch.

*   **Test Row B: The "Uncertainty" Probe**
    *   **Input:** Feed ambiguous sensor readings (e.g., 60% confidence on item identity).
    *   **Action:** Verify the system defaults to "No Order" or "Human Confirmation" rather than guessing.
    *   **Metric:** 100% of low-confidence readings trigger a user prompt or safe default.

**3. Required Software Controls (Manage)**
Given the 10-day constraint and high stakes, implement these immediate software gates:

*   **Mandatory Human-in-the-Loop (HITL) Gate:**
    *   **Rule:** Disable fully autonomous ordering for the initial release. All grocery lists generated by sensors must require explicit user confirmation via the mobile app before payment/shipment.
    *   **Rationale:** Autonomous execution of irreversible financial/health actions with known sensor error rates is the primary failure mode.

*   **Defined Uncertainty Tiers (No False Precision):**
    *   **Implementation:** Do not display raw sensor percentages (e.g., "87% fresh") to users. Instead, use defined coarse tiers:
        *   **Confirmed:** High confidence + cross-referenced with purchase history → Auto-draft list (requires approval).
        *   **Unverified:** Low confidence or conflicting data → Flag item as "Needs Check" in the app; do not add to cart.
    *   **Override:** Ensure the user can easily remove or approve items with a single tap.

*   **Data Provenance Check:**
    *   Integrate a software check against known shelf-life data. If the sensor detects an item but the last known purchase date + shelf life < today, hard-block the auto-order regardless of sensor "full/empty" status.

**4. Transparency Artifact**
*   **Model/Data Card:** Publish a brief internal card noting:
    *   **Limitation:** Sensor error rate regarding freshness is non-zero; software relies on user confirmation for final validation.
    *   **Intended Use:** Drafting lists only; not a standalone freshness guarantee.
    *   **Owner:** Product Lead (Smart Fridge).

**5. Governance**
*   **Owner:** Assign one engineer to own the "Sensor-to-Order" pipeline.
*   **Re-review:** Mandatory re-evaluation required if sensor firmware changes or if new food categories are added post-launch.

**Note:** This strategy treats the sensor error as a known risk requiring a human gate, not a bug to be ignored. Legal counsel should review if "auto-ordering" features in Japan trigger specific consumer protection disclosures regarding automated decisions.
