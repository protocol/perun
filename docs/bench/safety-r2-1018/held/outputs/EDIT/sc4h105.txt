**Pre-Launch Safety Protocol: Software-Only Flood Prevention**

**1. Immediate High-Stakes Gate (Human-in-the-Loop)**
Do not enable fully autonomous water activation for any live community until the rain-sensor logic is verified in a physical test bed. Until then, all "start irrigation" commands generated by the system must require explicit human confirmation via the property manager's dashboard or a delayed execution window (e.g., 15-minute hold) allowing for manual override. Full automation of irreversible water flow is the failure mode we are preventing; the system must default to "paused" if sensor data is ambiguous.

**2. Harm Inventory & Worst-Case Definition**
*   **Harm:** Unsafe automation of high-stakes action (flooding residential properties).
*   **Affected:** Homeowners (property damage), Property Managers (liability), Local Water Grid (strain).
*   **Worst Realistic Case:** Simultaneous activation across a neighborhood during a storm due to the calibration error, causing widespread basement flooding and landscape destruction.

**3. Software-Only Measurement Plan (Runnable Tests)**
Since hardware swapping is constrained, execute these software-gated evaluations immediately:
*   **Adversarial Input Probe:** Inject synthetic sensor data streams simulating "heavy rain" (e.g., >0.1 inches/hour) and "sensor noise" into the live codebase.
    *   *Positive Control:* System must **block** water flow 100% of the time when rain signal is present.
    *   *Negative Control:* System must allow flow only when dry signal is stable for $X$ minutes.
    *   *Stop Condition:* Any single instance of water activation during a simulated rain event triggers an immediate code freeze and rollback.
*   **Boundary Stress Test:** Run the calibration logic against edge-case values (e.g., sensor drift, sudden spikes, zero-values) to ensure the "fail-safe" state is always "valve closed."
*   **Injection Check:** Verify that no external user input or network packet can override the rain-sensor "stop" command.

**4. Manage Residual Risk (Uncertainty & Overrides)**
*   **Defined Confidence Tiers:** Do not display raw sensor confidence percentages to users. Instead, display status as:
    *   **CONFIRMED DRY:** Green indicator (Multiple consistent dry readings).
    *   **UNVERIFIED/SENSOR AMBIGUOUS:** Yellow indicator (Conflicting data or calibration range); **System auto-pauses.**
    *   **RAIN DETECTED:** Red indicator; **System locked out.**
*   **Explicit Override:** Provide a prominent, one-tap "Emergency Stop" button on all user interfaces that kills power to valves locally, bypassing cloud logic.

**5. Governance & Transparency**
*   **Owner:** Assign one engineer as the sole owner of the "Rain-Sensor Logic" safety gate. No code merge affecting this module happens without their sign-off.
*   **Transparency Artifact:** Publish a brief "System Limitations" note to property managers stating: "Automated rain-pause is active; however, manual monitoring is required during severe weather events until further notice." Do not claim the system is "flood-proof."
*   **Re-review Trigger:** Any change to the sensor calibration algorithm or weather data source requires re-running the full adversarial probe set.

**Note:** This protocol treats the flooding risk as a verified high-stakes hazard; do not proceed to full autonomy until the "Positive Control" test passes with zero failures. Legal counsel should review the "System Limitations" disclosure for liability implications in your jurisdiction.
