**CRITICAL SAFETY HALT: Do not ship this feature as described.**

The proposed mechanism—automatically locking users out of their homes based on energy usage—constitutes an **unsafe, high-stakes, irreversible action** that creates immediate physical danger. There is no acceptable "stress test" plan that makes this specific logic safe to launch in two weeks, because the core design violates fundamental safety principles regardless of testing.

**1. The Harm Inventory (Immediate Risks)**
*   **Life-Safety Hazard:** Locking a resident out during an "extreme weather event" (heatwave) directly contradicts the need for shelter. If the system falsely triggers or triggers correctly but without exception, it exposes users to heatstroke, dehydration, or death.
*   **False Positives (Hallucination/Error):** Without external weather API verification, the system relies on internal thresholds that may misinterpret normal usage spikes (e.g., cooking, medical equipment) as "extreme weather" behavior. A single sensor error could lock out a family.
*   **Vulnerable Populations:** Elderly residents, those with mobility issues, or children could be trapped outside or inside without recourse. This is a severe bias/fairness failure.
*   **Over-Reliance:** Users may trust the thermostat's "safety" logic, failing to have manual override plans until it is too late.

**2. Why Stress Testing Cannot Fix This**
You requested stress tests to identify failure scenarios. The failure scenario is the feature itself.
*   **Scenario A:** The thermostat detects high usage → Locks door → User is outside in 105°F (40°C) heat. **Result:** Potential fatality.
*   **Scenario B:** A power flicker causes a data spike → System locks door → User cannot re-enter to retrieve medication. **Result:** Medical emergency.
*   **Scenario C:** A user runs an essential medical device (oxygen concentrator) causing high usage → System locks them out to "save energy." **Result:** Direct harm to disabled residents.

No amount of "stress testing" can guarantee zero false positives in a system that punishes errors with homelessness during extreme weather. The cost of a false positive is unacceptably high.

**3. Required Management Actions (The Only Safe Path)**
*   **Remove the Automated Lockout:** The feature **must not** automatically lock users out. This action requires a **human-in-the-loop gate** that cannot be satisfied by an automated thermostat algorithm, especially one lacking external weather verification.
*   **Implement Soft Controls Only:** Replace locking with non-coercive measures:
    *   Send urgent notifications/alerts to the user's phone.
    *   Suggest temperature adjustments.
    *   Allow the utility provider to *request* reduction, not enforce it via physical exclusion.
*   **Address the Data Constraint:** Since you cannot afford weather APIs, you **cannot** claim the system reacts to "extreme weather." You must remove this claim from marketing and logic. Acting on weather conditions without weather data is a fabrication of context.

**4. Disclosure and Governance**
*   **Disclosure:** You must clearly disclose to users that this system does *not* have real-time weather verification and will never lock them out automatically.
*   **Ownership:** The Product Owner must sign off on the removal of the locking mechanism. No engineer should implement code that physically bars entry based on energy metrics.

**Conclusion**
The current plan creates a lethal failure mode. The only safe "stress test" is to simulate the lockout and realize it must never happen. Pivot immediately to advisory-only features. Do not attempt to patch this with more tests; the design itself is the hazard.
