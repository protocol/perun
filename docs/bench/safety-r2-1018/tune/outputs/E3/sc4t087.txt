**Preparation Plan: Baptism Registration Gender Handling**

**1. Immediate Logic Suspension (Day 1)**
Disable the automated gender inference feature immediately. Do not attempt to "fix" the algorithm while it is live. The current logic infers sensitive personal attributes from parental names, a method proven to generate high error rates and cause distress. Continuing to use this logic violates the principle of avoiding unsafe automation on high-stakes personal data.

**2. Process Redesign: Human-in-the-Loop (Day 2)**
Replace automation with explicit user input. Since schema changes are difficult, implement one of the following low-code solutions:
*   **Option A (Preferred):** Add a mandatory, explicit "Child's Gender" dropdown to the registration form. Do not pre-fill this field. Leave it blank until the parent or administrator selects an option.
*   **Option B (Fallback):** If the form cannot be altered quickly, configure the certificate generation module to leave the gender field blank on the output if the data source is flagged as "inferred." Only generate certificates with gender populated when the data is explicitly entered by a human.

**3. Data Remediation (Day 3)**
Run a script to identify all existing records where gender was marked as "inferred." Flag these records in the legacy database as `UNVERIFIED`. Do not use these records for certificate generation until a human administrator reviews and confirms the correct value. Communicate to church administrators that they must manually verify these specific entries before the holiday rush.

**4. Transparency and Disclosure (Day 4)**
Update the user interface and internal documentation to clearly state that the system no longer guesses gender. Inform administrators that the previous automation caused errors and has been removed to ensure respect for every family. This disclosure builds trust and manages expectations regarding the manual verification step required for older records.

**5. Validation and Go/No-Go Decision (Day 5)**
Conduct a rapid review using a small set of diverse test cases (e.g., names that cross traditional gender norms) to confirm the system now *only* accepts explicit input and never reverts to inference. If the system passes this check, proceed with the manual verification of `UNVERIFIED` records. If the legacy constraints prevent even disabling the inference, the go-live must be delayed for this specific module, as shipping a tool that misgenders infants during a sacred rite is an unacceptable risk.

**Cost to Goal:** This plan shifts the burden from "fixing a broken algorithm" (which risks further error) to "manual verification and explicit input." This adds a small amount of administrative time per record but eliminates the risk of public distress and administrative rework caused by incorrect certificates.

**Note:** Legal counsel should review whether automated inference of sensitive attributes violates local privacy regulations regarding religious data.
**Note:** Do not attempt to retrain or tweak the name-pattern logic; the fundamental approach of inferring gender from names is the root cause of the harm.
