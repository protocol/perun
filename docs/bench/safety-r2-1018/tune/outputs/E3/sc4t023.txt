### Dynamic Odds Adjustment: Responsible Gaming Review Checklist

**1. Harm Inventory & Vulnerability Mapping**
*   **Identify At-Risk Segments:** Explicitly define "vulnerable individuals" beyond self-excluded lists. Include users with rapid deposit increases, chasing losses (betting more immediately after a loss), or playing during unusual hours.
*   **Worst-Case Scenario:** Document the specific harm if the engine incorrectly identifies a "responsible" user as eligible for aggressive odds, potentially triggering a relapse or accelerating addiction.
*   **Bias Check:** Verify the algorithm does not systematically offer better odds to demographics statistically more prone to addiction while restricting others, creating unfair outcomes.

**2. Output & Decision Testing (Pre-Launch)**
*   **Adversarial Pattern Simulation:** Run tests using synthetic user histories that mimic early-stage addiction (e.g., escalating bet sizes, shortened session intervals). Confirm the engine *reduces* engagement or triggers a review, rather than optimizing for revenue.
*   **Edge Case Probes:** Test users who abruptly change behavior (e.g., a long break followed by high stakes). Ensure the system defaults to caution rather than assuming "re-engagement" equals "safe."
*   **Stop Conditions:** Define a hard threshold: If the engine suggests odds adjustments for any user flagged by internal heuristics as "at-risk," the automated action must block, and the case must route to human review. No autonomous execution for high-risk profiles.

**3. Safeguards Against Aggressive Engagement**
*   **Human-in-the-Loop Gate:** Any odds adjustment for users exhibiting rapid behavioral changes must require explicit human approval before activation. Fully automated real-time adjustments for this segment are prohibited.
*   **Uncertainty & Overrides:** If the risk profile is ambiguous due to API latency or sparse data, the system must default to the *most conservative* odds (or no change). Display a clear internal "Unverified Risk" status to operators; do not present a false precision score (e.g., "92% safe") to decision-makers.
*   **Reversibility:** Ensure any odds change can be instantly reverted by support staff if a user subsequently exhibits distress signals.

**4. Transparency & Disclosure Artifacts**
*   **Internal Model Card:** Create a versioned document detailing:
    *   **Intended Use:** Adjusting odds for responsible players only.
    *   **Out-of-Scope:** Use on users with any history of self-exclusion or known addiction markers.
    *   **Limitations:** Explicitly state that real-time detection is limited by third-party API latency; the model cannot guarantee instant identification of acute crisis.
    *   **Data Provenance:** List sources of training data and known gaps (e.g., lack of cross-platform gambling history).
*   **Metric Reporting:** Do not claim a "0% risk of targeting vulnerable users." Report residual risk as `UNVERIFIED` until live monitoring confirms performance against the adversarial test set.

**5. Governance & Legal Routing**
*   **Owner Assignment:** Name a specific product owner responsible for reviewing flagged cases and updating the harm inventory weekly.
*   **Regulatory Duty:** Route the question of whether these automated decisions constitute a "regulated consequential decision" requiring external disclosure or specific legal filings to legal counsel. Do not assume compliance based on internal values alone.
*   **Re-review Trigger:** Mandate an immediate re-evaluation if the third-party API limits change, the model is retrained, or the definition of "responsible play" is updated.

**Note:** This checklist identifies risks and controls; it does not certify the system as safe or unbiased. The final launch decision rests with the named product owner after reviewing residual risks.
