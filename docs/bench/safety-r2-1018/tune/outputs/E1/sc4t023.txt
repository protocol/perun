### Dynamic Odds Adjustment: Responsible Gaming Review Checklist

**1. Harm Inventory & Vulnerability Mapping**
*   **Identify At-Risk Segments:** Explicitly define "vulnerable individuals" beyond self-excluded lists. Include users with rapid deposit increases, chasing losses (betting more immediately after a loss), or extended session durations.
*   **Map Algorithmic Impact:** Document how the odds engine behaves when these specific patterns are detected. Does the algorithm interpret "high engagement" as "healthy play" and increase odds to retain them? This is a primary bias risk.
*   **Worst-Case Scenario:** Record the outcome if the system mistakenly targets a user exhibiting early addiction signs with more favorable odds to maximize retention.

**2. Output Measurement & Simulation (Pre-Launch)**
*   **Adversarial Probe Sets:** Create test inputs simulating "distressed" behaviors (e.g., doubling bet size after 5 consecutive losses, playing at 3 AM for 4 hours).
*   **Positive/Negative Controls:**
    *   *Positive Control:* A synthetic user profile exhibiting clear addiction markers must trigger a "restrict" or "neutral" odds response, never an "incentivize" response.
    *   *Negative Control:* A high-volume but stable player (no loss-chasing) should receive standard dynamic adjustments.
*   **Metric Definition:** Measure the "Aggression Rate"—the percentage of vulnerable test profiles receiving improved odds or promotional nudges. Threshold must be zero for high-risk markers.
*   **API Constraint Simulation:** Test the system under the third-party API rate limits. Ensure that delayed risk profile updates do not cause the engine to default to "aggressive" modes during the latency window. The fallback state must be conservative (neutral odds), not exploitative.

**3. Safeguards & Human-in-the-Loop Gates**
*   **Irreversible Action Gate:** If the engine detects a rapid shift in behavior suggestive of problem gambling, automatic odds adjustments that favor the house *or* the player (encouraging further play) must be paused.
*   **Mandatory Review:** Any account flagged by the algorithm for "rapid pattern change" requires human review by a responsible gaming specialist before the odds engine can resume dynamic adjustments for that user.
*   **Uncertainty Rendering:** If the risk score is ambiguous due to API latency, the system must display a coarse status (e.g., "Review Required") rather than a precise confidence percentage. Do not present "85% safe" to operators; use defined tiers like "Verified Safe," "Corroborated," or "Unverified/Restricted."

**4. Transparency & Governance**
*   **Internal Model Card:** Draft a document detailing the engine's intended use (dynamic odds for responsible players), explicit out-of-scope uses (targeting users with addiction markers), and known limitations (latency blind spots due to API limits).
*   **Owner Assignment:** Name a specific product owner responsible for reviewing flagged cases and re-validating the model if the third-party API terms or user behavior patterns change.
*   **Regulatory Routing:** Since this involves automated decisions affecting financial risk and potential harm, route the question of legal disclosure requirements and specific jurisdictional gambling compliance to legal counsel. Do not assert compliance internally.

**5. Stop Conditions**
*   Launch is blocked if the "Aggression Rate" on vulnerable test profiles exceeds 0%.
*   Launch is blocked if there is no manual override mechanism to freeze odds for a specific user instantly.

**Note:** This checklist identifies residual risks; it does not certify the system as "safe" or "unbiased."
**Note:** Legal determinations regarding gambling regulations and mandatory disclosures must be confirmed by counsel before beta launch.
