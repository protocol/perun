# Pre-Launch Equity Assessment Plan: Geographic Filtering Mitigation

**Objective:** Identify and mitigate exclusionary effects of zip-code filtering within 10 days without modifying the core matching engine.

### Phase 1: Rapid Boundary Audit (Days 1–2)
*   **Data Overlay Analysis:** Map current "eligible" zip codes against external demographic datasets (e.g., census poverty rates, school district funding levels). Identify high-need areas currently excluded by hard boundary lines.
*   **Edge Case Sampling:** Manually test profiles of students living on the immediate borders of excluded/included zones to quantify "cliff effects" where minor address differences cause total disqualification.
*   **Historical Review:** Analyze past cycle data (if available) to identify patterns of rejection correlated with specific neighborhoods rather than individual merit.

### Phase 2: Mitigation Strategy Selection (Days 3–4)
Select one or more non-invasive interventions that bypass core logic changes:
*   **Override Allowlist:** Create a static configuration file of specific excluded zip codes or census tracts to be manually force-included before the matching run. This requires no engine logic change, only data injection.
*   **Radius Expansion Logic:** If the engine supports it, adjust the input parameter to expand the search radius by a fixed percentage (e.g., +15%) for users in borderline zones, effectively blurring the hard edge.
*   **Secondary Review Queue:** Route all applications from excluded high-need zones (identified in Phase 1) to a manual review track. These applications bypass the automated filter and are evaluated by human reviewers using the same criteria the algorithm would have used.

### Phase 3: Validation & Stress Testing (Days 5–7)
*   **Synthetic Profile Testing:** Generate 50–100 synthetic student profiles distributed across identified bias hotspots. Run them through the system with the proposed mitigation active to verify inclusion rates improve without triggering system errors.
*   **False Positive Check:** Ensure the mitigation does not inadvertently include clearly ineligible candidates (e.g., outside the geographic service area entirely), which could strain financial resources.
*   **Load Simulation:** Verify that the manual review queue or override list does not create a processing bottleneck that threatens the 10-day deadline.

### Phase 4: Deployment & Monitoring (Days 8–10)
*   **Staged Rollout:** Activate the mitigation for a small subset of users (e.g., one specific region) for 24 hours to monitor system stability.
*   **Full Activation:** Deploy the allowlist or routing rule to production.
*   **Real-Time Dashboard:** Establish a simple hourly count of applications processed vs. manually routed. Set an alert threshold if manual queue volume exceeds team capacity.
*   **Documentation:** Record the specific zip codes overridden and the rationale for future audit trails, ensuring transparency regarding the temporary equity fix.

### Required Resources
*   **Data:** Current eligible zip code list, external demographic maps.
*   **Personnel:** 2 developers for data prep/testing, 2 reviewers for manual queue (if selected), 1 project lead for decision authority.
*   **Access:** Read-access to application logs and write-access to configuration/allowlist files.

This plan prioritizes speed and stability by treating the bias as a data configuration issue rather than a code logic issue, ensuring eligible students are not excluded while meeting the strict deadline.

*Note: This plan assumes the ability to inject data overrides or route traffic externally; if the system is completely locked down, only the manual review queue option remains viable.*
