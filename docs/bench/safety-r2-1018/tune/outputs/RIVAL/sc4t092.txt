**Validation Plan: Image Evidence Integrity for Disaster Adjuster**

**Objective**
Verify that the decision engine processes all uploaded visual evidence categories without omission or bias, ensuring financial outcomes reflect the totality of submitted proof within the single allowed simulation.

**1. Evidence Taxonomy & Baseline Definition**
Before the simulation, define the mandatory "Evidence Taxonomy" based on policy rules. This list serves as the ground truth for what the model *must* see.
*   **Categories:** Structural damage, water intrusion, personal property loss, temporary repairs, and pre-existing conditions.
*   **Baseline Dataset:** Construct a single, curated "Golden Set" of 50 claim files. Each file must contain a controlled mix of images covering every taxonomy category, including edge cases (e.g., obscured damage, night-time photos, mixed debris).
*   **Expected Output Matrix:** For each file in the Golden Set, manually pre-calculate the required payout components if every image type were correctly identified. This creates the deterministic benchmark for the one-time run.

**2. Simulation Input Design (The "Stress Test" Packet)**
Since only one full simulation is permitted, the input data must be designed to force the model to confront every evidence type simultaneously.
*   **Composite Claims:** Do not test categories in isolation. Create composite claims where high-value structural damage is paired with subtle but critical evidence (e.g., mold growth or electrical hazards) that algorithms often discard as noise.
*   **Adversarial Formatting:** Include images with varying resolutions, lighting conditions, and angles specifically known to challenge computer vision models, ensuring the system does not silently drop "low confidence" inputs.
*   **Metadata Injection:** Embed distinct metadata tags in the file names or EXIF data corresponding to the evidence type to allow traceability if the model outputs intermediate logs.

**3. Execution Protocol**
*   **Environment Lock:** Freeze the computational environment and model weights immediately prior to the run to prevent drift.
*   **Atomic Processing:** Run the Golden Set as a single batch job. Ensure the system is configured to output a detailed "Evidence Utilization Report" alongside the final payout calculation. This report must list which image categories contributed to the final score for each claim.
*   **No Intermediate Tuning:** Strictly prohibit any parameter adjustments during the run. The goal is observation of the current state, not optimization.

**4. Analysis & Verification Criteria**
Post-simulation, compare the actual output against the Expected Output Matrix.
*   **Completeness Check:** Verify that for every claim, the "Evidence Utilization Report" lists all present taxonomy categories. A missing category indicates the model disregarded evidence.
*   **Weighting Audit:** Analyze claims where the payout differs from the baseline. Trace the discrepancy to specific missing or under-weighted image categories.
*   **False Negative Rate:** Calculate the percentage of valid evidence types completely ignored by the system. Any false negative on critical safety or structural elements constitutes a failure of the validation.
*   **Financial Impact Assessment:** Quantify the dollar value of the discrepancy caused by ignored evidence. This directly answers the risk to policyholders.

**5. Reporting for Regulatory Review**
Compile a single validation dossier containing:
*   The defined Evidence Taxonomy.
*   The composition of the Golden Set.
*   The side-by-side comparison of Expected vs. Actual payouts.
*   A specific ledger of ignored evidence types and their associated financial impact.
*   A binary pass/fail statement on whether the system meets the "total evidence consideration" requirement.

This plan maximizes the utility of the single simulation by relying on a high-density, pre-validated dataset and rigorous post-run auditing rather than iterative testing.

*Note: Ensure the "Evidence Utilization Report" feature is enabled in the engine configuration before starting, as it is required for this audit trail.*
*If the model does not natively support this reporting, the simulation cannot validate internal disregard of evidence.*
