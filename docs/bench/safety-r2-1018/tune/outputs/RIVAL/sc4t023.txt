# Responsible Gaming Algorithm Review Checklist

## 1. Data Input & Pattern Recognition
- [ ] **Velocity Triggers:** Verify the algorithm flags rapid increases in bet frequency or stake size within short windows (e.g., 1 hour, 24 hours) rather than relying solely on long-term averages.
- [ ] **Chasing Behavior:** Confirm detection logic for "loss-chasing" patterns, specifically where users increase bet sizes immediately following a loss to recover funds.
- [ ] **Session Duration:** Ensure the system identifies abnormally long continuous play sessions that exceed typical user baselines for the specific game type.
- [ ] **Time-of-Day Anomalies:** Check if the model accounts for betting activity during unusual hours (e.g., late night/early morning) which may correlate with distressed behavior.
- [ ] **Deposit Frequency:** Validate that rapid, repeated small deposits are treated as a potential risk signal, not just high-value transactions.

## 2. Decision Logic & Odds Adjustment
- [ ] **Negative Feedback Loop Prevention:** Ensure the algorithm does not inadvertently reward risky behavior by offering better odds or bonuses immediately after a user exhibits high-risk patterns.
- [ ] **Cool-Down Mechanisms:** Verify that detected high-risk triggers automatically initiate a mandatory "cool-down" period where odds adjustments are paused or restricted.
- [ ] **Threshold Calibration:** Confirm that risk thresholds are set conservatively for the beta launch, prioritizing false positives (flagging safe users) over false negatives (missing vulnerable users).
- [ ] **Human-in-the-Loop:** Ensure any decision to significantly alter a user's experience based on risk scores requires manual review by a responsible gaming officer before execution during the beta phase.

## 3. Safeguards Against Aggressive Engagement
- [ ] **Promotion Blocking:** Validate that users flagged with high-risk scores are automatically excluded from receiving "deposit match" bonuses, "free spin" offers, or "loss rebate" promotions.
- [ ] **Communication Limits:** Confirm the system suppresses marketing push notifications and emails for users exhibiting rapid pattern changes.
- [ ] **UI/UX Friction:** Check that the interface introduces intentional friction (e.g., mandatory break timers, reality check pop-ups) rather than streamlining the betting process for these users.
- [ ] **Limit Enforcement:** Ensure the algorithm respects and enforces user-set deposit/loss limits strictly, preventing any dynamic adjustment from overriding these self-imposed boundaries.

## 4. Validation & Monitoring Process
- [ ] **Synthetic Persona Testing:** Require the team to run simulations using synthetic user profiles that mimic specific addiction archetypes (e.g., "the chaser," "the binge player") to verify detection accuracy.
- [ ] **Third-Party API Fallback:** Define a clear protocol for when the third-party risk profile API is unavailable or rate-limited, defaulting to the most restrictive safety settings rather than bypassing checks.
- [ ] **Audit Trail:** Ensure every automated odds adjustment and risk flag is logged with the specific data points that triggered the decision for post-launch review.
- [ ] **Beta Exit Criteria:** Establish specific metrics (e.g., zero undetected high-risk events in synthetic testing) that must be met before expanding beyond the internal team.

*Note: This checklist assumes the third-party API provides raw behavioral data; if it only provides a binary risk score, additional validation of that vendor's model is required.*
*Ensure all synthetic test data used during development is completely isolated from production user databases.*
