**Preparation Plan: Baptism Registration Gender Handling**

**1. Immediate Logic Suspension (Day 1)**
Disable the automated gender inference engine immediately. Do not attempt to "correct" the pattern-matching logic, as inferring gender from parental names is fundamentally unreliable and the root cause of the distress. Replace the automated output with a mandatory, empty "Gender" field that requires explicit human selection by the church administrator or parent. This stops the generation of new errors instantly without requiring database schema changes.

**2. Harm Inventory & Impact Assessment (Day 2)**
Document the specific failure mode: the system currently presents unverified inferences as facts, violating the dignity of the sacrament and causing administrative rework. Identify the affected groups (families with non-traditional naming patterns, non-binary parents, or cross-cultural names) and record the worst-case scenario (public misgendering during a sacred rite). Assign one team member as the owner of this risk until the holiday season concludes.

**3. Data Remediation Protocol (Days 3–4)**
Since schema changes are constrained, implement an application-layer override. Create a simple "verification flag" in the existing legacy structure (e.g., reusing a nullable "notes" field or a boolean "is_verified" column if available) to mark records where gender was auto-inferred.
*   **Action:** Generate a report of all upcoming holiday baptisms where gender was previously auto-filled.
*   **Manual Gate:** Require church administrators to manually confirm or correct these specific records before certificates can be generated. No certificate prints without this human confirmation.

**4. Interface & Disclosure Updates (Day 5)**
Update the user interface to remove any implication that gender is "guessed."
*   **Labeling:** Change form labels from pre-filled values to "Select Gender" with options: Male, Female, Prefer not to say, or Custom (if the legacy DB text field allows).
*   **Disclosure:** If any historical data remains uncertain, add a discreet internal note for administrators: "Record requires verification," ensuring they know the data is not authoritative.

**5. Testing & Validation (Day 6)**
Do not test for "accuracy rates" of the old logic, as the logic is retired. Instead, test the **human gate**:
*   **Probe:** Attempt to generate a certificate with an unverified/blank gender field.
*   **Pass Condition:** The system must block certificate generation and prompt for manual selection.
*   **Edge Case:** Verify that administrators can successfully override any pre-existing bad data in the legacy view.

**6. Go-Live Governance (Day 7)**
Formalize the "Human-in-the-Loop" rule for the holiday season: No automated gender decisions are permitted for baptism records. Document this constraint in the release notes. Schedule a post-holiday review to determine if a proper schema change can be funded to support explicit data collection rather than inference.

**Note:** This plan prioritizes a human verification gate over algorithmic fixes because name-based gender inference cannot be made "accurate" enough for sacred rites.
**Note:** Legal counsel should be consulted regarding data privacy implications of storing inferred gender data, even temporarily.
