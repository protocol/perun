I found four minor issues and nothing critical. There is no SSRF, because the handle is validated and URL-encoded, the base host is fixed, redirects are rejected, and the avatar host is allow-listed. The upstream response is also capped in size and time, and only whitelisted fields are returned.

1. **Rate limiter reset (`server.js`, line 17, API4).** The limiter wipes all counters whenever `counts.size > 10000`. An attacker with many source addresses, such as an IPv6 range, can push the map past that size and reset their own counter, bypassing the 60 requests per minute limit.
2. **Rate limiting keyed on `req.ip` (`server.js`, line 21, API8/API4).** `trust proxy` is not configured. Behind a reverse proxy or load balancer, every client shares the proxy's IP, so one client can trigger 429s for everyone. If `trust proxy` is later set too permissively, `X-Forwarded-For` can be spoofed to evade the limit.
3. **Upstream fetch amplification (`server.js`, line 33, API4).** Only successful lookups are cached, so unknown or failing handles trigger an upstream request every time. There is also no global cap on concurrent upstream fetches. The `inflight` map only coalesces requests for the same handle. Rotating through many distinct handles (and IPs) can exhaust outbound capacity or the directory's quota.
4. **Incomplete `displayName` sanitization (`sanitize.js`, line 16, API10).** The directory response is trusted too much. Only ASCII control characters and `<>` are stripped. Unicode bidi overrides, zero-width characters, and other format characters pass through, which allows spoofed or confusing names. Quotes and `&` also pass through, which matters if a consumer renders the value into HTML attributes or other contexts.
