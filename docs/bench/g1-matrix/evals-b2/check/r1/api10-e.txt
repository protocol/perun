I found four issues, one of them minor.

1. **Unbounded upstream body (API10 and API4).** `directory.js` line 10 only limits size by checking the `Content-Length` header. A chunked or header-less response bypasses that check. `res.json()` on line 13 then buffers the whole body in memory, so a compromised or misbehaving directory can exhaust memory. The 4-second timeout bounds the time but not the size. I filed this under API10, since the root cause is trusting the upstream API's headers. It is also an API4 resource-consumption risk.

2. **Upstream profile not bound to the requested handle (API10).** `server.js` line 13 never checks that the returned `handle` equals the requested `req.params.handle`. `sanitize.js` validates the handle's format but not its identity. `cache.put` (`cache.js` line 7) keys the entry by the upstream-supplied `profile.handle`. A request for `/members/alice` can therefore return bob's profile and cache it under `bob`. A buggy or compromised directory can poison other users' cache entries for 5 minutes. The cache entry for `alice` is also never created, so every request for `alice` goes upstream again.

3. **No rate limiting and no negative caching (API4).** `server.js` lines 8-20 expose an unauthenticated endpoint. Each uncached valid handle triggers an outbound request. Failures and invalid directory responses are never cached. An attacker can cycle through handles to generate unlimited upstream traffic and to enumerate members. They can also flood the 1000-entry cache and evict legitimate entries.

4. **Minor hardening gaps (API8).** The Express app on `server.js` line 6 leaves the `X-Powered-By` header enabled and sets no security headers (for example via `helmet`). Nothing in the app enforces TLS or limits request size, so those protections would have to come from elsewhere.

I found no SSRF. The base URL is fixed, the handle is validated and URL-encoded, and redirects are disabled. The avatar URL is restricted to an HTTPS host allowlist.
