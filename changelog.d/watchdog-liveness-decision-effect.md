### Fixed
- `green()` in `.claude/skills/agentic-delivery/scripts/landing_watchdog.py` judged every status in a PR's check rollup, including the train's own progress marker (the `perun/train-stage` status: pending while a run is queued, gating or landing, failure after a skipped or failed run), while `merge_train.py` judges check runs only. A PR left in a dead run, or skipped once, therefore stopped counting as a green PR waiting, and every signal built on that count undercounted it. That one status is now ignored, both when judging the checks and when testing that the PR has any; any other pending status still blocks.
- `ci_head` in `train_land.sh` had the same defect, and it is a pre-existing one, not a regression of this change: it judged the whole rollup including the train's own marker, so after a skipped, failed or deferred train, where the marker is failure or error, the solo re-ride escape (a PR that rode trains without landing is landed alone once its own checks pass) could never see an all-green rollup for exactly the PRs it exists for, and never fired. It now drops the marker before judging, still requires at least one remaining check, and still reads a lookup or parse failure as not green.

### Added
- Run liveness in `landing_watchdog.py`: the rate alarms say "slow" but could not tell a slow train from a dead one. The probe now also reads the train's progress markers from the open PRs (stage = first word of the status description, time = its `at=<epoch>` else the status creation time, expected run time = `eta<=Ns` else 60 min; a marker with no stage word or no time is skipped) and the time of the newest commit on the default branch's first-parent line (a landing; a time more than 5 minutes ahead of the clock is ignored). The last train activity is the newest of every marker, whatever its run, and that landing; an outcome beats a live marker at the same second. Two warn-only messages come from it, a stuck line and a clause on the stall line, with the same throttle, cache, hook and `check` CLI, failing open.
- "Train run stuck: run R posted <stage> on K PRs X min ago (expected <= Y min), no outcome since. Check the train runner, not the PRs." fires only when the last train activity is itself a queued, gating or landing marker older than 1.5 times its expected time; it names that marker's run and stage and counts the PRs carrying the same run and stage. A run id comes from each `merge_train.py stage` call rather than from a whole train, so markers are not grouped by run: any newer marker or landing supersedes an older live one, which keeps a dead run's marker on a PR no later train re-posted from alarming for ever.
- " No train run in X min: start the train or check its runner." is a clause on the existing stall line (0 merged in the window with green PRs waiting), not a line of its own. It is added when markers exist, the last activity is not a live marker, and it is older than the larger of 1.5 times its expected time and the check window, with X counted from that last activity (a landing counts, so a healthy repo with an old skipped marker on an open PR stays quiet). A repo with no marker, or whose last marker is a fresh outcome, gets the plain stall line.
- A parsed `eta` is capped at 24 hours, so a made-up eta cannot hide a dead run for ever, and an `at=` more than 5 minutes ahead of the clock is not trusted: the status creation time is used instead (the marker is skipped when there is none), so a future stamp cannot mute the alarms.
- `gh pr list --json statusCheckRollup` exports a status's context, state and start time but not its description (checked on gh 2.99), and the stage, run id and time live in the description. So when that list shows a train marker, one extra `gh api graphql` call reads the markers of the open PRs into the default branch; with no marker listed there is no extra call, a failed or unreadable reply reads as no markers (silent), and the call shares the 15-minute throttle. The tests exercise it through a fake `gh`; it has not yet been run against a live repository.
- Decision effect: `landing_watchdog.py expect 'train_size>=N' [--hours H]` records a decision in `<git-common-dir>/perun-decisions.jsonl` (env `PERUN_DECISIONS` overrides; N and H are whole numbers >= 1, H defaults to 24, anything else exits 2 with usage). The first argument is quoted everywhere it is shown, because an unquoted `>=` is a shell redirect: bash runs the command without it and leaves a stray file named `=N`. While the newest unexpired decision is unmet, that is, at least two trains that began after it carried a median of fewer than N PRs, the hook adds "Decision not in effect: train_size>=N set X h ago; the K trains since carried a median of M PRs. Check that the runner reads it." A met or expired decision, fewer than two trains since, a ledger record without a time, and a missing or unreadable file are silent, so a decision the runner never applied no longer reads as a slow train.
- `train_yield.py record` takes an optional last argument, the epoch second the train began, and stamps each ledger line with `"start"` as well as `"at"` (the time the line was written, at the end of the train). `train_land.sh` takes the start epoch once, next to its elapsed-time clock, and passes it from its exit trap. The new `sizes_since(path, at)` returns the PR counts of the trains that began at or after a time, falling back to `"at"` for a record with no start, so a train that began before a decision and ended after it is not judged against it. A record written before the stamps never counts as after a decision, and the existing readers (`report`, `solo`, the yield alarm) ignore the new keys.
- Known limits, stated in the script's docstring: markers come only from the current heads of open PRs, so a re-push or a close in the middle of a run drops one; the creation-time fallback is the post time, not the run start; any landing supersedes a live marker, so a hand merge, or a landing stage that hangs after its first merge, silences the stuck line (the stall line still fires once nothing merges for the window); `train_size` reads the local ledger only, so trains run on another host are not seen.
- `fanout-host-sizing.md` shows one example each of the stuck line, the stall line with its idle clause, and the decision line, next to the yield and merge-rate alarms.
