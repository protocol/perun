### Added
- `route_auth_map.py --privileged` also prints `OWN:` rows, which `review_checks.sh --full` reports as tool `ownership`, rule `missing-ownership-check` (CWE-639, OWASP API1:2023). A row is an authenticated NestJS route, declared with plain verb decorators or ts-rest, that updates or deletes a record by a client-sent id (`PUT /things/:uid`) or writes an owner id from the request body (`connect: { uid: dto.ownerUid }`), where neither the controller member nor the `@Injectable` service method it calls compares the requester to the owner. A service that takes a requester argument and ignores it still counts as no check. When a public or unauthenticated `GET` lists the same collection, the row says so, because that route hands out the ids. A route with a check is not dropped: it prints as an `OWN-CHECKED:` row naming the class of check the scan read (`requester-compare`, `decorator-guard` or `machine`) and the matched text, so a reviewer can see what was taken as the check, and `review_checks.sh --full` reports it as a tool `ownership`, rule `ownership-check-read` row with that message. Check reading is a hint, never a reason to hide a route: the scan can misread a check, so a checked route is still a row to verify. The stderr summary gives both counts. These count as checks: a comparison of the requester's id (from the token, `req.user`, a requester parameter or a `@CurrentUser()`-style parameter) with an owner-like field, a `where` on the write's own call, or on a lookup of the model it writes, that sets an owner field to the requester's id (`user.id`, `requesterUid`; a bare `userId` or `authorId` variable is not the requester's id) or names an owner id in shorthand (`{ uid, ownerUid }`) whose variable is declared from the requester's id earlier in a statement of its own (`const ownerUid = requester.uid;`) and not assigned again before the `where` (`ownerUid = dto.ownerUid;`), and, on a route whose path carries a record id, also names that id (`where: { uid, ownerUid: user.uid }`); and a guard or decorator on the class or the member that names a privileged role (admin, staff, superuser, moderator or owner: `@Roles('admin')`, `@UseGuards(OwnerGuard)`) or an object-level policy check (`@CheckPolicies(...)`, or a guard named `PoliciesGuard`, `PolicyGuard`, `AbilityGuard`, `AbilitiesGuard` or `Casl...Guard`, with or without a prefix). A role decorator counts only when every role it lists is privileged, because any listed role may call: `@Roles('user', 'admin')` and `@Roles(Role.User, Role.Admin)` are not checks. `@Roles('user')`, a bare `RolesGuard`, a permission decorator and a guard whose name only contains the word, such as `AvailabilityGuard` or `CapabilityGuard`, say who may call, not whose record it is, so they are not checks. Nor is a `where` with a bare `id`, `uid` or `pk` set to the requester's id (the requester's own row), a `where` on another model, or, on a route whose path carries a record id, a requester-scoped `where` that does not name that id (another model's `updateMany({ where: { userId: requester.uid } })`, or a lookup of the same model by owner alone). A comparison with `null`, another literal or a named constant (`requester.uid === SYSTEM_UID`), a comparison of the client body with the record (`dto.ownerUid !== t.ownerUid`), a client-sent owner id compared with the requester on a route whose path carries a record id (read directly or through a local such as `const { ownerUid } = dto`), a destructure default (`const { ownerUid = requester.uid } = dto`, on one line or several) and a local named `user` that holds a loaded record are not checks. Only guard and role decorators are read; `@UseInterceptors(...)`, `@UsePipes(...)` and parameter decorators never count, whatever their names say. Nothing else counts: a role or policy word in a body (`this.policies`, `UpdatePolicyDto`, `dto.capabilities`), a helper call whatever its name (`hasOwner(t)`, `assertOwner(...)`), and a `ForbiddenException` or other 403 thrown for any reason all keep the row, so some rows are false positives where the check lives in a helper. Words inside string literals outside a guard or role decorator's arguments (a `@Controller('policies')` prefix, a `@Put(':uid/availability')` path, a log message) and Swagger `@Api*(...)` decorators never count. A field set from the requester's id, such as an `updatedBy` audit field or `ownerId: user.id` in a write payload, is not a check. A route is `machine` only when every guard on its class and method is a machine-credential guard (an internal, service, integration, machine or M2M auth, key or token guard, but not one whose name also accepts a user or session, such as `JwtOrApiKeyGuard`; a bare or org `ApiKeyGuard` is not one, because a user or an org often holds that key), because no end user calls it. A user guard next to a machine guard keeps the row `OWN`. Guards are read from the class and method decorators only, so a guard a controller merely imports does not count. The scan follows one hop into the service, including the helper methods that service calls on its own class; a service class name that two files define reads both. A check inside a guard class, a base class or a deeper repository layer is not seen. Routes that already have a `privileged-route` row are not repeated. Known misreads, where a route the scan reads as checked can still let one user write another's record: a client owner value not named `dto` or `body` (`req.body.ownerUid`, `@Body('ownerUid')`, `@Query`), a comparison that does not gate the write (it only sends a notification, sets a flag, or runs a `findFirst` whose result is never checked), a lookup on another model, a spread after the owner key (`where: { uid, ownerUid: requester.uid, ...dto }`), a privileged word in a decorator that is not an auth decorator, a guard imported under an alias, the precedence between a class and a member `@Roles`, two service classes with the same name, and a requester loaded from a client-sent id. ts-rest handlers that implement a whole contract at once print no row either way. The write call can be a Prisma, TypeORM (including `increment` and `softRemove`), Sequelize, Mongoose (`findByIdAndUpdate`, `findOneAndDelete`, `replaceOne`, `bulkWrite`) or MikroORM (`nativeUpdate`, `nativeDelete`, `persistAndFlush`) method. Known misses: a write through MikroORM `em.flush()` after `wrap(t).assign(dto)`, Knex `.del()` or a CQRS `commandBus.execute(...)` makes no row at all, and a Mongoose or MikroORM filter that scopes the write to the requester (`findOneAndUpdate({ _id: uid, owner: requester.uid }, dto)`) is not read as a check, so that route stays an `OWN` row.

### Changed
- `ownership_sibling_check.py` no longer reads a 403, `Forbidden`, `PermissionDenied` or `PermissionError` in a handler as an ownership check, because a handler can refuse for any reason (an archived record, a field too long). A handler that loads a record by a client id and only raises 403 is now reported when a sibling checks ownership.
- `ownership_sibling_check.py` no longer drops a handler that has its own check. It prints it as an `OWNERSHIP-CHECKED:` row with the class of check (`decorator-guard`, `guard-call` or `requester-compare`) and the line or lookup it read. `review_checks.sh` still reports only the `OWNERSHIP:` rows, and the stderr summary gives both counts.
