### Added
- `.claude/skills/agentic-delivery/scripts/privacy_guard.py`: a PreToolUse(Bash) hook that denies (exit 2) a GitHub write whose title or body matches the repo's banlist. Nothing scanned the text an agent publishes, so a banlisted identifier in an issue or PR body went out unchecked while the privacy gate only read committed files. It covers what `comms_guard.py` covers and reads text through its extraction: `gh pr|issue|release create|edit|comment`, and `curl` or `gh api` calls to `repos/<owner>/<repo>/pulls` or `/issues`, with the title (`--title`/`-t`, `-f title=`, JSON `title`) and the body (`--body`, a heredoc, `$(cat FILE)`, `--body-file`, `-d` or `--input` JSON, `-f body=`, `-F body=@FILE`). `-f`/`--raw-field` text is scanned as typed (gh sends `@jane` as a mention); only `-F`/`--field` reads `@FILE`, and an `@FILE` it cannot read is scanned as typed. Every write in a command is read, not only the first. A body file that the same command writes (`> F`, `>> F`, `tee F`) is read from the heredoc that feeds it, because the disk holds an old copy or none and the command's other heredocs (a `python3 - <<'PY'` script, a `git commit -m "$(cat <<'EOF' ...)"`) are not the body: a clean rewrite is no longer denied for the stale text or an unrelated heredoc, and a banlisted heredoc is no longer missed because the file does not exist yet. The patterns are the actionable lines of `.banlist.txt` then `.banlist.local.txt` at the git top-level of the session directory (a linked worktree falls back to the main checkout's gitignored local file), each run through `grep -E` over each line of the text, as `ci-gates.sh privacy` runs it. The deny reason names the title or the body line number and the pattern's 1-based number among those lines, never the matched text. It fails open: no repo, no banlist, no title or body, an unreadable body file (a readable title is still checked), bad input, a missing `git` or `grep`, or any error allows. Opt out for a session or project with `PERUN_PRIVACY_GUARD=off` in settings `env`. The module docstring lists what it does not cover (merge and review, `--fill`, a body fed to stdin by a pipe, text built from a shell variable, close and reply routes, and other forms). It is registered in the operating-layer template on the Bash matcher without `|| true` (which would turn the deny into an allow), listed in `perun_doctor.py` `HOOK_SCRIPTS`, and has a row in `scripts/guard-registry.tsv`.
- Scope of the banlist scan. The scan runs on every write except one whose explicit target is a sibling: another repository under the owner of the session's `origin` remote, where a private repository's name belongs. The session's own repository (implicit, or named by `-R`/`--repo`, a github.com URL or a `repos/` path), the Perun repository, every other owner's repository, a write that names no repository and a session with no usable `origin` stay scanned, and a write that names several repositories is skipped only when every one is a sibling. The target is read from the write's own region: from the write to the next `gh` or `curl` write or to the end of its command line (`&&`, `||`, `;`, `|`, a newline or a `#` comment; a backslash-newline continues the line). A `.git` suffix is dropped, so the session repository's clone URL still names the own repository. Heredoc bodies, quoted strings that hold a space and a one-word title or body are blanked first, so text that only mentions a repository (a body quoting `-R acme/other` or naming `repos/acme/other/issues/3`, a later `echo filed https://github.com/...`) sets no target and a write cannot skip the scan by naming a sibling in its text.
- Own-repository rule in the same hook. A project's banlist does not list the project's own name, so a field report filed from that project's session into the public Perun repository carried the name past the banlist. When a write targets the Perun repository (`SELF_REPO`, by `-R`/`--repo`, a `repos/protocol/perun/` path or its github.com URL, read from the write's own region as above) and the session's `origin` remote names a different repository, a title or body line that names that repository is denied: as `owner/name`, or as the bare name when it is distinctive (it holds `-`, `_` or `.`, or has 8 or more characters), case-insensitive and whole word. The reason gives the location (`title`, `body line N`) and never the name. It needs no network, and a session inside the Perun repository, with no `origin`, or with an unparsable one has no such rule. Reading the target from the write's own region also stops a write that names the session repository from being denied for an unrelated mention of the Perun repository later in the command or in its text.
- `scripts/test_privacy_guard.py` (40 offline tests on fictional Acme fixtures in throwaway git repos, wired in `scripts/ci-tests.d/privacy-guard.sh`): every write form and every title form is denied without echoing the text, line and pattern numbers (an invalid ERE is skipped, not renumbered), the five-hit cap, POSIX-class and case-sensitive matching through `grep -E`, the linked-worktree fallback, the allow paths (clean text, other commands, no repo, no banlist, an empty banlist, an unreadable body, the opt-out, bad input, another tool), the template and doctor wiring, `-F body=@FILE` followed by more arguments, flag-like words inside a quoted title or body or a heredoc body, every write in a command, a body file the command writes itself (fresh, stale, and beside an unrelated heredoc), `-f` against `-F` for `@`, the own-repository rule (each target form, ssh and https origins, other targets, a Perun session, no origin, short and distinctive bare names, whole-word and case-insensitive matching, both reasons together, a failing `git`), and the scope rule on an acme/acme-widgets session (each sibling target form skipped; the own repository, Perun, another owner, a Perun origin or none, an origin in the Perun organisation and a `-r` reviewer scanned; text that only names a sibling; a sibling write beside an own write; six tail cases that must allow and the controls that must still deny). Twenty-nine mutants of the new code (the sibling skip, the target region and its blanking, `-f` against `-F`, the feeding heredoc, the origin parse) each fail at least one of these tests.
- `scripts/guard-registry.tsv` and the `# rail:` header of `privacy_guard.py` state the new scope in the same words.

### Changed
- `comms_guard.py`: `_rest_body(tail, cwd)` is now `_rest_field(tail, cwd, key, literal=False)`, so the title of a REST write is read by the same code as its body. `extract` still returns the body and the existing comms_guard tests pass unchanged. `literal` makes an unreadable `-F body=@FILE` come back as the typed text instead of raising; only `privacy_guard.py` passes it, so the comms lint still treats an unreadable file as no body.
- `comms_guard.py`: `-F body=@FILE` and `-F 'body=@FILE'` read `@FILE` as one shell word, so more arguments after it (`--jq .id`, `-f title=t`, `&& echo done`) no longer turn the read into a failure and a skipped lint. A flag-like word inside a quoted string or a heredoc body (the title "Add -b flag", a body that mentions `-t`) is no longer read as a flag: `_flags` blanks quoted strings and heredoc bodies (the new `_plain`, which the privacy hook's target region reuses) before it looks for a flag, and an unclosed quote hides nothing. Blanking keeps the raw offsets that the heredoc and `$(cat FILE)` readers need, which a shell tokenizer would not, and it falls back to the earlier first-textual behaviour wherever a quote does not pair.
- `comms_guard.py`: `@` means a file only for `-F`/`--field`. `-f`/`--raw-field` sends its text as typed, so `-f body='@jane thanks'` and `-f title='@jane ...'` are linted and scanned as written; the first version of this change read them as a missing file and skipped them, and the earlier code read an unquoted `-f body=@FILE` as a file that gh does not read. A comms lint of `-f body=@FILE` now sees the text `@FILE`.

Decision record (evil twin). Skeptic: a deny hook that agents cannot see into will occasionally block a legitimate write, and the secret-shaped patterns here lack the gate's placeholder relaxation. The banlist is the session repo's, so a write into another owner's private repository that names the session project is denied, and a name that is legitimate there must be reworded. Better way: relax secret patterns with `secret_scan.py`'s placeholder rule, ask the network whether the target is private, or skip every write that has `--repo`. All rejected. The relaxation script lives under `scripts/` and is not installed with the skills, so the hook would behave differently per install. A visibility lookup needs the network and a token, which this hook avoids, and a failed lookup must either block or leak. Skipping on any `--repo` would exempt the upstream-contribution flow, where a leak into a public repo matters most; the sibling rule skips only the origin owner's other repositories, so a write into Perun or into another owner's repository stays scanned. Accepted residuals: a public sibling in the origin's organisation is not scanned, so a banlisted identifier written there goes out; another owner's private repository is scanned, so a legitimate name in it is denied (reword it or opt out); a target set by `GH_REPO` is not seen. A blocked line is cheap to reword because the reason names it, and `PERUN_PRIVACY_GUARD=off` is the owner's escape. The own-repository rule trades a missed short bare name (caught only as `owner/name`) for never denying an ordinary word such as `app`; a list of the session's own words is the upgrade if a leak slips through. Kill criterion: two false positives from a secret-shaped pattern, from a write into another owner's repository, or from the own-repository rule in one release means narrow the hook (drop those sections, ship the relaxation, or drop the bare-name match) before it blocks more work, and one banlisted identifier that reaches a public sibling means drop the sibling skip.
