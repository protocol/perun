### Fixed
- `handback_cap.py`'s background-work block text no longer says "You own it until it exits". The scan matches any test or build whose cwd is in the lane's worktree, and that process may have been started by someone else working in the same worktree. The text now says what the lane can do (wait for the pid with `lane_guard.py wait --pid <pid> --timeout <s>`, or stop it if this lane started it) and that the hold ends on its own after `HANDBACK_PUSH_MAX_S` (30 minutes by default) at most, as the push and commit hold text already did.
- A hold's window now restarts once its condition is gone. `_hold` keeps the first block's time as the mtime of the lane's `.push`, `.bg` or `.dirty` state file and nothing removed that file, so after one block that was more than 30 minutes old, a later push or commit, background run or dirty tree in the same lane was released at once instead of being held for a fresh window. `check()` now removes the lane's state file (new `_release`, which ignores `OSError`) for each hold whose check found no such condition, so the next block opens a fresh `HANDBACK_PUSH_MAX_S` window. `check()` also no longer returns at the first hold that blocks: the push or commit, background and dirty-worktree checks are all evaluated before it returns 2, so the reset also happens while a higher hold blocks (for example: a dirty-worktree hold opened more than 30 minutes ago, the tree cleaned while a commit is still running, the commit ending, the tree dirtied again, and the lane is held again for a fresh window). The first hold that blocks still wins in the same order (push or commit, background, dirty) with the same text, a lower hold is still never started on a call where a higher one blocks, and a blind lower check now prints its `COULD_NOT_CHECK` line before that hold's text. A check that could not run (`COULD_NOT_CHECK`) keeps the hold, and a condition that stays live past the window is still released, so a stuck process cannot trap the lane. The dirty-worktree hold goes through the same `_hold` and gets the same reset.

### Changed
- The `_push_running` docstring and the comment above `PUSH_RE` now state a known limit: `ps` prints argv without quoting, so a space inside a `-c` value or a `-C` path splits it (`git -c user.name=Jane Smith commit`, `git -C /acme/my repo commit`), `PUSH_RE` does not match, and that push or commit is not held (the check fails open and does not print `COULD_NOT_CHECK`). The behaviour is unchanged; it is now documented and pinned.
- Test: `python3 .claude/skills/agentic-delivery/scripts/handback_cap.py --selftest` (already run by CI) goes from 83 to 117 cases. Ten of the new ones fail on the previous code (107 of 117 passed there): each of the push, background and dirty-worktree holds starting a fresh window when the condition clears and returns (old first block, condition gone, condition back, held again); the background and dirty holds doing the same when a higher hold blocks while their own condition is gone, including their state file being removed; and the background hold text naming the way out rather than ownership. The other twenty-four pin behaviour that already held: the first block and the release after the window for each of the three holds, a condition that clears and passes, a hold whose scan could not run keeping its state file, a lower hold opening its first block, the first hold that blocks winning (push or commit, then background, then dirty) with no lower hold started, `_skip_pids` skipping the hook's ancestors and descendants (a synthetic process table, hook then child then a grandchild `git commit`) while an unrelated `git commit` pid is still counted, the same through `_push_running`, and three `known-limit-*` cases (a `-c` value with a space and a `-C` path with a space are not held, a `-c` value without one is). Each of the three keep-on-`None` cases fails when its scan's `None` is treated as empty (`if not running`, `elif not bg`, `elif not dirty`).
