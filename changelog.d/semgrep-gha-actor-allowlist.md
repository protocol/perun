### Added
- One bundled GitHub Actions semgrep rule in `templates/semgrep-taint/gha.yml`, for a workflow that authorizes `github.actor` against an allow-list read from a repository variable: anyone with write access can edit repository variables, so any writer could add themselves. `review_checks.sh` already loads the whole template directory, so it runs in the default review with no wiring change, like the other bundled rules (and, like them, only when the repo has no semgrep rules of its own).
- `perun.gha.actor-allowlist-from-vars` (WARNING; a heuristic lead, so the message starts with `[heuristic]`), scanned only in `.github/workflows/*.yml|yaml` and `action.yml|yaml` (language `regex`, not `yaml`, so a file that fails YAML parsing is still scanned): an actor check (`github.actor`, `github.triggering_actor`, `GITHUB_ACTOR`) fed by `vars.NAME`. Three regexes, comment lines skipped: the variable and the actor are the two operands of one comparison or `contains()` (any variable name), or a variable named like an allow-list (allow, releaser, deployer, approver, admin, maintainer, trusted) and an actor reference sit in one step, in either order. The message says who can edit what (anyone with write access can create, update and delete repository variables, and a repository variable overrides an organization variable of the same name) and names the fix: an environment variable read in a step of a job that declares that environment (creating one needs admin access in an organization repository, and environment variables are only available once the job starts, so not in a job-level `if`), or a code-owned file. Known ceilings: the rule cannot see where a variable is defined, so a job that already reads the list from its environment still flags (the message says to drop the lead); a hint-named variable and an unrelated actor reference in one step flag; `context.actor`, `GITHUB_ACTOR_ID` and a job- or workflow-level `env` compared in a later step are not matched.
- New test `scripts/test_semgrep_gha_actor_allowlist.py` (registered in `scripts/ci-tests.d/semgrep-gha-actor-allowlist.sh`): fictional workflow and `action.yml` fixtures annotated `# ruleid:` and `# ok:` (14 expected hits: 9 in one release workflow, 1 in a `.yaml` deploy workflow, 1 in each of three composite-action copies, 1 in a workflow that is not valid YAML), with a literal list, a bot check, an unrelated variable, a hint-named variable with no actor, adjacent steps and jobs, a code-owned file and a commented-out check as the clean cases, plus a copy under `docs/` that must stay clean. The live part runs semgrep offline with one job and prints SKIP without it; CI installs none, so the offline part replays the rule's own regexes with Python's `re` over every fixture and pins the severity, the `[heuristic]` message, the name hints and the path scope. Against the previous release's `templates/semgrep-taint` the live check misses all 14 expected hits, and a copy of the rule with `languages: [yaml]` fails on the invalid-YAML workflow.
- `references/tool-hub.md` gains one table row for the rule (no reference listed the bundled semgrep rules by id, so the CLI tools table is the nearest home), and `docs/standards-index.md` logs the five GitHub Docs pages fetched 2026-10-30 that ground the message, including that the REST page says "collaborator access" for environment variables where the how-to page says `admin`.
