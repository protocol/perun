### Changed
- `perun.js.ssrf` (in `.claude/skills/deep-code-review/templates/semgrep-taint/js.yml`) now also reads app-router input, the same sources as `perun.js.sqli`, only inside an exported `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE` or `OPTIONS` handler (`export async function`, `export function` or `export const NAME = async (...) =>`) with the request as its first parameter: the URL search parameters (`request.nextUrl.searchParams`, `new URL(request.url).searchParams` with or without a base argument, `searchParams` of a variable assigned `new URL(request.url)` earlier in the same block, and `searchParams` destructured from `new URL(request.url)` or from `request.nextUrl`) and `await request.json()`, `await request.formData()` and `await request.text()`. A function that is not such a handler is not a source, and every existing source, sink, sanitizer and guard is kept, so a `fetch`, `axios`, `got`, `http.get` or `https.get` call that takes such a value is reported unless an allowlist check that returns before the call guards it. Left out: route-segment `params` (dynamic route params); a handler passed by name or wrapped in another call (`export const GET = handle`, `export const GET = withAuth(async (request) => {...})`); `request.nextUrl` held in a variable or a destructured name (`const url = request.nextUrl`, `const { nextUrl } = request`); and a body read through `.catch(...)` or `.then(...)` (`await request.json().catch(() => null)`).
- `perun.js.path-traversal` reads the same app-router input in the same handlers, keeping every existing source, sink, sanitizer (`path.basename(...)`) and guard, so a value that reaches `fs.readFile`, `fs.readFileSync`, `fs.createReadStream`, `fsp.readFile`, `res.sendFile`, `res.download` or `response.sendFile` is reported. Left out: a bare `readFile(...)` imported from `fs/promises`, and `fs.promises.readFile(...)` with the other `fs.promises` reads, are not sinks (the file-system reads are matched only on the receivers `fs` and `fsp`); the other gaps listed for `perun.js.ssrf` apply here too.
- `perun.js.open-redirect` reads the same app-router input in the same handlers and also reports the first argument of `NextResponse.redirect(...)` and `Response.redirect(...)`. The rule still has no guard or sanitizer, so a target is reported even after a check: a `startsWith("/")` test that also rejects `//` does not make it safe, because the URL parser reads `/\host` and `/<tab>/host` as another host. A constant target such as `new URL("/login", request.url)` stays clean. Left out: the `redirect()` and `permanentRedirect()` of `next/navigation` are not sinks; the other gaps listed for `perun.js.ssrf` apply here too.
- `perun.js.fetch-no-timeout` now also matches a Next route handler declared as `export function NAME(...) {...}` (not async) or `export const NAME = async (...) => {...}`, with any number of parameters, and the methods `HEAD` and `OPTIONS` beside `GET`, `POST`, `PUT`, `PATCH` and `DELETE`. Handlers are matched by shape in any file outside the test paths, so a non-async `export const NAME = (...) => {...}`, a function expression (`export const NAME = function (...) {...}`), an expression-bodied arrow (`export const NAME = (...) => fetch(url)`) and a non-route file such as `lib/http.ts` that exports such a name are matched too. The pages handler and Express callback branches, the signal and spread-options exemptions and the test-path excludes are unchanged, and only `fetch` is matched. Left out: a handler passed by name or wrapped in another call (`export const GET = handle`, `export const GET = withAuth(async (request) => {...})`) is not seen.
