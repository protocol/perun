### Added
- `review_checks.sh` now routes guarddog 3.2.0 as an offline supply-chain heuristic step. With a base, it reads every changed `package-lock.json`, finds the npm packages the lock newly adds (a name@version pair absent from the merge-base lock, so a version bump counts as new) and runs `guarddog npm scan --output-format json DIR` on each one that is installed under `node_modules` inside the repo at the locked version. The installed `package.json` must say so: a lock-only bump leaves the old code on disk, and scanning it would read as clean, so that package is counted as not installed at the locked version. Packages whose lock entry has `hasInstallScript` go first. At most 25 are scanned, within a total budget of about 300 s (`REVIEW_GUARDDOG_BUDGET`, in seconds; each scan also keeps the usual 60 s timebox), and every package left out is named in a `not-checked` row. The step runs only when `guarddog --version` says 3.x (the scan JSON was checked on 3.2.0); any other answer is one named `not-checked` row.
- Leads and gaps. Each `threat-*` rule that hits becomes one lead per package and rule (first location and hit count), tagged `[heuristic]`. `capability-*` rules fire on benign packages and stay quiet, and code or match snippets are never read. A rule that errors (guarddog lists it under `errors`) costs only that rule: the other hits stay and a `not-checked` row names the failed rule. Output with no `threat-*` rule at all is not-run. A lock that adds nothing is silent; nothing installed at the locked version, a lockfileVersion 1 lock, an unparseable lock and `--full` (no base) print one `SKIPPED` line each. It never runs `verify` and never fetches a package: guarddog treats a non-directory argument as a registry name, so only existing in-repo directories are passed.
- Control characters never drop a row. A `\r` in a package name, lock key or hit location used to split the row, and the closing summary dropped the pieces silently. Those characters now show as `?`, and a lock entry that cannot be scanned safely (no version, or control characters in its name, version or key) is a named `not-checked` row, never skipped quietly.
- Install hooks. guarddog's install-hook rules (`threat-npm-preinstall-script`, `threat-process-hooks`) match `*/package.json`, a nested path, so they never flag a package's own root `package.json`, where install hooks live (checked on 3.2.0 with fictional fixtures). A newly added lock entry with `hasInstallScript` is therefore a lead of its own (tool `package-lock`, rule `has-install-script`, tagged `[heuristic]`), emitted whether or not guarddog is installed.
- guarddog has no offline flag, and at startup it refreshes its top-package lists from github.com, hugovk.github.io and packages.ecosyste.ms (seen under a dead proxy). The supported opt-out is the environment variable `GUARDDOG_TOP_PACKAGES_CACHE_LOCATION` pointing at a directory of fresh stub lists, which a local scan never reads. The step sets it. When guarddog's own kernel sandbox cannot start (a nested sandbox: its stderr says `Sandbox initialization failed`, matched case-insensitively), the step retries once with `--no-sandbox` and keeps a dead proxy (`HTTP_PROXY` and friends pointing at 127.0.0.1:9) on every later scan, because that sandbox is what otherwise blocks guarddog's network.
- New test `scripts/test-review-checks-guarddog.sh` (68 checks with guarddog installed; 60 checks plus one SKIP line where it is not, as in CI; registered in `scripts/ci-tests.d/review-checks-guarddog.sh`). It runs git with `GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null` and clears the proxy variables. A shim covers found, clean, crash, bad JSON, no threat rule, rule errors, a wrong or failing `--version`, the nested sandbox with its real capitalised message, `--full`, a missing tool, the cap, the time budget and its order, a removal-only lock, nothing installed, a stale install, no lock at base, a v1 lock, a moved base tip, control characters and the `hasInstallScript` leads. The real-binary section is host-only: CI has no guarddog, so it prints one SKIP line there. It uses fictional packages (placeholder names, `example.invalid` hosts) and includes a control proving the no-egress check can fail: an empty-dir scan with an empty cache dir under a dead proxy must print a download error. Against the script from before the guarddog step it fails 47 of 68.
- `tool-hub.md`: a CLI row for guarddog, the egress and dead-proxy lines, and one line saying pinact (`pinact run`) is the fixer for unpinned-action findings; it needs the GitHub API, so never in offline runs.
- Measured on the installed `node_modules` of a real app (2026-10-30, guarddog 3.2.0, `--no-sandbox` because the host sandbox nests; taken before the 3.x version probe, about 0.3 s, was added): 25 newly-added-style packages (evenly spaced by name from the 382 top-level packages without nested dependencies, 6.4 MB) took 15.7 s for the whole `review_checks.sh` run (0.3 s without the step) and produced 0 leads. The largest package alone (next 16.4.3, 192 MB of compiled bundles) took 20.1 s and produced 10 leads, all presumed false positives (heuristic matches in bundled framework code, not audited by hand). Expect leads on large bundled packages; small packages stayed quiet.
